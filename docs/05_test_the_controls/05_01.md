# Task 05-01 — DLP policies

## Introduction

Data Loss Prevention (DLP) in Power Platform is a **connector-governance** control. It sorts every
connector into Business, Non-Business, or Blocked, refuses to let data flow between the Business and
Non-Business groups in the same agent or flow, and can block named connectors outright — including the
generic **HTTP action** and **custom connectors**. It is the first thing most platform teams reach for,
and it is genuinely useful. It is also frequently asked to do jobs it structurally cannot do, so this is
the right place to learn where its boundary sits.

## Description

You will confirm the estate's DLP posture (a baseline policy applies to `Halcourt-Prod` only; the
default, `Claims-Test`, and `Maker-Sandbox` environments have none), then configure DLP to block the
generic HTTP action and custom/MCP connectors in the environments that need it. Then you return to two
Module 4 failures and retest: **Scenario C** (excessive connector / tool permissions — Claims Copilot's
Dataverse reach and Underwriting's `run_query`) and **Scenario E** (the Policy Lookup Bot's hard-coded
HTTP action and the Underwriting MCP server). You record two verdicts and, for each, the risk that DLP
leaves behind.

## Success Criteria

- [ ] You can state, per environment, whether a DLP policy applies and what it classifies.
- [ ] You configured (or, offline, specified precisely) a DLP policy that blocks the HTTP action and
  custom/MCP connectors in a target environment.
- [ ] You re-ran Scenario C and Scenario E against the configured policy and observed the result.
- [ ] You recorded a **CLOSES IT / DENTS IT / MISSES IT** verdict for DLP against both C and E in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.
- [ ] You can articulate the one thing DLP cannot see: the semantic content of grounding text.

## Key Tasks

### 01: Map the current DLP posture and configure a policy

Before you change anything, know what is already there. Then tighten the environments that carry risky
connectors.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Power Platform admin center** (PPAC), open **Security → Data and privacy → Data policy**. The
   **Applied to** column shows which environments each policy is scoped to. Confirm the baseline
   `Halcourt-Prod-DLP` applies to `Halcourt-Prod` and that `Claims-Test`, `Maker-Sandbox`, and the default
   environment have **no** policy. Then open the baseline (**Edit Policy → Prebuilt connectors**) and read
   what it actually does: which connectors sit in Business, which group a new connector lands in by
   default, and whether it blocks anything.
2. Offline, corroborate this from your `environments-export.csv`: the `dlp_policy` column is populated for
   `Halcourt-Prod` only and blank for the other three. This is the gap the attackers in Module 4 relied
   on — the "test" and default environments are ungoverned.
3. Open (or create) a data policy scoped to `Halcourt-Prod`. In the connector classification, move the
   generic **HTTP** / **HTTP with Microsoft Entra ID** connector and **custom connectors** to the
   **Blocked** group. This is the lever meant to govern the Policy Lookup Bot's HTTP call and the
   Underwriting Assistant's MCP calls. Both are nodes inside the agents' topics, not connections, and the
   documented behavior covers them: blocking the HTTP connector stops agents that contain HTTP request
   nodes from publishing, **endpoint filtering** on the HTTP connector is the finer lever (allow or deny
   specific endpoints), and an MCP server reached through a Power Platform connector is blocked along with
   that connector. The retest confirms whether that enforcement holds in this tenant.
4. Decide, deliberately, what to do about `Claims-Test`. It has no DLP and is a production-use candidate
   (Scenario F). Extend a policy to it, or note that leaving it ungoverned
   is itself the finding.
5. Classify **Dataverse** and **SharePoint** into the Business group so they cannot be combined with an
   unmanaged data-egress connector in the same agent. Save and publish the policy.
6. Give the policy a minute to apply, then reopen the affected agents in **Copilot Studio** and look for
   the connector being flagged or disabled.

{: .warning }
> **Expect side effects.** In this lab's tenant, a data policy that split Business from Non-Business in
> `Halcourt-Prod` stopped agents with a connector tool from publishing: *"There is a conflict between
> business and non-business connectors."* Copilot Studio agents pull in platform connectors of their own,
> and at least one of them landed in the Non-Business group — which one, the platform doesn't say.
> Knowledge-only agents were not affected. If your policy breaks the legitimate agents, record that too: a
> control that blocks the business is a control someone will switch off.

</details>

### 02: Re-run Scenario C and Scenario E, then record the verdict

Configuring is not testing. Go back to the two scenarios and run the *same* steps you ran in Module 4.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario E first** (it is the one DLP is built for). Re-open
   [Task 04-05 — HTTP / MCP / tool boundary]({% link docs/04_break_the_agents/04_05.md %}) and repeat the
   Policy Lookup Bot and Underwriting Assistant checks. The documented expectation: with the HTTP
   connector blocked, an agent with an HTTP request node can no longer be published; an MCP server reached
   through a blocked Power Platform connector is blocked with it. Observe whether that holds here: can the
   agent still be published and run the HTTP action? Can the Underwriting Assistant still reach its MCP
   server? Note whether the block stops the calls — and separately, whether it does anything about
   the static API key and static bearer token themselves (DLP governs connectors, not the credential design
   behind a call).
2. **Scenario C.** Re-open [Task 04-03 — Excessive connector / tool permissions]({% link docs/04_break_the_agents/04_03.md %}).
   Re-run the Claims Copilot Dataverse checks. Watch carefully: DLP decides *whether the Dataverse
   connector is allowed*, but it does not change **what svc-claims can read inside Dataverse** once the
   connector is allowed. Ask yourself whether blocking or allowing the connector changed the over-read of
   Customer PII at all. For Underwriting's `run_query`, note whether your DLP change removed only the
   over-scoped tool, the whole integration, or nothing at all.
3. **Offline path.** From `connections-export.csv`, `HTTP-PolicyAPI` (auth `API key in action config`) and
   `MCP-Underwriting` (auth `Static bearer token`) are the integrations a Prod DLP that blocks HTTP and
   custom connectors is aimed at. Neither is a Power Platform connection — the pack lists them so every
   credential is in one file. The documented expectation is that an HTTP block stops the HTTP request node
   from publishing and that an MCP server reached through a blocked connector is blocked with it; offline,
   record that expectation as unconfirmed in this tenant. `DV-Claims-Shared` (auth `Service account`) is a
   first-party connector — reason about whether DLP changes the *permissions* svc-claims holds inside it.
   Record the result as a reasoned conclusion.
4. Record a verdict for **DLP × C** and **DLP × E** in the matrix. For each, write the remaining risk in
   one line — the thing that is still true after DLP is on.

</details>

{: .caution }
> This is a re-run against an intentionally vulnerable training estate the facilitator provisioned. You
> are here to **observe and record** whether the connector is stopped — not to extract data. Do not export
> real customer records or exfiltrate the API key; note that the path exists and move on.

{: .important }
> **The boundary to name.** DLP sees *connectors and the data flows between them*. It cannot see the
> **semantic content** of text the agent is allowed to ground on. An injection instruction hidden in an
> approved SharePoint document (Scenario A) and an exfiltration coaxed out through an allowed grounding
> source (Scenario B) both travel entirely inside connectors DLP has already permitted. Keep that in mind
> when you are tempted to reach for DLP against those two scenarios in later tasks.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **DLP × E:** suggested **DENTS IT**. Blocking the HTTP connector (or filtering its endpoints) and the
  connector behind an MCP server stops those calls from being published or made, once the retest confirms
  enforcement. The static API key and static bearer token still exist and still work wherever the
  integration is allowed; DLP does nothing to the credential design.
- **DLP × C:** suggested **MISSES IT** (or **DENTS IT** if you blocked the whole integration). DLP decides
  whether the Dataverse connector is allowed, not what `svc-claims` can read once it is. Removing the
  over-scoped `run_query` tool only by blocking its whole integration trades the business function for the
  fix.
- **Remaining risk to note:** grounding content (Scenarios A and B) travels inside connectors DLP already
  permits.

</details>

## Summary

DLP is a connector firewall. It answers "should this agent be able to use the HTTP action or a custom
connector at all?" and does not answer "what can an already-allowed connector reach, and what does the text
flowing through it say?" You configured it against the estate, retested Scenarios C and E, and located the
two failures (A and B) that live in a layer DLP cannot inspect. Record the verdict and remaining risk in
the matrix.
