# Task 05-05 — Agent 365 governance

## Introduction

Governance tooling — **Agent 365** — is where you get an inventory of every agent and its identity,
ownership records, orphaned-resource detection, and lifecycle policy. It is the control most likely to *find*
the estate's lifecycle failures for you. The discipline this task teaches is the difference between a control
that **solves** a problem and one that merely **exposes** it: an inventory that lists an orphaned agent has
done something valuable, but the agent is still orphaned until someone acts.

## Description

You will look at the estate the way the Agent 365 registry sees it, record what it finds and what it
misses, write the ownership policy the findings call for, then retest **Scenario F** (lifecycle) after
your facilitator blocks Onboarding Guide. For each finding you record whether governance **closed** it
(the agent actually stopped) or only **exposed** it (it appears in a list, and remediation is a separate
action).

## Success Criteria

- [ ] You searched the registry for your estate id and recorded which of the estate's agents it lists, and
  which it doesn't.
- [ ] You recorded what the **Agents without owners** and **Agents at risk** tiles show for the estate, and
  what that misses.
- [ ] You wrote an ownership policy: the owner rule, and one action for each lifecycle finding.
- [ ] You retested Scenario F by reading Onboarding Guide's registry **Status** while it was blocked.
- [ ] You recorded the **Agent 365** column's **F** cell in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), with a
  **Retest log** block.

## Key Tasks

### 01: Find the estate in the registry

The registry is Agent 365's inventory: if an agent isn't in it, none of its detections can see it.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the Microsoft 365 admin center, select **Agents** → **All agents**, and stay on the **Registry** tab.
2. Read the four summary tiles: **Total agents**, **Agents at risk**, **Agents without owners** and
   **Connected platforms**. They count the whole tenant, not just your estate.
3. Search the list for your estate id.
4. Compare the result with the agents in your inventory, and record which agents are listed and which are
   not.

</details>

Without the tenant: in `agents-export.csv`, note each agent's environment; the registry lists only agents
in the default environment, so record the rest as not listed.

<details markdown="block">
<summary>Reveal what the search returns</summary>

Two agents: **Expense Helper** and **Onboarding Guide**, the two in the default environment. Claims
Copilot and the agents in `Halcourt-Prod` aren't listed. Record that as a finding: the registry misses
every agent outside the default environment, so nothing it detects covers them.

</details>

### 02: Check for the orphan and the risk signals

Onboarding Guide's owner, Tom Dean, has left and his account is still enabled; you have that from your
inventory. This checks whether the registry knows it.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Read the **Agents without owners** tile, then select it and check whether Onboarding Guide is listed.
2. Read the **Agents at risk** tile.
3. Select **Onboarding Guide** in the list and open **Data & tools**. Its send-email tool (Office 365
   Outlook) is listed.
4. Record the result of each check as what the registry does or doesn't detect.

</details>

Without the tenant: record the tiles as unknown, and Onboarding Guide's Outlook connection from
`connections-export.csv`.

<details markdown="block">
<summary>Reveal what the checks show</summary>

**Agents without owners** reads 0 and Onboarding Guide isn't listed; **Agents at risk** reads "—" (no
signals). The registry counts an agent as ownerless only when its owner's account has been *deleted*; an
owner who has left but whose account still exists doesn't count. Record both as gaps: the orphan has a
live mail-send tool, and nothing in the registry flags it.

</details>

### 03: Check for the drift

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Record that Claims Copilot, a production-use agent in `Claims-Test`, isn't in the registry at all
   (Key Task 01), so the registry can't flag its drift from test to production.

</details>

### 04: Write the ownership policy

Detection only helps if each finding has an owner rule and an action behind it. Write both.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Write the owner rule in one sentence: who must own a production agent, and what happens when that
   owner leaves.
2. For Onboarding Guide and for Claims Copilot, write one action from: assign a new owner, **Block** the
   agent, or **Delete** it, and why.

</details>

<details markdown="block">
<summary>Reveal the suggested policy</summary>

- **Owner rule:** every agent in use has a present, accountable human owner; when the owner leaves, the
  agent is reassigned or blocked within a set time, and the owner's connections are reviewed.
- **Onboarding Guide:** **Block** now, then assign a new owner or delete it. Blocking stops it at once
  and can be undone; deleting can't.
- **Claims Copilot:** assign an accountable owner and move it to `Halcourt-Prod` through the release
  process, or block it. It has to be found by hand first: the registry doesn't list it.

</details>

### 05: Block Onboarding Guide and retest Scenario F

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

Your facilitator, with AI Administrator activated:

1. Opens the Microsoft 365 admin center → **Agents** → **All agents** → **Registry**, searches for the
   estate id and selects **Onboarding Guide**.
2. Selects **Block** and confirms.
3. After the retests, selects Onboarding Guide again → **Unblock** (confirm in your tenant) and confirms.

Block is the action demonstrated because it can be undone. **Delete** can't, and removing the orphaned
Outlook connection means deleting it. For a lab account **Block** and **Assign new owner** are greyed out.

Then you:

1. Search the registry for Onboarding Guide and read its **Status**. Onboarding Guide has no Teams link,
   so the status is the retest: a blocked agent can't run, so it can't send mail.
2. Record what the block leaves behind: the agent, its Entra identity and its Outlook connection still
   exist.

</details>

Without the tenant: reason about what blocking does to Onboarding Guide's mail-send path, and what it
leaves in place, from its rows in `agents-export.csv` and `connections-export.csv`.

{: .note }
> Be honest about which did the work: the registry's detection, or the action someone took.

### 06: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In your [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), fill
   the **Agent 365** column's **F** cell.
2. Copy a **Retest log** block below the matrix: Before, After, Verdict, and Remaining risk. Say whether
   the orphan was stopped or only listed, and that the registry listed neither the orphan as ownerless nor
   Claims Copilot at all.
3. In the **Agent 365** column's **B**, **C**, **D** and **E** cells, note inventory value only: the
   registry exposes, it doesn't remediate, and it doesn't list the agents those scenarios use.

</details>

{: .important }
> **Solves versus exposes.** Inventory and orphan detection are close to a real fix for lifecycle failures
> if, and only if, detection is wired to an action: block the agent, reassign the owner, remove the
> connection. A dashboard that lists an orphan has *exposed* the problem, which is valuable and still not
> the same as *closing* it. Record which one you actually achieved.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Agent 365 × F:** suggested **DENTS IT**. The registry didn't flag the orphan and doesn't list Claims
  Copilot; the block stopped Onboarding Guide because a person acted on what you found. It becomes
  **CLOSES IT** only if detection is wired to an action you can show took effect.
- **Other scenarios:** inventory value at most: the registry missed most of the estate, including every
  agent in `Halcourt-Prod` and `Claims-Test`.
- **The registry's blind spots:** an owner who has left isn't ownerless while the account exists, and
  agents outside the default environment aren't listed.

</details>

## Summary

Governance is the control meant to find lifecycle failures. Here the registry listed two of the estate's
agents, flagged no orphan and no risk, and couldn't see Claims Copilot at all; the block on Onboarding
Guide worked because someone acted on your inventory. An inventory entry is exposure, and closing needs an
action. Record the verdict and remaining risk in the matrix.
