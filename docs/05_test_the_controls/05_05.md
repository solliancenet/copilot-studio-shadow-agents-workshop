# Task 05-05 — Agent 365 governance

## Introduction

Governance tooling — **Agent 365** together with the **CoE Starter Kit** — is where you get an inventory
of every agent and its identity, ownership records, orphaned-resource detection, and lifecycle policy. It
is the control most likely to *find* the estate's lifecycle failures for you. The discipline this task
teaches is the difference between a control that **solves** a problem and one that merely **exposes** it:
an inventory that lists an orphaned agent has done something valuable, but the agent is still orphaned until
someone acts.

## Description

You will use governance tooling to surface the lifecycle failures, then retest **Scenario F** (lifecycle —
the orphaned Onboarding Guide whose owner's account is disabled, and the Claims Copilot that drifted from
test to production). You configure ownership and orphan-detection policy, then decide, for each finding,
whether governance **closed** it (the connection is actually disabled, the owner actually reassigned) or
only **exposed** it (it now appears in a report, and remediation is still a separate action). Because
Agent 365's exact 2026 admin surfaces are still moving, you will flag what you could and could not confirm.

## Success Criteria

- [ ] You produced (or specified) an inventory that lists every agent, its owner, its environment, and its
  connections — including the orphaned and drifted agents.
- [ ] You configured an ownership policy and orphaned-resource detection, and identified the remediation
  action each finding needs.
- [ ] You re-ran Scenario F and observed whether the orphan's live mail-send connection was actually
  stopped or merely reported.
- [ ] You recorded a **CLOSES IT / DENTS IT / MISSES IT** verdict for Agent 365 governance against F (and
  noted its inventory value for the other scenarios) in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), with a
  remaining-risk note.
- [ ] You flagged which 2026 Agent 365 capabilities you verified in-tenant versus assumed.

## Key Tasks

### 01: Inventory, detect orphans, and set ownership policy

Governance earns its keep by making the invisible visible. Start by generating the inventory that Module 2
had you build by hand.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. First discover which **Agent 365** views exist in this tenant, and pull the agent list from them with
   whatever owner, environment, published-state, and connection fields they expose — the exact fields are
   one of the 2026 details to verify in-tenant. Where a view or field is missing, fall back to the **CoE
   Starter Kit** inventory or your CSVs.
2. Turn on **orphaned-resource detection** / ownership reporting. The target findings are the ones
   matching owners across your CSVs reveals: an agent whose owner's account is disabled, and connections
   whose owner has left.
3. Offline, run that detection yourself: look up each owner UPN in `agents-export.csv` in
   `users-export.csv`. `Onboarding Guide` is owned by `tom.dean@halcourtmutual.onmicrosoft.com`, whose
   `account_enabled` is `FALSE` — an orphan. Do the same for `connections-export.csv`:
   `O365-Outlook-Onboarding` is still owned by the disabled Tom Dean, and it can **send mail**. Also flag
   `Claims Copilot` in `Claims-Test` as a test-environment agent that is a production-use candidate.
4. Define an **ownership policy**: every production agent must have a present, accountable human owner; a
   disabled owner triggers reassignment or decommission. Decide the remediation for each finding — reassign,
   disable the connection, or retire the agent.

</details>

### 02: Re-run Scenario F, then record the verdict

The retest hinges on one distinction: did the governance action actually change the estate, or just
describe it?

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Re-open [Task 04-06 — Lifecycle]({% link docs/04_break_the_agents/04_06.md %}). Before remediation,
   confirm the orphaned Onboarding Guide is still published and its Outlook connection can still send mail.
2. Apply the remediation your policy dictates — reassign the owner, and disable or remove the orphaned
   connections. Now retest: can the agent still send mail as the departed owner's connection? The verdict
   depends on whether governance **detection alone** changed this, or whether it took a **separate
   remediation action** you performed. Be honest about which did the work.

   Remediation needs rights in the agent's environment, not just a tenant admin role: give yourself System
   Administrator in that environment (PPAC → the environment → **Settings → Users + permissions →
   Users**). If you retire the agent, check whether retiring it also removed its Entra identity.
3. For the Claims Copilot half, note that inventory surfaces the test-to-production drift, but the *fix*
   (a scoped role, a gated promotion) lived in Tasks 05-02 and 05-03. Governance's contribution here is
   making the drift visible and assignable, not repairing it.
4. Consider the other scenarios briefly: check whether Agent 365 shows the HTTP/MCP integrations and
   secret exposure (E), the shared-connection and service-account use (C/D), and the over-broad grounding
   (B). Where it does, ask whether it **remediates** or only **reveals** — that distinction is your
   remaining-risk note.
5. Record a verdict for **Agent 365 × F**, with a remaining-risk note that states plainly whether the
   orphan is gone or merely listed.

</details>

{: .important }
> **Solves versus exposes.** Inventory and orphan-detection are close to a real fix for lifecycle failures —
> if, and only if, detection is wired to an action: disable the connection, reassign the owner, retire the
> agent. On its own, a governance dashboard that lists the orphaned Onboarding Guide has *exposed* the
> problem, which is genuinely valuable and still not the same as *closing* it. Record which one you actually
> achieved.

{: .note }
> **2026 product detail — verify in the tenant.** Agent 365's exact admin views, the fields it exposes for
> agent and workload identities, and how far its automated orphan-detection and lifecycle policy reach are
> evolving through 2026. Confirm the specific capabilities in your delivery tenant and annotate your verdict
> with what you verified rather than assumed. Where the tenant lacks a capability, the CoE Starter Kit
> inventory is the fallback that still lets you complete this task.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Agent 365 × F:** suggested **DENTS IT** when governance only lists the orphan and the drifted agent —
  that is exposure. It becomes **CLOSES IT** only if detection is wired to an action you can show took
  effect: the Outlook connection disabled, the owner reassigned, or the agent retired (and its Entra
  identity checked).
- **Other scenarios:** whatever Agent 365 shows for B, C/D and E is inventory value — it reveals, it does
  not remediate.

</details>

## Summary

Governance is the control that finds lifecycle failures — the orphaned agent, the drifted test bot, the
ghost connection. Retesting Scenario F forces the distinction that matters: an inventory entry is exposure,
and closing requires an action. Flag the 2026 capabilities that still need in-tenant confirmation, and
record the verdict and remaining risk in the matrix.
