# Task 05-05 — Agent 365 governance

## Introduction

Governance tooling — **Agent 365** — is where you get an inventory of every agent and its identity,
ownership records, orphaned-resource detection, and lifecycle policy. It is the control most likely to *find*
the estate's lifecycle failures for you. The discipline this task teaches is the difference between a control
that **solves** a problem and one that merely **exposes** it: an inventory that lists an orphaned agent has
done something valuable, but the agent is still orphaned until someone acts.

## Description

You will use governance tooling to surface the lifecycle failures, then retest **Scenario F** (lifecycle —
the orphaned Onboarding Guide whose owner's account is disabled, and the Claims Copilot that drifted from
test to production). You configure ownership and orphan-detection policy, then decide, for each finding,
whether governance **closed** it (the connection is actually disabled, the owner actually reassigned) or
only **exposed** it (it now appears in a report, and remediation is still a separate action).

## Success Criteria

- [ ] You produced (or specified) an inventory that lists every agent, its owner, its environment, and its
  connections — including the orphaned and drifted agents.
- [ ] You defined an ownership policy and orphaned-resource detection, and identified the remediation
  action each finding needs.
- [ ] You re-ran Scenario F and observed whether the orphan's live mail-send connection was actually
  stopped or merely reported.
- [ ] You recorded a **CLOSES IT / DENTS IT / MISSES IT** verdict for Agent 365 governance against F (and
  noted its inventory value for the other scenarios) in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), with a
  remaining-risk note.
- [ ] You compared what the registry flagged with what your CSVs show, and named what it missed.

## Key Tasks

### 01: Open the Agent 365 registry

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the Microsoft 365 admin center, select **Agents** → **All agents** → **Registry**.
2. Read the summary tiles:
   a. **Total agents**;
   b. **Agents without owners**;
   c. **Unmanaged agents**.
3. Filter **Platform** to Copilot Studio and find the estate's agents. Note any agent listed twice under
   different **Publisher type**s.
4. Select **Export** to save the filtered list as a CSV; keep it for the next key tasks.

</details>

### 02: Look for the orphan

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Select the **Agents without owners** tile.
2. Check whether Onboarding Guide is listed.
3. Look up Tom Dean's account status in the Microsoft Entra admin center (**Entra ID** → **Users**).

</details>

{: .note }
> The registry counts an agent as ownerless only when its owner's account has been *deleted*. A disabled
> owner doesn't count — if Onboarding Guide isn't listed, you have found a gap in the tool, not a clean agent.

### 03: Check the risk signals

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Select the **Agents at risk** tile.
2. For each estate agent with a count in the **Risks** column, open **Risk details** and note:
   a. the severity of each signal;
   b. which platform raised it (Purview, Entra, Defender).

</details>

### 04: Look for the drift

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In your exported list, read each estate agent's **Platform**, **Owner** and **Last modified**.
2. In the Power Platform admin center, find which environment each lives in.
3. Note test-environment agents that are production-use candidates (Claims Copilot in `Claims-Test`).

</details>

### 05: Define the ownership policy

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Define an **ownership policy**: every production agent must have a present, accountable human owner; a
   disabled owner triggers reassignment or decommission.
2. For each finding, choose one action: assign an owner, **Block** the agent, or **Delete** it.

</details>

> Do Key Task 06 if you can reach the tenant, or Key Task 07 if you can't. Both lead to Key Task 08.
{: .note }

### 06: Watch the remediation, then retest Scenario F (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Your facilitator **Blocks** Onboarding Guide in the Microsoft 365 admin center registry, and unblocks it
   after the retests. Block is the one action that can be undone cleanly, so it is the one demonstrated.
   The others are described, not performed: **Delete** can't be reversed, and removing the orphaned
   Outlook connection in the Power Platform admin center means deleting it, which can only be undone by
   recreating it and signing in again as its owner.
2. Re-open [Task 04-06 — Lifecycle]({% link docs/04_break_the_agents/04_06.md %}) and retest: can
   Onboarding Guide still send mail?
3. Note what the block leaves behind: the blocked agent, its Entra identity and its connections still
   exist; a deleted agent may leave its identity behind too.

</details>

{: .note }
> Be honest about which did the work: the registry's detection, or the action you took.

### 07: Reason about Scenario F (offline route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In `users-export.csv`, find agent owners whose `account_enabled` is `FALSE`.
2. In `connections-export.csv`, find connections those owners still own, and which agent uses each.
3. Note test-environment agents that are production-use candidates.
4. Record a reasoned conclusion: what would the registry flag, and what would it miss?

</details>

### 08: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Record **Agent 365 × F** with a remaining-risk note that says whether the orphan is gone or merely
   listed — and whether the registry listed it at all.
2. For B, C/D and E, note what the **Risks** column showed: exposure, not remediation.

</details>

{: .important }
> **Solves versus exposes.** Inventory and orphan-detection are close to a real fix for lifecycle failures —
> if, and only if, detection is wired to an action: disable the connection, reassign the owner, retire the
> agent. On its own, a governance dashboard that lists the orphaned Onboarding Guide has *exposed* the
> problem, which is genuinely valuable and still not the same as *closing* it. Record which one you actually
> achieved.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Agent 365 × F:** suggested **DENTS IT** when governance only lists the orphan and the drifted agent —
  that is exposure. It becomes **CLOSES IT** only if detection is wired to an action you can show took
  effect: the Outlook connection disabled, the owner reassigned, or the agent retired (and its Entra
  identity checked).
- **Other scenarios:** whatever Agent 365 shows for B, C/D and E is inventory value — it reveals, it does
  not remediate.
- **The registry's blind spot:** a disabled owner isn't ownerless to the registry — Onboarding Guide only
  shows up if Tom Dean's account is deleted, so detection alone may miss the estate's orphan.

</details>

## Summary

Governance is the control that finds lifecycle failures — the orphaned agent, the drifted test bot, the
ghost connection. Retesting Scenario F forces the distinction that matters: an inventory entry is exposure,
and closing requires an action. Record the verdict and remaining risk in the matrix.
