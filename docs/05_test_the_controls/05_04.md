# Task 05-04 — Conditional Access

## Introduction

Conditional Access (CA) is an **authentication-time** control. It decides whether a principal can get a
token — under what conditions (MFA, compliant device, trusted location, sign-in risk) — and it can block
legacy authentication outright. That makes it excellent at the front door and, by design, blind to
everything that happens *after* a principal is already authenticated. Most of the Module 4 failures are
post-authentication authorization problems, so this task is largely about learning which failures CA can
touch and, more usefully, which it structurally cannot.

## Description

You will inventory the estate's CA posture (`CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth` exist; there
is **no** policy targeting workload or agent identities), then explore **Conditional Access for workload
identities** as a way to constrain the auto-created agent identities. Then you retest **Scenario D**
(confused deputy) and **Scenario E** (the HTTP / MCP boundary) and record where CA lands — including the
hard case where the target API trusts a static key rather than an Entra token, so CA has nothing to gate.

## Success Criteria

- [ ] You can list the estate's existing CA policies and confirm none targets a workload/agent identity.
- [ ] You evaluated (or configured, if the tenant supports it) a Conditional Access for workload identities
  policy scoped to the agent identities.
- [ ] You re-ran Scenario D and Scenario E and observed whether CA changed the outcome.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for CA against D and E in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.
- [ ] You can state the CA boundary in one sentence: authentication, not authorization.

## Key Tasks

### 01: Inventory CA and target the workload identities

CA cannot protect an identity it does not target. The estate's agent identities are targeted by nothing.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In **Microsoft Entra → Protection → Conditional Access**, list the policies. Confirm
   `CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth` exist and that both target **human** principals.
   Confirm no policy is scoped to a service principal or agent identity. You may also see
   Microsoft-managed policies — Microsoft can add them once security defaults are off. They are not part of
   the estate's baseline.
2. In the **Microsoft Entra admin center**, open **Entra ID → Agents → Agent identities** and note the
   auto-created agent identities. Each is named after its agent, as
   `<agent name> (Microsoft Copilot Studio)`. Expect more of them than there are agents: identically named
   identities from any other estate in the tenant, plus identities left behind by agents that were
   deleted. Offline, they are the rows of your `agent-identities-export.csv`, each with an `app_id` (the
   filled-in pack labels them `cs-agent-*`). These are the workload identities a Conditional Access for
   workload identities policy could target. This capability applies to service principals, not to the
   classic user-based policies already in place.
3. Create (or, if the tenant/licensing does not support it, specify precisely) a Conditional Access for
   workload identities policy scoped to those agent identities — for example, blocking sign-ins from
   outside expected locations or on elevated sign-in risk. Conditional Access is tenant-wide, and the lab
   tenant's baseline is shared by every estate built there: check with the facilitator before you create a
   policy, and otherwise specify it.
4. Write down the critical dependency before you test: a CA policy on a workload identity only bites when
   the resource **trusts Entra tokens**. If the resource authenticates the caller some other way — a static
   API key, a shared bearer token — then Entra never issues a gated token for that call, and CA has nothing
   to act on.

</details>

### 02: Re-run Scenario D and Scenario E, then record the verdict

Two retests that should teach the authentication/authorization split cleanly.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario D.** Re-open [Task 04-04 — Identity / confused deputy]({% link docs/04_break_the_agents/04_04.md %}).
   Run the low-privilege-user path against Claims Copilot again. Jordan Blake is a fully authenticated,
   compliant employee — MFA satisfied, legacy auth irrelevant. Observe whether any CA condition changes the
   fact that, once authenticated, the agent reads and writes claims **as `svc-claims`**. The escalation
   happens after every authentication check has already passed.
2. **Scenario E.** Re-open [Task 04-05 — HTTP / MCP / tool boundary]({% link docs/04_break_the_agents/04_05.md %}).
   The Policy Lookup Bot's HTTP action authenticates to the Policy API with a **static API key in the
   action config**, and the Underwriting MCP uses a **static bearer token**. Both are wired inside the
   agents' topics: in **Copilot Studio**, open each agent's **Topics** page to see how the HTTP request
   node and the MCP call authenticate (the **Tools** page doesn't show them). Offline, the filled-in
   `connections-export.csv` lists both, `HTTP-PolicyAPI` and `MCP-Underwriting`, with their `auth_type`.
   Ask: is there any Entra token in that call for CA to gate? Then consider the narrow case — if the
   integration were re-built to use per-user Entra auth, a CA for workload identities policy *could*
   constrain where the agent identity's token is usable. That "only if" is the whole verdict.
3. **Offline path.** Join `agent-identities-export.csv` (the workload identities CA could target) with
   `connections-export.csv` (the auth types). Every connection whose auth is `API key in action config`,
   `Static bearer token`, or `Service account` is a call CA cannot see. Reason the verdicts from that join
   alone.
4. Record verdicts for **Conditional Access × D** and **× E**, each with remaining risk. For E, your
   remaining-risk note should name the static-credential dependency explicitly.

</details>

{: .note }
> **2026 product detail — verify in the tenant.** Whether Conditional Access for workload identities
> applies to Copilot Studio's auto-created agent identities, and exactly which conditions are enforceable
> on them, is an evolving 2026 capability. Treat the workload-identity policy behavior as something to
> confirm in your delivery tenant rather than assume; note what you actually observed next to your verdict.

{: .important }
> **The boundary to name.** CA governs *whether and under what conditions a principal authenticates*. Every
> Module 4 failure that is really about *what an already-authenticated principal is allowed to do* — the
> confused deputy, the over-broad Dataverse read, the unvalidated input to an HTTP action — sits on the far
> side of that line. And CA cannot gate a call that never asks Entra for a token in the first place.

## Summary

Conditional Access is a front-door control in a module full of after-you-are-inside problems. Scoping it to
the agent identities is worth doing, and against a properly Entra-authenticated integration it can constrain
where an agent's token is used. But retesting Scenarios D and E shows its limits sharply: the confused
deputy escalates only after authentication succeeds, and the estate's HTTP and MCP integrations authenticate
with static secrets CA never sees. You recorded verdicts that separate authentication from authorization —
the distinction this task exists to teach.
