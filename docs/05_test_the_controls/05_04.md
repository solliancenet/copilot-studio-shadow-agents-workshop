# Task 05-04 — Conditional Access

## Introduction

Conditional Access (CA) is an **authentication-time** control. It decides whether a principal can get a
token — under what conditions (MFA, compliant device, trusted location, sign-in risk) — and it can block
legacy authentication outright. That makes it excellent at the front door and, by design, blind to
everything that happens *after* a principal is already authenticated. Most of the Exercise 04 failures are
post-authentication authorization problems, so this task is largely about learning which failures CA can
touch and, more usefully, which it structurally cannot.

## Description

You will inventory the estate's Conditional Access policies read-only, then write down — on paper — a
**Conditional Access for agents** policy for the agent identities from your inventory. Then you reason
through **Scenario D** (confused deputy) and **Scenario E** (the HTTP / MCP boundary) and record where CA
lands — including the hard case where the target API trusts a static key rather than an Entra token, so CA
has nothing to gate.

## Success Criteria

- [ ] You can list the estate's existing CA policies and confirm none targets an agent identity.
- [ ] You wrote a Conditional Access for agents policy as four parts — who, target resources, condition,
  grant — and you know why the estate's two existing policies don't cover agents.
- [ ] You reasoned whether Conditional Access could change Scenarios D and E, and labelled both verdicts reasoned.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for CA against D and E in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.
- [ ] You can state the CA boundary in one sentence: authentication, not authorization.

## Key Tasks

### 01: Inventory Conditional Access

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Microsoft Entra admin center**, open **Entra ID** → **Conditional Access** → **Policies**. Your
   account has read-only access: you can open policies, but **New policy** is greyed out.
2. List the policies and their state. For each, open it and check:
   a. which users or groups it targets;
   b. whether it is scoped to any service principal or agent identity.
3. Note how many Microsoft-managed policies there are. Microsoft can add them once security defaults are
   off; they aren't part of the estate's baseline.

If you're working offline, the estate's baseline is two user-targeted policies, both On:
`CA-Block-Legacy-Auth` and `CA-Require-MFA-Admins`.

</details>

### 02: Write a Conditional Access policy for agents

This is a paper exercise. You can't create policies, and Conditional Access is tenant-wide: one wrong
policy in the lab tenant locks out every account in every estate. You'll write the policy down and label
your verdicts reasoned.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. To see where each part of a policy lives, open an existing one read-only: **Conditional Access** →
   **Policies** → select a policy. The editor's left column has:
   a. **Assignments** → the who-picker, probably labelled **Users, agents (Preview) or workload
      identities**, with a **What does this policy apply to?** drop-down offering **Users and groups**,
      **Agents** and **Workload identities** (confirm the exact labels in your tenant);
   b. **Target resources**;
   c. **Conditions**;
   d. **Access controls** → **Grant**.
2. Write a policy for the estate's agent identities as four parts:
   a. **Who** — the agent identities in your inventory (`agent-identities-export.csv`);
   b. **Target resources**;
   c. **Condition**;
   d. **Grant**.
3. Note why the two existing policies don't already cover these identities.

</details>

<details markdown="block">
<summary>Reveal the suggested policy</summary>

- **Who:** **Agents** — the estate's agent identities.
- **Target resources:** all resources, or the ones the agents call, such as Dataverse.
- **Condition:** agent risk **High**.
- **Grant:** **Block access**.

Why the existing policies don't carry over: agents never use legacy password protocols — they get modern
Entra tokens — so blocking legacy authentication has nothing to block. And an agent can't do MFA, so
requiring it either blocks the agent outright or gets skipped.

This policy still does nothing for D or E. `svc-claims` and the static keys aren't the agent identity.

</details>

{: .note }
> **What Conditional Access for agents covers in Copilot Studio.**
> - Any policy only bites when the resource **trusts Entra tokens**. A static API key or shared bearer token
>   never asks Entra for a token, so Conditional Access has nothing to act on.
> - Conditional Access on the Agent ID's connector scopes is evaluated at runtime only when the agent runs
>   in **Microsoft Teams**. Other channels use the existing connector authentication flow.
> - Custom connectors, MCP servers and REST API tools add no API permissions to the Agent ID.
> - An agent acting on behalf of the signed-in user is governed by user policies, not agent-identity ones.
> - An agent created before May 2026 may still use a legacy app registration (tagged
>   `AgentCreatedBy:CopilotStudio` under **Entra ID → App registrations**). Agent-identity targeting
>   doesn't cover it.

### 03: Reason through Scenarios D and E

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **D:** You sign in as yourself and pass every check; the split between your authority and `svc-claims`'s
   happens after that. Does any Conditional Access policy — on you, on the agent identity, or on
   `svc-claims` as an Entra user — stop the agent reading as `svc-claims`?
2. **E:** You found in Task 04-05 that Policy Lookup Bot sends a static API key and Underwriting Assistant a
   static bearer token. Is there an Entra token in either call for Conditional Access to gate?

</details>

{: .note }
> For D, keep three cases apart: (a) the agent policy you wrote in Key Task 02;
> (b) user-targeted CA on `svc-claims` as an Entra user — its sign-in and token refresh can be governed;
> (c) static API keys and bearer tokens, which never involve Entra CA for the downstream call. Which of these
> touches the point where the requester's authority and the acting credential's authority split?

{: .note }
> For E, if the integration were rebuilt on Entra auth, Conditional Access *could* constrain where the token
> is usable — a user policy for on-behalf-of calls, an agent-identity policy for autonomous ones. Note that
> "only if".

### 04: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In your [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), fill
   the **Conditional Access** column's **D** and **E** cells.
2. For each, copy a **Retest log** block below the matrix: Before, After, Verdict, and Remaining risk — the
   thing still true with the policy in place.
3. For E, name the static-credential dependency explicitly in your remaining-risk note.

</details>

{: .important }
> **The boundary to name.** CA governs *whether and under what conditions a principal authenticates*. Every
> Exercise 04 failure that is really about *what an already-authenticated principal is allowed to do* — the
> confused deputy, the over-broad Dataverse read, the unvalidated input to an HTTP action — sits on the far
> side of that line. And CA cannot gate a call that never asks Entra for a token in the first place.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Conditional Access × D:** suggested **MISSES IT**. The requester authenticates legitimately; the split
  between their authority and `svc-claims`'s happens after every authentication check has passed.
  User-targeted CA on `svc-claims` can govern its sign-in and token refresh, but not what it reads for
  whoever asks. A policy on the agent identity doesn't reach it either: the Dataverse call's token subject
  is `svc-claims`, not the Agent ID.
- **Conditional Access × E:** suggested **MISSES IT** as built. The HTTP action and the MCP tool carry a
  static API key and a static bearer token, so there is no Entra token to gate, and these tools add no
  permissions to the Agent ID. Only if the integration were rebuilt on Entra auth could CA constrain where
  a token is usable — that "only if" belongs in your remaining-risk note.

</details>

## Summary

Conditional Access is a front-door control in an exercise full of after-you-are-inside problems. Writing a
policy for the agent identities is worth doing, and against a properly Entra-authenticated integration it
can constrain where a token is used. Reasoning through Scenarios D and E shows where that front door sits
relative to the confused deputy and the static-secret integrations. Record the verdict and remaining risk in the matrix.
