# Task 05-04 — Conditional Access

## Introduction

Conditional Access (CA) is an **authentication-time** control. It decides whether a principal can get a
token — under what conditions (MFA, compliant device, trusted location, sign-in risk) — and it can block
legacy authentication outright. That makes it excellent at the front door and, by design, blind to
everything that happens *after* a principal is already authenticated. Most of the Exercise 04 failures are
post-authentication authorization problems, so this task is largely about learning which failures CA can
touch and, more usefully, which it structurally cannot.

## Description

You will inventory the estate's CA posture (`CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth` exist; there
is **no** policy targeting workload or agent identities), then explore **Conditional Access for workload
identities** as a way to constrain the auto-created agent identities. Then you retest **Scenario D**
(confused deputy) and **Scenario E** (the HTTP / MCP boundary) and record where CA lands — including the
hard case where the target API trusts a static key rather than an Entra token, so CA has nothing to gate.

## Success Criteria

- [ ] You can list the estate's existing CA policies and confirm none targets a workload/agent identity.
- [ ] You evaluated (or configured, if the tenant supports it) a Conditional Access for workload identities
  policy scoped to the agent identities.
- [ ] You re-ran Scenario D and Scenario E and observed whether CA changed the outcome.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for CA against D and E in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.
- [ ] You can state the CA boundary in one sentence: authentication, not authorization.

## Key Tasks

### 01: Inventory Conditional Access

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In **Microsoft Entra → Protection → Conditional Access**, list the policies.
2. Check that `CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth`:
   a. exist;
   b. target only **human** principals;
   c. aren't scoped to any service principal or agent identity.
3. Note any Microsoft-managed policies — Microsoft can add them once security defaults are off; they aren't
   part of the estate's baseline.

Without the tenant: the estate's baseline is the two policies above, both user-targeted.

</details>

### 02: Find the agent identities

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Microsoft Entra admin center**, open **Entra ID → Agents → Agent identities**.
2. Note each agent's identity, named `<agent name> (Microsoft Copilot Studio)`.
3. Note any identity with no matching agent in your inventory, and any identically named identities from
   other estates in the tenant.

Without the tenant: the rows of your `agent-identities-export.csv` (the filled-in pack labels them
`cs-agent-*`).

</details>

### 03: Specify a Conditional Access policy for workload identities

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Create a Conditional Access for workload identities policy scoped to those agent identities — for
   example, blocking sign-ins from outside expected locations or on elevated sign-in risk.
2. Conditional Access is tenant-wide and the lab tenant's baseline is shared by every estate: check with the
   facilitator first; otherwise, or if the tenant/licensing doesn't support it, write the policy down
   instead.

</details>

{: .note }
> This capability applies to service principals, not to the classic user-based policies. A CA policy on a
> workload identity only bites when the resource **trusts Entra tokens**. If the resource authenticates the
> caller some other way — a static API key, a shared bearer token — Entra never issues a gated token for
> that call, and CA has nothing to act on.

> For each scenario below, do the tenant key task if you can reach the tenant, or the offline key task if
> you can't. Both lead to Key Task 08.
{: .note }

### 04: Retest Scenario D (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Re-open [Task 04-04 — Identity / confused deputy]({% link docs/04_break_the_agents/04_04.md %}).
2. Run the low-privilege path against the published Claims Copilot with your own lab account.
3. Observe whether any CA condition changes what the agent reads and writes as `svc-claims` once you're
   authenticated.

</details>

{: .note }
> Keep three cases apart: (a) CA for workload identities on the agent's Entra Agent ID; (b) user-targeted
> CA on `svc-claims` as an Entra user — its sign-in and token refresh can be governed; (c) static API keys
> and bearer tokens, which never involve Entra CA for the downstream call. Which of these touches the point
> where the requester's authority and the acting credential's authority split?

### 05: Reason about Scenario D (offline route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In `connections-export.csv`, find the identity whose credential `DV-Claims-Shared` carries
   (`svc-claims`).
2. Note that `svc-claims` is an Entra user: user-targeted CA can govern its sign-in and token refresh,
   though not what it is authorized to read.
3. Record a reasoned conclusion.

</details>

### 06: Retest Scenario E (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Re-open [Task 04-05 — HTTP / MCP / tool boundary]({% link docs/04_break_the_agents/04_05.md %}).
2. In **Copilot Studio**, open each agent's **Topics** page and see how the HTTP request node and the MCP
   call authenticate (the **Tools** page doesn't show them).
3. Ask: is there any Entra token in that call for CA to gate?

</details>

{: .note }
> If the integration were rebuilt on per-user Entra auth, a CA for workload identities policy *could*
> constrain where the token is usable. Note that "only if".

### 07: Reason about Scenario E (offline route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In `connections-export.csv`, find `HTTP-PolicyAPI` and `MCP-Underwriting` and their `auth_type`.
2. Note that a call whose auth is `API key in action config` or `Static bearer token` is a call Entra CA
   never sees.
3. Record a reasoned conclusion.

</details>

### 08: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Record verdicts for **Conditional Access × D** and **× E**, each with remaining risk.
2. For E, name the static-credential dependency explicitly in your remaining-risk note.

</details>

{: .note }
> **2026 product detail — verify in the tenant.** Microsoft documents that Conditional Access on an agent's
> Entra Agent ID is enforced at runtime only when the agent runs in **Microsoft Teams**; other channels use
> the existing connector authentication flow. Custom connectors, MCP servers and REST API tools add no API
> permissions to the Agent ID. Which conditions are enforceable, and how your tenant's licensing affects
> them, is still something to confirm in your delivery tenant rather than assume; note what you actually
> observed next to your verdict. Conditional Access for agents also needs a Microsoft Agent 365 license (or
> Microsoft 365 E7).

{: .important }
> **The boundary to name.** CA governs *whether and under what conditions a principal authenticates*. Every
> Exercise 04 failure that is really about *what an already-authenticated principal is allowed to do* — the
> confused deputy, the over-broad Dataverse read, the unvalidated input to an HTTP action — sits on the far
> side of that line. And CA cannot gate a call that never asks Entra for a token in the first place.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Conditional Access × D:** suggested **MISSES IT**. The requester authenticates legitimately; the split
  between their authority and `svc-claims`'s happens after every authentication check has passed.
  User-targeted CA on `svc-claims` can govern its sign-in and token refresh, but not what it reads for
  whoever asks.
- **Conditional Access × E:** suggested **MISSES IT** as built. The HTTP action and MCP call carry a static
  API key and a static bearer token, so there is no Entra token to gate, and these tools add no
  permissions to the Agent ID. Only if the integration were rebuilt on Entra auth could CA constrain where
  a token is usable — that "only if" belongs in your remaining-risk note.

</details>

## Summary

Conditional Access is a front-door control in an exercise full of after-you-are-inside problems. Scoping it to
the agent identities is worth doing, and against a properly Entra-authenticated integration it can constrain
where a token is used. Retesting Scenarios D and E shows where that front door sits relative to the
confused deputy and the static-secret integrations. Record the verdict and remaining risk in the matrix.
