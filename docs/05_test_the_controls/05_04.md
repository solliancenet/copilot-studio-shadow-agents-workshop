# Task 05-04 — Conditional Access

## Introduction

Conditional Access (CA) is an **authentication-time** control. It decides whether a principal can get a
token — under what conditions (MFA, compliant device, trusted location, sign-in risk) — and it can block
legacy authentication outright. That makes it excellent at the front door and, by design, blind to
everything that happens *after* a principal is already authenticated. Most of the Exercise 04 failures are
post-authentication authorization problems, so this task is largely about learning which failures CA can
touch and, more usefully, which it structurally cannot.

## Description

You will inventory the estate's CA posture (`CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth` exist; there
is **no** policy targeting workload or agent identities), then specify a **Conditional Access for agents**
policy that targets the auto-created agent identities. Then you retest **Scenario D**
(confused deputy) and **Scenario E** (the HTTP / MCP boundary) and record where CA lands — including the
hard case where the target API trusts a static key rather than an Entra token, so CA has nothing to gate.

## Success Criteria

- [ ] You can list the estate's existing CA policies and confirm none targets an agent identity.
- [ ] You specified a Conditional Access for agents policy that
  targets the agent identities, and you know which access pattern it covers.
- [ ] You re-ran Scenario D and Scenario E and observed whether CA changed the outcome.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for CA against D and E in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.
- [ ] You can state the CA boundary in one sentence: authentication, not authorization.

## Key Tasks

### 01: Inventory Conditional Access

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In **Microsoft Entra → Protection → Conditional Access**, list the policies.
2. Check that `CA-Require-MFA-Admins` and `CA-Block-Legacy-Auth`:
   a. exist;
   b. target only **human** principals;
   c. aren't scoped to any service principal or agent identity.
3. Note any Microsoft-managed policies — Microsoft can add them once security defaults are off; they aren't
   part of the estate's baseline.

Without the tenant: the estate's baseline is the two policies above, both user-targeted.

</details>

### 02: Find the agent identities

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Microsoft Entra admin center**, open **Entra ID → Agents → Agent identities**.
2. Note each agent's identity, named `<agent name> (Microsoft Copilot Studio)`.
3. Note any identity with no matching agent in your inventory, and any identically named identities from
   other estates in the tenant.
4. An agent created before May 2026 may not appear here. It may still use a legacy app registration, tagged
   `AgentCreatedBy:CopilotStudio`, under **Entra ID → App registrations**. Note any you find.

Without the tenant: the rows of your `agent-identities-export.csv` (the filled-in pack labels them
`cs-agent-*`).

</details>

### 03: Specify a Conditional Access policy for agents

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Specify a Conditional Access policy for the estate's agent identities:
   a. under **Assignments**, select **agent identities** (or their blueprint) — not workload identities;
   b. choose the agent identities from Key Task 02;
   c. pick a condition and grant control — for example, block when agent risk is elevated.
2. Write the policy down; don't create it. Conditional Access is tenant-wide, and one wrong policy in the lab
   tenant locks out every account in every estate, so this control is specified, not demonstrated. Label
   your verdicts reasoned.

</details>

{: .note }
> Conditional Access for agents targets agents by **access pattern**. An agent acting on behalf of a
> signed-in user is governed by user or group policies. An autonomous agent is governed by policies on its
> agent identity or blueprint. An agent-user account is governed by policies on that account. A policy on
> one token subject doesn't apply to another. And any policy only bites when the resource **trusts Entra
> tokens**: a static API key or shared bearer token never asks Entra for a token, so Conditional Access has
> nothing to act on.

> For each scenario below, do the tenant key task if you can reach the tenant, or the offline key task if
> you can't. Both lead to Key Task 08.
{: .note }

### 08: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Record verdicts for **Conditional Access × D** and **× E**, each with remaining risk.
2. For E, name the static-credential dependency explicitly in your remaining-risk note.

</details>

{: .note }
> **What Conditional Access for agents covers in Copilot Studio.**
> - Conditional Access on the Agent ID's connector scopes is evaluated at runtime only when the agent runs
>   in **Microsoft Teams**. Other channels use the existing connector authentication flow.
> - Custom connectors, MCP servers and REST API tools add no API permissions to the Agent ID.
> - An agent acting on behalf of the signed-in user is governed by user policies, not agent-identity ones.
> - API keys bypass Entra token issuance, so Conditional Access doesn't apply to them.
> - An agent created before May 2026 may still use a legacy app registration. Agent-identity targeting
>   doesn't cover it.
> - Licensing: Microsoft 365 E7, or Agent 365 plus Entra P1 or Microsoft 365 E3. Some targeting and
>   conditions are in preview; for agent identities the main condition is agent risk (preview).
>
> Note what you observed in the retest next to your verdict.

{: .important }
> **The boundary to name.** CA governs *whether and under what conditions a principal authenticates*. Every
> Exercise 04 failure that is really about *what an already-authenticated principal is allowed to do* — the
> confused deputy, the over-broad Dataverse read, the unvalidated input to an HTTP action — sits on the far
> side of that line. And CA cannot gate a call that never asks Entra for a token in the first place.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Conditional Access × D:** suggested **MISSES IT**. The requester authenticates legitimately; the split
  between their authority and `svc-claims`'s happens after every authentication check has passed.
  User-targeted CA on `svc-claims` can govern its sign-in and token refresh, but not what it reads for
  whoever asks. A policy on the agent identity doesn't reach it either: the Dataverse call's token subject
  is `svc-claims`, not the Agent ID.
- **Conditional Access × E:** suggested **MISSES IT** as built. The HTTP action and the MCP tool carry a
  static API key and a static bearer token, so there is no Entra token to gate, and these tools add no
  permissions to the Agent ID. Only if the integration were rebuilt on Entra auth could CA constrain where
  a token is usable — that "only if" belongs in your remaining-risk note.

</details>

## Summary

Conditional Access is a front-door control in an exercise full of after-you-are-inside problems. Scoping it to
the agent identities is worth doing, and against a properly Entra-authenticated integration it can constrain
where a token is used. Retesting Scenarios D and E shows where that front door sits relative to the
confused deputy and the static-secret integrations. Record the verdict and remaining risk in the matrix.
