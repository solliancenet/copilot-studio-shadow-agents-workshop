# Task 05-03 — Agent identities & least privilege

## Introduction

This is the task where the most Exercise 04 failures are directly addressable. The question that runs through
the whole workshop — *whose authority is this agent exercising, and what can it reach when it does?* — is answered
here by shrinking the authority and narrowing the reach. Concretely: replace an over-permissioned Dataverse
role with a scoped custom role plus narrower **record-level access**. Then scope an agent's **grounding**, so
the account its knowledge source reads with can't reach data the requesting user can't. Where you get this
right, the data is not reachable, and there is nothing left for an attacker to coax out.

## Description

You will work three failures. **Scenario B** (exfiltration): Benefits Buddy grounds on the whole `HR-Benefits`
site, including the `Leadership/` folder with the executive compensation file — you identify the knowledge
source's authentication mode and effective reader, then watch your facilitator narrow the source or that
reader's permission on `Leadership/`. **Scenario C** (excess connector permissions): the `svc-claims` service
account behind Claims Copilot holds a broad Dataverse role over **all** Claim and Customer rows — your
facilitator replaces it with a scoped role and narrower record-level access. **Scenario D** (confused deputy):
the same over-grant lets a low-privilege chat user reach any claim — you observe how much of that closes when
the acting identity is least-privileged, and what pattern still remains.

## Success Criteria

- [ ] You identified Benefits Buddy's effective reader, and recorded how the facilitator scoped its grounding
  (or the SharePoint permission behind it) so the agent can no longer reach
  `Leadership/2026-comp-bands.xlsx`.
- [ ] You recorded how the facilitator replaced the broad Dataverse grant on the Claims connection identity
  with a scoped custom security role and a fixed, defined subset of `Claim` / `Customer`, and compared that
  subset with the one you would have chosen.
- [ ] You re-ran Scenarios B, C, and D against the scoped configuration and observed the result for each.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for least privilege against B, C, and D
  in the [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each
  with a remaining-risk note.
- [ ] You can explain, in mechanism terms, why scoping the identity changes what Scenarios B and C can
  reach — and why the same scoping leaves the Scenario D pattern largely in place for you to judge.

### 02: Build a scoped Dataverse role (Scenarios C and D)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Confirm `svc-claims` is a service account: **Entra ID → Users** in the Microsoft Entra admin center, or
   `is_service_account` in your `users-export.csv`. Every chat user borrows this one account, so the role
   it holds is the reach of every conversation.
2. Watch the facilitator build the scoped role in the `Claims-Test` environment's Dataverse:
   a. a custom security role with **read** on `Claim` and `Customer` at **user** (or business-unit) depth,
      not organization, and only the tables the adjuster job needs;
   b. remove from the identity behind `DV-Claims-Shared` the organization-wide read/write, and any
      customizer or admin role Task 04-03 found;
   c. give it a fixed data subset with ownership, business units, teams and sharing — for example, the
      claims assigned to or shared with a team the account belongs to. A user-depth role with nothing owned
      or shared returns almost nothing; that's the design until the subset is granted.
3. Decide the subset you would have given `svc-claims`, and compare it with the facilitator's.

<!-- ![Dataverse custom security role scoped to user-level read on Claim and Customer, with organization-wide privileges removed](../../media/ex05_t03_kt01_s01.png) -->

</details>

{: .note }
> Record-level access is the difference between "can query the table" and "can query *these* records".

{: .note }
> A shared `svc-claims` has **one fixed Dataverse security context**: a user-level role on it does not make
> the agent see each requesting adjuster's own claims — it sees what `svc-claims` owns or is shared.
> Requester-specific access needs per-user (on-behalf-of) authorization, requester-aware authorization in
> the integration, or a deliberately constrained fixed data subset for the service identity.

> For each scenario below, do the tenant key task if you can reach the tenant, or the offline key task if
> you can't. Both lead to Key Task 09.
{: .note }

### 09: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Record verdicts for **Least privilege × B**, **× C**, and **× D**.
2. For each, note the remaining risk.

{: .caution }
> Everything here runs against a training estate — the records, the people and the keys are made up. You're
> still practicing the habit you'll need on a real estate: confirm the path exists, record it, and move on.

{: .important }
> **Where the boundary sits.** Least privilege attacks *reachability*: scope the acting credential and the
> knowledge source, and less data is there to reach — retest and see how much is left. It does not change
> *whose credential acts*. A least-privileged shared service account is still one fixed security context
> every chat user borrows.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Least privilege × B:** suggested **CLOSES IT** when the retest shows the comp file no longer appears —
  if the knowledge source's effective reader cannot reach `Leadership/`, there is nothing to leak.
- **Least privilege × C:** suggested **CLOSES IT** or **DENTS IT**, depending on how far the reachable set
  shrank. A fixed, deliberately constrained data subset for `svc-claims` removes the over-read; a role that
  still reaches most records only dents it.
- **Least privilege × D:** suggested **DENTS IT**. The blast radius is smaller, but every requester still
  borrows `svc-claims`'s single security context, so the confused-deputy pattern remains. Its resolution
  is user-context (on-behalf-of) or requester-aware authorization — a design change on the integration,
  not a smaller role.
- Two of these should feel decisively different; one only partly better — that difference is the lesson.

</details>

## Summary

Scoping the Dataverse role and record-level access, and scoping the grounding, attack the reachability
that Scenarios B and C depend on. Scenario D asks a different question — whose credential acts — and role
size alone does not answer it. Record the verdict and remaining risk in the matrix.
