# Task 05-03 — Agent identities & least privilege

## Introduction

This is the task where the most Module 4 failures are directly addressable. The question that runs through
the whole workshop — *whose authority is this agent exercising, and what can it reach when it does?* — is answered
here by shrinking the authority and narrowing the reach. Concretely: replace an over-permissioned Dataverse
role with a scoped custom role plus narrower **record-level access**, and scope an agent's **grounding** so
whoever its knowledge source reads as cannot reach data the requesting user cannot. Where you get this
right, the data is not reachable, and there is nothing left for an attacker to coax out.

## Description

You will work three failures. **Scenario B** (exfiltration): Benefits Buddy grounds on the whole
`HR-Benefits` site, including the `Leadership/` folder with the executive compensation file — you identify
the knowledge source's authentication mode and effective reader, then narrow the source or that reader's
permission on `Leadership/`. **Scenario C** (excess connector permissions): the `svc-claims` service account
behind Claims Copilot holds a broad Dataverse role over **all** Claim and Customer rows — you replace it
with a scoped role and narrower record-level access. **Scenario D** (confused deputy):
the same over-grant lets a low-privilege chat user reach any claim — you observe how much of that closes
when the acting identity is least-privileged, and what pattern still remains.

## Success Criteria

- [ ] You scoped Benefits Buddy's grounding (or the SharePoint permission behind it) so the agent can no
  longer reach `Leadership/2026-comp-bands.xlsx`.
- [ ] You replaced the broad Dataverse grant on the Claims connection identity with a scoped custom
  security role, and narrowed record-level access on `Claim` / `Customer`.
- [ ] You re-ran Scenarios B, C, and D against the scoped configuration and observed the result for each.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for least privilege against B, C, and D
  in the [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each
  with a remaining-risk note.
- [ ] You can explain, in mechanism terms, why scoping the identity changes what Scenarios B and C can
  reach — and why the same scoping leaves the Scenario D pattern largely in place for you to judge.

## Key Tasks

### 01: Scope the grounding (Scenario B) and the Dataverse role (Scenarios C/D)

Least privilege is two moves here: put the sensitive file out of the agent's reach, and shrink what the
acting credential can do in Dataverse.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scope Benefits Buddy's grounding.** In **Copilot Studio**, open Benefits Buddy's knowledge sources.
   It currently grounds on the entire `HR-Benefits` SharePoint site. First identify the knowledge source's
   authentication mode and its **effective reader** — whose permission decides what it can return. Then
   narrow the source to only the folders the benefits use-case needs, excluding `Leadership/`, or, if
   grounding must stay at the site level, remove that effective reader's permission on the `Leadership/`
   folder. The test is the same either way — can the agent reach the file at all?
2. **Build a scoped Dataverse role.** In the `Claims-Test` environment's Dataverse, create a custom
   security role that grants **read** on `Claim` and `Customer` at the **user/team** scope — not
   organization scope — and only the tables the adjuster job needs. Remove the organization-wide
   read/write from the identity behind the `DV-Claims-Shared` connection — and any customizer or admin role,
   if Task 04-03 found one.
3. **Narrow record-level access.** Use the role's privilege depth, record ownership, business units, teams
   and sharing to limit which `Claim` and `Customer` records the acting credential can reach. This is the
   difference between "can query the table" and "can query *these* records".
4. **Reconsider the shared service account.** The connection runs as `svc-claims`, a service account
   rather than a person: look it up in the **Microsoft Entra admin center** under **Entra ID → Users**, or
   read `is_service_account` in your `users-export.csv`. A shared `svc-claims` has **one fixed Dataverse
   security context**: a user-level role on it does not make the agent see each requesting adjuster's own
   claims — it sees what `svc-claims` owns or is shared. Requester-specific access needs per-user
   (on-behalf-of) authorization, requester-aware authorization in the integration, or a deliberately
   constrained fixed data subset for the service identity. Note this now; you will check it in the
   Scenario D retest.

### 02: Re-run Scenarios B, C, and D, then record the verdict

Three retests. Compare each outcome with what you saw in Module 4.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario B.** Re-open [Task 04-02 — Data exfiltration]({% link docs/04_break_the_agents/04_02.md %})
   and repeat the attempt to get Benefits Buddy to surface the leadership compensation figures. With the
   grounding scoped, observe: does the file's content still appear?
2. **Scenario C.** Re-open [Task 04-03 — Excessive connector / tool permissions]({% link docs/04_break_the_agents/04_03.md %}).
   Re-run the Claims Copilot Dataverse queries. With the scoped role and narrower record-level access, check
   whether the agent can still list **all** Customer rows and their PII, or only a smaller set.
3. **Scenario D.** Re-open [Task 04-04 — Identity / confused deputy]({% link docs/04_break_the_agents/04_04.md %}).
   Run the low-privilege-user path again (your own lab account chatting with the published Claims
   Copilot). The agent **still acts as `svc-claims`, not as the user**. Observe precisely: is the reachable
   data smaller, and is the requesting user still exercising a credential that is not theirs? The retest may
   show a smaller blast radius while the confused-deputy pattern remains; Task 05-04 and Task 05-07 examine
   what does and does not touch it.
4. **Offline path.** From `connections-export.csv`, `DV-Claims-Shared` has `auth_type = Service account`
   and is `shared_with` the Claims-Adjusters group; `users-export.csv` confirms `svc-claims` is a service
   account. Reason about what scoping svc-claims' role and narrowing record-level access does to the
   over-read (Scenario C), what narrowing the grounding does to the exfiltration (Scenario B), and whether
   role size changes the shared-credential acting model (Scenario D). Record each as a reasoned conclusion.
5. Record verdicts for **Least privilege × B**, **× C**, and **× D**, each with remaining risk.

</details>

{: .caution }
> Training estate only. When you retest, confirm the *shape* of the result — "the file no longer appears",
> "the reachable set shrank" — rather than harvesting the underlying PII. Recording that the reach
> shrank is the deliverable; the data is not.

{: .important }
> **Where the boundary sits.** Least privilege attacks *reachability*: scope the acting credential and the
> knowledge source, and less data is there to reach — retest and see how much is left. It does not change
> *whose credential acts*. A least-privileged shared service account is still one fixed security context
> every chat user borrows.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Least privilege × B:** suggested **CLOSES IT** when the retest shows the comp file no longer appears —
  if the knowledge source's effective reader cannot reach `Leadership/`, there is nothing to leak.
- **Least privilege × C:** suggested **CLOSES IT** or **DENTS IT**, depending on how far the reachable set
  shrank. A fixed, deliberately constrained data subset for `svc-claims` removes the over-read; a role that
  still reaches most records only dents it.
- **Least privilege × D:** suggested **DENTS IT**. The blast radius is smaller, but every requester still
  borrows `svc-claims`'s single security context, so the confused-deputy pattern remains. Its resolution
  is user-context (on-behalf-of) or requester-aware authorization — a design change on the integration,
  not a smaller role.
- Two of these should feel decisively different; one only partly better — that difference is the lesson.

</details>

## Summary

Scoping the Dataverse role and record-level access, and scoping the grounding, attack the reachability
that Scenarios B and C depend on. Scenario D asks a different question — whose credential acts — and role
size alone does not answer it. Record the verdict and remaining risk in the matrix.
