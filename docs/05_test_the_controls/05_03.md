# Task 05-03 — Agent identities & least privilege

## Introduction

This is the task where the most Module 4 failures are directly addressable. The question that runs through
the whole workshop — *whose authority is this agent exercising, and what can it reach when it does?* — is answered
here by shrinking the authority and narrowing the reach. Concretely: replace an over-permissioned Dataverse
role with a scoped custom role plus **row-level security**, and scope an agent's **grounding** so its
identity cannot read data the requesting user cannot. When you get this right, the data simply is not
reachable, and there is nothing left for an attacker to coax out.

## Description

You will work three failures. **Scenario B** (exfiltration): Benefits Buddy grounds on the whole
`HR-Benefits` site, including the `Leadership/` folder with the executive compensation file — you scope the
grounding so the agent identity cannot read it. **Scenario C** (excess connector permissions): the
`svc-claims` service account behind Claims Copilot holds a broad Dataverse role over **all** Claim and
Customer rows — you replace it with a scoped role and row-level security. **Scenario D** (confused deputy):
the same over-grant lets a low-privilege chat user reach any claim — you observe how much of that closes
when the acting identity is least-privileged, and what pattern still remains.

## Success Criteria

- [ ] You scoped Benefits Buddy's grounding (or the SharePoint permission behind it) so its identity
  cannot read `Leadership/2026-comp-bands.xlsx`.
- [ ] You replaced the broad Dataverse grant on the Claims connection identity with a scoped custom
  security role, and enabled row-level security on `Claim` / `Customer`.
- [ ] You re-ran Scenarios B, C, and D against the scoped configuration and observed the result for each.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for least privilege against B, C, and D
  in the [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each
  with a remaining-risk note.
- [ ] You can explain, in mechanism terms, why scoping the identity changes what Scenarios B and C can
  reach — and why the same scoping leaves the Scenario D pattern largely in place for you to judge.

## Key Tasks

### 01: Scope the grounding (Scenario B) and the Dataverse role (Scenarios C/D)

Least privilege is two moves here: make the sensitive file unreadable to the agent identity, and shrink
what the acting identity can do in Dataverse.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scope Benefits Buddy's grounding.** In **Copilot Studio**, open Benefits Buddy's knowledge sources.
   It currently grounds on the entire `HR-Benefits` SharePoint site. Narrow it to only the folders the
   benefits use-case needs, excluding `Leadership/`. If grounding must stay at the site level, instead fix
   it at the source: remove the agent identity's (or the connection owner's) read permission on the
   `Leadership/` folder so the compensation file is not in reach. The test is the same either way — can the
   agent read the file at all?
2. **Build a scoped Dataverse role.** In the `Claims-Test` environment's Dataverse, create a custom
   security role that grants **read** on `Claim` and `Customer` at the **user/team** scope — not
   organization scope — and only the tables the adjuster job needs. Remove the organization-wide
   read/write from the identity behind the `DV-Claims-Shared` connection — and any customizer or admin role,
   if Task 04-03 found one.
3. **Enable row-level security.** Configure ownership/business-unit or record-sharing so a given adjuster
   sees only their **own** assigned claims, not every row. This is the difference between "can query the
   table" and "can query *these* rows".
4. **Reconsider the shared service account.** The connection runs as `svc-claims`, a service account
   rather than a person: look it up in the **Microsoft Entra admin center** under **Entra ID → Users**, or
   read `is_service_account` in your `users-export.csv`. Least privilege on a *shared* identity still means
   everyone who uses the agent inherits that identity's reach — note this now; you will feel it in the
   Scenario D retest.

</details>

### 02: Re-run Scenarios B, C, and D, then record the verdict

Three retests. Two of them should feel decisively different; one should feel only partly better — and that
difference is the lesson.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario B.** Re-open [Task 04-02 — Data exfiltration]({% link docs/04_break_the_agents/04_02.md %})
   and repeat the attempt to get Benefits Buddy to surface the leadership compensation figures. With the
   grounding scoped, observe: does the file's content still appear? If the identity cannot read it, there
   is nothing to leak.
2. **Scenario C.** Re-open [Task 04-03 — Excessive connector / tool permissions]({% link docs/04_break_the_agents/04_03.md %}).
   Re-run the Claims Copilot Dataverse queries. With the scoped role and row-level security, check whether
   the agent can still list **all** Customer rows and their PII, or only the assigned subset.
3. **Scenario D.** Re-open [Task 04-04 — Identity / confused deputy]({% link docs/04_break_the_agents/04_04.md %}).
   Run the low-privilege-user path again (the Jordan Blake persona chatting with Claims Copilot). Least
   privilege shrinks what the deputy can reach — but the agent **still acts as `svc-claims`, not as the
   user**. Observe precisely: is the reachable data smaller, and yet is the requesting user still exercising
   an identity that is not theirs? That residual is the confused-deputy pattern; Task 05-04 and Task 05-07
   examine what does and does not touch it.
4. **Offline path.** From `connections-export.csv`, `DV-Claims-Shared` has `auth_type = Service account`
   and is `shared_with` the Claims-Adjusters group; `users-export.csv` confirms `svc-claims` is a service
   account. Reason: scoping svc-claims' role and enabling row-level security removes the *over-read*
   (Scenario C) and starves the exfiltration (Scenario B), while the shared-identity acting model
   (Scenario D) is unchanged by role size alone.
5. Record verdicts for **Least privilege × B**, **× C**, and **× D**, each with remaining risk. Expect
   these three cells to *not* all read the same.

</details>

{: .caution }
> Training estate only. When you retest, confirm the *shape* of the result — "the file no longer appears",
> "only my assigned claims return" — rather than harvesting the underlying PII. Recording that the reach
> shrank is the deliverable; the data is not.

{: .important }
> **Where the boundary sits.** Least privilege attacks *reachability*: scope the identity and the data
> behind over-permission (Scenario C) and over-broad grounding (Scenario B) is simply not there to reach —
> retest and see how much is left. But it does not change *whose identity acts*. A perfectly
> least-privileged shared service account is still a shared identity every chat user borrows, so the
> confused-deputy pattern (Scenario D) survives a smaller role. Its resolution is user-context
> (on-behalf-of) authorization — a design change on the integration, not a smaller role.

## Summary

This is the highest-yield control in the module. Scoping the Dataverse role with row-level security and
scoping the grounding directly attack the reachability that Scenarios B and C depend on — when the agent
identity cannot read the comp file or the full Customer table, there is nothing to exfiltrate or
over-read. Scenario D is the honest caveat: shrinking the acting identity's reach helps, but the pattern of
a user borrowing an identity that is not theirs survives a smaller role. You recorded three verdicts that
should not all match, which is exactly the point.
