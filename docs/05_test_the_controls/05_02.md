# Task 05-02 — Environment strategy

## Introduction

In Power Platform, the **environment** is the real isolation boundary. Each environment has its own
Dataverse database, its own DLP scope, its own maker access, and its own set of connections. A deliberate
environment strategy — a locked-down default environment, a managed production environment, and
short-lived test environments with a *gated* path to production — is one of the highest-leverage controls
you have. It is also commonly misread as a security boundary that does more than it does, so this task is
about testing the difference between "moved" and "fixed".

## Description

You will assess the estate's four environments (`Halcourt (default)`, `Halcourt-Prod`, `Claims-Test`,
`Maker-Sandbox`), watch your facilitator add connector blocks to the default environment, record why maker
access there can't be locked to a group, specify connector availability where the strategy is broken, and design the gated promotion that `Claims-Test` never had. Then
you retest **Scenario C** (excessive connector / tool permissions) and **Scenario F** (lifecycle — the "test"
environment that quietly became production), and record what environment separation actually bought you versus
what it left untouched.

## Success Criteria

- [ ] You can describe each environment's type, DLP status, and maker access, and name which ones are
  risk-bearing.
- [ ] You recorded which connectors the facilitator blocked in the default environment, explained why its
  maker access can't be restricted to a group, and specified connector availability per environment.
- [ ] You defined a gated promotion path (test → production) that would have stopped `Claims-Test` from
  silently becoming production.
- [ ] You re-ran Scenario C and Scenario F and observed what changed and what did not.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for environment strategy against C and F
  in the [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each
  with a remaining-risk note.

### 03: Watch the facilitator lock down the default environment

The default environment is shared by every estate in the lab tenant, so your facilitator makes this change
for the room and reverts it straight after the retests.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

The facilitator:

1. Applies a data policy to the default environment that blocks **HTTP** and **custom connectors** — the
   same blocks as Task 05-01.

You: note which connectors the policy blocks. Then look at who can make agents in `Halcourt (default)`.
Every licensed user in the tenant is an Environment Maker there automatically, and that can't be removed,
so swapping the role's members for `Halcourt-Makers` would not restrict anyone. Write that down as a
finding: the default environment can be governed with data policies, but not fenced to a group of makers.
That is why sensitive agents belong in their own environments, where maker access *can* be restricted.
Without the tenant, write the policy down as you would apply it, and the same finding.

</details>

### 04: Constrain connectors per environment

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Specify, for each environment, that HTTP and custom/MCP connectors are allowed only if both are true:
   a. one of its agents needs the integration for its stated purpose;
   b. the environment is managed and has a data policy.
2. Specify them as blocked everywhere else.
3. Record the result as a small table: environment → allowed or blocked → reason.

</details>

### 05: Design the missing gate

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Sketch a promotion path from a short-lived test environment to `Halcourt-Prod`: a Power Platform
   pipeline with an approval step before deployment.
2. List what the approver checks:
   a. a present, accountable owner;
   b. each connection's owner and `auth_type`;
   c. the connectors the agent uses against what its purpose needs.

</details>

### 10: Record the verdicts

<details markdown="block">

{: .note }
> **Forward-looking by design.** Environment strategy changes where agents *can* be built and how they
> *get promoted*. It works on drift and shadow sprawl, and it sets up least privilege and lifecycle to
> succeed. It does not reach inside an environment to change a connection's role or an agent's owner.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Environment strategy × F:** suggested **DENTS IT**. A gated promotion path is exactly what
  `Claims-Test` lacked, and it prevents the *next* drift; it does not retroactively fix the agent already
  in use, and it does nothing for the orphaned Onboarding Guide.
- **Environment strategy × C:** suggested **DENTS IT**. A properly scoped environment with only the
  connectors it needs reduces reach; it does not shrink what `svc-claims` can read.
- **Remaining risk to note:** an over-permissioned connection or an already-orphaned agent does not heal
  because you drew a cleaner boundary around it.

</details>

## Summary

Environment separation is the frame the other controls hang on: it decides which connectors exist, which
DLP applies, and who can build. Retesting Scenarios F and C shows where a gated promotion path helps and
where the boundary stops — it narrows reach but does not reach inside an environment to un-grant a role.
Record the verdict and remaining risk in the matrix.
