# Task 05-02 — Environment strategy

## Introduction

In Power Platform, the **environment** is the real isolation boundary. Each environment has its own
Dataverse database, its own DLP scope, its own maker access, and its own set of connections. A deliberate
environment strategy — a locked-down default environment, a managed production environment, and
short-lived test environments with a *gated* path to production — is one of the highest-leverage controls
you have. It is also commonly misread as a security boundary that does more than it does, so this task is
about testing the difference between "moved" and "fixed".

## Description

You will assess the estate's four environments (`Halcourt (default)`, `Halcourt-Prod`, `Claims-Test`,
`Maker-Sandbox`), see your facilitator add connector blocks to the default environment, record why maker
access there can't be locked to a group, specify connector availability where the strategy is broken, and design the gated promotion that `Claims-Test` never had. Then
you retest **Scenario C** (excessive connector / tool permissions) and **Scenario F** (lifecycle — the "test"
environment that quietly became production), and record what environment separation actually bought you versus
what it left untouched.

## Success Criteria

- [ ] You can describe each environment's type, DLP status, and maker access, and name which ones are
  risk-bearing.
- [ ] You recorded which connectors the facilitator blocked in the default environment, explained why its
  maker access can't be restricted to a group, and specified connector availability per environment.
- [ ] You defined a gated promotion path (test → production) that would have stopped `Claims-Test` from
  silently becoming production.
- [ ] You checked whether the change reached Scenarios C and F, and recorded what it did not touch.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for environment strategy against C and F,
  and for DLP against F, in the
  [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each with a
  remaining-risk note.

### 02: The facilitator locks down the default environment

The default environment is shared by every estate in the lab tenant, so your facilitator makes this change
for the room and reverts it straight after the retests.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

The facilitator:

1. Opens `Halcourt-Prod-DLP` (**Edit Policy**) and selects **Next** to **Environments**.
2. On **Available**, searches for `default`, ticks `Halcourt (default)`, and selects **+ Add to policy**.
   The row moves to **Added to policy**; **Next** stays disabled until it does.
3. Selects **Next** and saves on **Review**. The default environment now has the same HTTP and
   custom-connector blocks as Task 05-01.
4. After the retests, removes `Halcourt (default)` from the policy the same way, then restores the policy to
   its baseline (Task 05-01's put-back).

You: note which connectors the policy blocks. Then look at who can make agents in `Halcourt (default)`.
Every licensed user in the tenant is an Environment Maker there automatically, and that can't be removed,
so swapping the role's members for `Halcourt-Makers` would not restrict anyone. Write that down as a
finding: the default environment can be governed with data policies, but not fenced to a group of makers.
That is why sensitive agents belong in their own environments, where maker access *can* be restricted.

</details>

### 03: Specify where these connectors belong

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each environment, answer three questions:
   a. Does an agent in it need HTTP, custom or MCP connectors for its stated purpose?
   b. Is the environment managed?
   c. Does it have a data policy?
2. Allow the connectors only if all three are yes; block them otherwise.
3. Write one row per environment: result and reason. The rows that should block but have no policy to do
   it are your remaining risk.

</details>

<details markdown="block">
<summary>Reveal the suggested table</summary>

| Environment | Result | Reason |
|---|---|---|
| `Halcourt (default)` | **Blocked** | No agent there needs HTTP or MCP, and it isn't managed. |
| `Halcourt-Prod` | **Allowed**, limited to their own endpoints | Policy Lookup Bot (HTTP) and Underwriting Assistant (MCP) need them; it's managed and has `Halcourt-Prod-DLP`. |
| `Claims-Test` | **Blocked** | Claims Copilot uses only Dataverse, which no data policy can block; not managed, no policy. |
| `Maker-Sandbox` | **Blocked** | Team Wiki's HTTP isn't part of a wiki helper's job; not managed, no policy. |

`Claims-Test` and `Maker-Sandbox` should block these connectors, but have no policy that does.

</details>

### 04: Design the missing gate

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Write the promotion path as numbered stages, from build in a short-lived test environment to deploy in
   `Halcourt-Prod`, with an approval step by someone other than the maker.
2. Write the approver's checklist:
   a. an accountable owner;
   b. each connection's owner and `auth_type`;
   c. the connectors and grant against the agent's purpose;
   d. the environment it runs in.
3. Run Claims Copilot through your checklist: which checks does it fail?

</details>

<details markdown="block">
<summary>Reveal a suggested gate and the Claims Copilot check</summary>

1. **Build** in a short-lived test environment that gets a data policy and a review date when it's created.
2. **Request promotion** through a Power Platform pipeline to `Halcourt-Prod`; nothing deploys yet.
3. **Approval** by a named approver, not the maker, against the checklist.
4. **Deploy** to `Halcourt-Prod` as a managed solution, under `Halcourt-Prod-DLP`.
5. **Retire** the test copy; the test environment is deleted at its review date.

| Check | Claims Copilot today | Pass? |
|---|---|---|
| An accountable owner | Priya Nair, present | Yes |
| Each connection's owner and `auth_type` | `DV-Claims-Shared`, owned by `svc-claims`, Service account | **No:** every chat borrows one service account |
| Connectors and grant vs. purpose | Needs the adjuster's own claims; `svc-claims` has Organization-level create, read and write on every Claim and Customer row | **No:** the grant is far broader than the job |
| The environment it runs in | `Claims-Test`: Sandbox, unmanaged, no data policy, doing real work | **No:** it never went through promotion |

The gate would have stopped Claims Copilot. It works only on the *next* promotion, though.

</details>

### 05: Check Scenarios F and C

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario F.** Neither lifecycle agent is touched by the default-environment change: Onboarding Guide
   sends mail through Office 365 Outlook, which isn't blocked, and Claims Copilot is in `Claims-Test`,
   which didn't change. Record that.
2. Check whether **blocking a connector** could stop Onboarding Guide: look for Office 365 Outlook on
   Microsoft's list of connectors that can't be placed in the Blocked group (Learning Resources). The list
   uses the newer Microsoft 365 names, so Office 365 Outlook would appear as **Microsoft 365 Outlook**.
   Record what you find for the DLP × F cell.
3. Ask whether the gate from Key Task 04 would have stopped Claims Copilot, and whether it does anything
   for the copy already running.
4. **Scenario C.** Nothing changed in `Claims-Test`, so there's nothing to retest. Record that: environment
   strategy decides which connectors exist, not what `svc-claims` can read.

</details>

### 06: Record the verdicts

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In your [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), fill
   the **Env strategy** column's **C** and **F** cells, and the **DLP** column's **F** cell.
2. For each, copy a **Retest log** block below the matrix: Before, After, Verdict, and Remaining risk.

</details>

{: .note }
> **Forward-looking by design.** Environment strategy changes where agents *can* be built and how they
> *get promoted*. It works on drift and shadow sprawl, and it sets up least privilege and lifecycle to
> succeed. It does not reach inside an environment to change a connection's role or an agent's owner.

<details markdown="block">
<summary>Reveal the suggested verdicts and reasoning</summary>

- **Environment strategy × F:** suggested **DENTS IT**. A gated promotion path is exactly what
  `Claims-Test` lacked, and it prevents the *next* drift; it does not retroactively fix the agent already
  in use, and it does nothing for the orphaned Onboarding Guide.
- **Environment strategy × C:** suggested **MISSES IT**. Nothing in Claims Copilot's environment changed,
  and a properly scoped environment still doesn't shrink what `svc-claims` can read.
- **DLP × F:** suggested **MISSES IT**. Office 365 Outlook, Onboarding Guide's only connector, is on
  Microsoft's list of connectors a data policy can't put in the **Blocked** group (as Microsoft 365
  Outlook), so the connector-blocking this exercise does can't take away its send-mail capability. A
  data policy also never touches ownership, so the orphan is still an orphan. Whether another mechanism
  (advanced connector policies, or forcing a data-group conflict) could reach it is open (#100).
- **Remaining risk to note:** an over-permissioned connection or an already-orphaned agent does not heal
  because you drew a cleaner boundary around it.

</details>

## Summary

Environment separation is the frame the other controls hang on: it decides which connectors exist, which
DLP applies, and who can build. Retesting Scenarios F and C shows where a gated promotion path helps and
where the boundary stops — it narrows reach but does not reach inside an environment to un-grant a role.
Record the verdict and remaining risk in the matrix.
