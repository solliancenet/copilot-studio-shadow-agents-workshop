# Task 05-02 — Environment strategy

## Introduction

In Power Platform, the **environment** is the real isolation boundary. Each environment has its own
Dataverse database, its own DLP scope, its own maker access, and its own set of connections. A deliberate
environment strategy — a locked-down default environment, a managed production environment, and
short-lived test environments with a *gated* path to production — is one of the highest-leverage controls
you have. It is also commonly misread as a security boundary that does more than it does, so this task is
about testing the difference between "moved" and "fixed".

## Description

You will assess the estate's four environments (`Halcourt (default)`, `Halcourt-Prod`, `Claims-Test`,
`Maker-Sandbox`), tighten maker access and connector availability where the strategy is broken, and design
the gated promotion that `Claims-Test` never had. Then you retest **Scenario C** (excessive connector /
tool permissions) and **Scenario F** (lifecycle — the "test" environment that quietly became production),
and record what environment separation actually bought you versus what it left untouched.

## Success Criteria

- [ ] You can describe each environment's type, DLP status, and maker access, and name which ones are
  risk-bearing.
- [ ] You restricted maker access on the default environment and specified connector availability per
  environment.
- [ ] You defined a gated promotion path (test → production) that would have stopped `Claims-Test` from
  silently becoming production.
- [ ] You re-ran Scenario C and Scenario F and observed what changed and what did not.
- [ ] You recorded **CLOSES IT / DENTS IT / MISSES IT** verdicts for environment strategy against C and F
  in the [Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}), each
  with a remaining-risk note.

## Key Tasks

### 01: Assess the environments and tighten the strategy

Separation only helps if the boundaries are drawn where the risk is. Start by writing down what each
environment actually is.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In **PPAC → Environments**, record for each environment its **type**, **managed** status, **DLP
   policy**, and **maker access**. Offline, this is `environments-export.csv` in full: the default
   environment allows **All users** to build and has no DLP; `Claims-Test` is a **Sandbox** with no DLP
   but real production traffic; `Maker-Sandbox` is a personal developer environment; only `Halcourt-Prod`
   is Managed with a DLP policy.
2. **Lock down the default environment.** It is where shadow and orphan agents were born (Expense Helper
   and Onboarding Guide both live here). Restrict who can create agents and connections, and apply a DLP
   policy so an ungoverned build surface stops being the path of least resistance. In the lab tenant the
   default environment is shared by every estate built there, so specify this change rather than applying
   it, unless the facilitator says otherwise.
3. **Constrain connectors per environment.** A sensitive environment should only expose the connectors its
   agents legitimately need. Decide which environments should even be *able* to host an HTTP action or a
   custom/MCP connector — this reinforces what you did in Task 05-01, but now as a property of the
   environment rather than a single policy.
4. **Design the missing gate.** Sketch a promotion path where an agent built in an ephemeral test
   environment must pass an explicit review — ownership, connections, connector scope — before it can be
   deployed to `Halcourt-Prod`. Note that pipelines and managed environments are the mechanism; the point
   here is that `Claims-Test` had **no gate at all**.

</details>

### 02: Re-run Scenario C and Scenario F, then record the verdict

Now test what the boundary does and does not move.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Scenario F.** Re-open [Task 04-06 — Lifecycle]({% link docs/04_break_the_agents/04_06.md %}). The
   Claims Copilot half of that scenario is a sandbox agent doing production work. Ask: does putting a real
   environment strategy in place *retroactively* fix the agent that already drifted, or does it only
   prevent the **next** one? Separately, does an environment gate do anything about the orphaned Onboarding
   Guide, whose owner is already gone?
2. **Scenario C.** Re-open [Task 04-03 — Excessive connector / tool permissions]({% link docs/04_break_the_agents/04_03.md %}).
   A well-scoped environment can limit *which connectors exist*, which narrows reach. But watch the core
   over-grant: `Claims Copilot` runs on the shared `svc-claims` Dataverse connection with a broad role.
   Moving the agent to a cleaner environment does not, by itself, shrink what that service account can
   read. Note whether the PII over-read is gone or merely relocated.
3. **Offline path.** From `agents-export.csv`, `Claims Copilot` is in `Claims-Test` and has a recent
   `last_modified_utc` — active production use in a sandbox. From `environments-export.csv`, that sandbox
   has no DLP and Claims-team maker access. Reason: an ephemeral test environment with a gated promotion
   would have forced a review that could have caught the shared service-account connection **before** it
   reached production — but the connection's over-permission is a Dataverse-role problem, addressed in the
   next task.
4. Record a verdict for **Environment strategy × C** and **Environment strategy × F** in the matrix, with
   the remaining risk for each.

</details>

{: .note }
> **Prevents the next one; rarely fixes this one.** Environment strategy is a forward-looking control. It
> changes where agents *can* be built and how they *get promoted*. It is powerful against drift and shadow
> sprawl, and it sets up least privilege and lifecycle to succeed — but an over-permissioned connection or
> an already-orphaned agent does not heal because you drew a cleaner boundary around it.

## Summary

Environment separation is the frame the other controls hang on: it decides which connectors exist, which
DLP applies, and who can build. Tested against Scenario F it shows its real strength — a gated promotion
path is exactly what `Claims-Test` lacked — and tested against Scenario C it shows its limit: the boundary
narrows reach but does not reach inside an environment to un-grant a role. You located both edges and
recorded honest verdicts.
