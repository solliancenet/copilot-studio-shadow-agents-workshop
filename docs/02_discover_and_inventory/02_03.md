# Task 02-03 — Hunt the problem estate

## Introduction

The findings aren't in any single CSV. They show up only in your inventory, where each agent's row
brings together facts from several: an owner who has left, a connection owned by someone who left, a
sandbox doing production work. This task teaches you the hunts: the specific questions that turn a
flat inventory into a risk picture. It also teaches the harder discipline: an agent that *looks*
risky is not a finding until you can show the two records that prove it, and an agent that looks scary can
be **clean** once you inspect its effective access.

## Description

You will run five targeted hunts against your inventory from Task 02-02, each looking for one problem
condition. Each hunt produces a **candidate list**, not a verdict. You then confirm every candidate with a
second data point, and — just as important — you deliberately try to **clear** the agents that only look
risky. You are building evidence, not vibes.

## Success Criteria

- [ ] You ran each of the five hunts and recorded the candidate agents each one surfaced.
- [ ] For every candidate you confirmed the condition with a second data point (not just the one column that flagged it).
- [ ] You distinguished the **agent owner** from the **connection owner** wherever they differ. (Whose credential actually acts on each call is Exercise 03's question.)
- [ ] You attempted to clear at least the agents that look risky on name or location alone, and wrote a one-line justification for each you cleared.
- [ ] You can explain why a sandbox location or a duplicated name is a **candidate**, not a **verdict**.
- [ ] You compared your hunt results and clearances with the suggested ones.

## Key Tasks

### 01: Run the five hunts

Each hunt is a question about the inventory you built in Task 02-02. Write down which agents turn up. Do
**not** assume the column that flagged an agent is the whole story — confirm with the second data point
in each hunt.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Orphaned: is the owner gone?** In your inventory's **Owner (status)** column, find every agent whose
   owner has left or is disabled.
   - *Confirm:* does its **Tool calls** column still list a connection? An orphan whose connection is
     still there is the dangerous kind: nothing has cut off what its owner set up.

   <details markdown="block">
   <summary>Reveal the suggested answer</summary>

   **Onboarding Guide**: owner `tom.dean` left on 2026-01-30, and his account is still enabled. It still
   has its connection, `O365-Outlook-Onboarding`, which can send mail.

   </details>

2. **Shadow: is it built in a personal environment?** In your inventory's **Environment** column, find
   every agent in a **Developer** environment. A Developer environment belongs to one maker, and is never
   a sanctioned place to run agents for others.
   - *Confirm:* was IT ever meant to govern it? Is the environment unmanaged in your inventory?

   <details markdown="block">
   <summary>Reveal the suggested answer</summary>

   **Team Wiki** and **Meeting Notes Summarizer**, both in `Maker-Sandbox` (Developer), which is `managed`
   `No`, with Dev Kim as its only maker, and no DLP. Team Wiki is confirmed: it searches Microsoft 365 on
   Dev's own connection, so its reach is everything Dev can read. Meeting Notes Summarizer is only a
   candidate; Key Task 02 looks at it.

   </details>

3. **Test became prod: does the label lie?** In your inventory, find every agent in a **Sandbox**
   environment. Is it published, and does its **Purpose** say it does real business work, not
   experimentation?
   - *Confirm:* does the same environment show no DLP? That's production work running with sandbox
     governance.

   <details markdown="block">
   <summary>Reveal the suggested answer</summary>

   **Claims Copilot**, in `Claims-Test` (Sandbox). It's published and available, and it helps claims
   adjusters look up claims: real business work. `Claims-Test` has no DLP.

   </details>

4. **Shared connection: does the agent run as someone else?** In your inventory's **Tool calls** column,
   find every line whose connection owner:
   - isn't the agent's owner,
   - is a service account, or
   - has left or is disabled.

   With Maker-provided credentials, a service account, a flow owner or a key, the call carries that
   connection's authority, not the person chatting's, so anyone who chats with the agent acts as its
   connection owner.
   - *Confirm:* that owner's status, already in the line.

   <details markdown="block">
   <summary>Reveal the suggested answer</summary>

   Three agents:
   - **Claims Copilot** on `DV-Claims-Shared`, owned by `svc-claims`, a service account, not the agent
     owner `priya.nair`.
   - **Sales Nudge** on `DV-CRM-Shared`, owned by `tom.dean`, not the agent owner `lena.ford`. Tom left on
     2026-01-30, and his account is still enabled.
   - **Onboarding Guide** on `O365-Outlook-Onboarding`, owned by `tom.dean`, who has left.

   </details>

5. **Unknown or ambiguous owner: is anyone personally accountable?** In your inventory's
   **Owner (status)** column, find every agent owned by a shared mailbox, or by anything that isn't a
   person. Then find any agent whose owner is active but whose **Tool calls** belong to someone who has
   left or is disabled: the owner can't account for authority that isn't theirs, and the person whose
   authority it is has gone. The same agent can take this flag and hunt 4's.
   - *Confirm:* what is the agent wired to? An ambiguously owned agent with an external integration or a
     hard-coded credential is worse than one with none.

   <details markdown="block">
   <summary>Reveal the suggested answer</summary>

   Two agents:
   - **Policy Lookup Bot**: owner `it.helpdesk` is a shared mailbox. Its HTTP request calls an external
     API with an API key in a header: a hard-coded credential.
   - **Sales Nudge**: owner `lena.ford` is active, but it runs on `DV-CRM-Shared`, owned by `tom.dean`,
     who has left. Lena can't account for Tom's CRM access, and Tom is gone.

   **Onboarding Guide** doesn't take this flag. Its owner is a known, named person who has left: that's
   hunt 1's Orphaned flag.

   </details>

</details>

### 02: Clear the ones that only look risky

Some agents will trip a hunt on **name or location alone** and turn out to be fine. Clearing them is real
security work: you owe a reason, not a shrug. Do not clear an agent because it "seems okay" — clear it
because its **effective access** is limited and you can point to the evidence.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **A name or a location is not a verdict.** An agent can trip a hunt on its name alone (a copy, a "v2")
   or its location alone (a personal or sandbox environment). Before you decide, check its effective
   access:
   - **Knowledge:** your inventory's **Grounding** column.
   - **Tools and actions:** your inventory's **Tool calls** column. Check whether any of them writes or
     sends.
   - **Acting credential:** the `auth_type` and connection owner in each **Tool calls** line.
   - **Audience:** who can chat with it. This isn't in your inventory: it's the agent's sharing in Copilot
     Studio.

   Without the tenant, your inventory's Grounding is Unknown: leave the agent uncleared until that check
   is done.
2. **Clear it only if its reach fits its purpose.** If what it can read and do is proportionate to its
   stated purpose, and limited to data its users could already see, clear it. Still record where you
   found it (for example, "discovered in a personal environment"), and say explicitly that its risk is
   low.
3. **Write the justification.** For every agent you clear, record one line: which hunt flagged it, what you
   checked, and why the effective access makes it acceptable. A cleared agent with a written reason is a
   finding; a cleared agent with no reason is an assumption waiting to bite you.
4. **Re-check the confident ones.** The mirror-image discipline: an agent that looks boring but has a
   service-account connection, a departed or disabled connection owner, or a broad group share is **not** clean, no
   matter how ordinary its name. Let the records, not the names, decide.

</details>

<details markdown="block">
<summary>Reveal the suggested clearances</summary>

Decide on your own clearances first, then compare.

- **HR FAQ v2 (copy).** It trips on its name: a "v2" copy of an HR bot, in `Halcourt-Prod`. *Checked:* its
  **Knowledge** is the `HR FAQ` document library in the `HR-Benefits` site, and nothing else. That library
  holds one FAQ and is open to all staff. It is not the whole site, and it is not `Shared Documents` or
  `Leadership/`. It has no tools or actions, and its knowledge source searches the library directly, with no
  connection. *Justification:* it reads one all-staff FAQ that every employee can
  already see, and it can't write or send anything. Cleared, low risk.
- **Meeting Notes Summarizer.** It trips the shadow hunt: `Maker-Sandbox`, a personal environment.
  *Checked:* it has no tools or actions, and its **Knowledge** is one SharePoint source,
  *DevKim-OneDrive-Notes*, which it searches with no connection. Whose access that search uses is Unknown
  until Exercise 04. *Not yet cleared:* check what that source holds first. If it's only Dev's own notes,
  clear it as low risk and record it as discovered in a personal environment.

From the pack alone you can't clear either one. The pack doesn't hold grounding, so neither can be cleared
until you check it.

No flag is not the same as cleared. **Benefits Buddy**, **Underwriting Assistant** and **Expense Helper**
take none of the five flags, but nothing here clears them. Exercise 03 maps what they can reach.

</details>

{: .caution }
> "Sandbox equals bad" and "duplicate equals sprawl" are pattern-matching, not analysis. They generate
> candidates; they do not close cases. The whole point of this hunt is to replace the vibe with evidence
> you can show someone: the two rows that prove it.

{: .note }
> A clean agent is a finding too. If you cannot justify *why* an agent is fine, it is not cleared yet — it
> is just un-reviewed.

## Summary

You ran five hunts — orphaned owner, shadow environment, test-became-prod, shared connection, and ambiguous
owner — and treated each result as a candidate to be confirmed, not a verdict. You separated the agent owner
from the connection owner wherever they diverged, and you did the harder half of the job: clearing the
agents that only look risky, with a written reason for each. Next you consolidate all of this into the
finished deliverable and set the flags.
