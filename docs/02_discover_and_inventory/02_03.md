# Task 02-03 — Hunt the problem estate

## Introduction

The findings are not written in any single file. They live in the **joins**: an agent whose owner is
disabled, a connection owned by someone who left, an environment that is a sandbox on paper but production
in practice. This task teaches you the hunts — the specific cross-references that turn a flat inventory
into a risk picture. It also teaches the harder discipline: an agent that *looks* risky is not a finding
until you can show the join that proves it, and an agent that looks scary can be **clean** once you inspect
its effective access.

## Description

You will run five targeted hunts against the artifact pack, each looking for one problem condition. Each
hunt produces a **candidate list**, not a verdict. You then confirm every candidate with a second data
point, and — just as important — you deliberately try to **clear** the agents that only look risky. You are
building evidence, not vibes.

## Success Criteria

- [ ] You ran each of the five hunts and recorded the candidate agents each one surfaced.
- [ ] For every candidate you confirmed the condition with a second data point (not just the one column that flagged it).
- [ ] You distinguished the **agent owner** from the **connection owner** wherever they differ, and noted which identity is the real actor.
- [ ] You attempted to clear at least the agents that look risky on name or location alone, and wrote a one-line justification for each you cleared.
- [ ] You can explain why a sandbox location or a duplicated name is a **candidate**, not a **verdict**.

## Key Tasks

### 01: Run the five hunts

Each hunt is a join with a filter. Run them against your inventory; write down which agents fall out. Do
**not** assume the column that flagged an agent is the whole story — confirm with the second data point
noted in each hunt.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Orphaned — the owner is gone.** Join each agent's `owner_upn` to `users-export.csv` and filter where
   `account_enabled = FALSE`. An active, published agent whose owner's account is disabled has nobody
   accountable. *Confirm with the second data point:* check whether that agent still has a **live
   connection** in `connections-export.csv` — an orphan with a working connection is the dangerous kind.
2. **Shadow — built in a personal/developer environment.** Join `environment` to `environments-export.csv`
   and filter where `type` is **Developer** (individual maker) — a personal environment that was never a
   sanctioned place to run production agents. Every agent in that environment is a candidate. *Confirm with
   the second data point:* was IT ever meant to govern this environment? A developer/personal environment
   with all-maker or individual access is a blind spot by design.
3. **Test-became-prod — the label lies.** Join `environment` to `environments-export.csv` and filter where
   `type = Sandbox`. Then look at the agent's own row: is it `published = Yes`, `status = Active`, recently
   modified, and described as doing **real business work** (not experimentation)? A sandbox that is quietly
   carrying production load is a finding. *Confirm with the second data point:* check whether the same
   environment has **no DLP** (`dlp_policy` empty) — production work running with sandbox governance.
4. **Shared connection — the agent runs as someone else.** For each agent, compare its `owner_upn` against
   the `connection_owner_upn` of the connection(s) it uses. Flag a candidate when **any** of these is true:
   the connection owner is **not** the agent owner; the connection owner is a **service account**
   (`is_service_account = TRUE` in `users-export.csv`); the connection owner's account is **disabled**; or
   the connection is `shared_with` a group. The connection identity — not the agent owner — is who the
   agent acts as. *Confirm with the second data point:* look up the connection owner in `users-export.csv`
   to see exactly whose authority is in play.
5. **Unknown / ambiguous owner — nobody is personally accountable.** Join `owner_upn` to
   `users-export.csv` and filter where `is_shared_mailbox = TRUE` (or where the "owner" is otherwise a
   non-person). A shared mailbox as owner means an agent that everyone and no one owns. *Confirm with the
   second data point:* check what that agent is wired to — an ambiguously-owned agent with an external
   integration or a hard-coded credential is worse than one with none.

</details>

### 02: Clear the ones that only look risky

Some agents will trip a hunt on **name or location alone** and turn out to be fine. Clearing them is real
security work: you owe a reason, not a shrug. Do not clear an agent because it "seems okay" — clear it
because its **effective access** is limited and you can point to the evidence.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **A duplicated or "v2" name is not a verdict.** An agent that looks like sprawl — a copy, a "v2" — might
   be a least-privilege, read-only bot grounded on an already-published, all-staff library. Inspect its
   connection: is the `connection_owner_upn` the same present, enabled person as the agent owner? Is it a
   plain delegated user connection with no group sharing? If its reach is limited to data everyone can
   already see, clear it — and write down why.
2. **A sandbox location is not a verdict.** Being in `Maker-Sandbox` makes an agent a **shadow candidate**
   (hunt 2 above). But candidate is not conviction. If the connection touches only the **maker's own**
   data (for example, the maker's own OneDrive notes), has no shared connection, and takes no action on
   anyone else's data, its blast radius is small. It is still worth recording as "discovered in a personal
   environment," but its risk is low — say so explicitly.
3. **Write the justification.** For every agent you clear, record one line: which join flagged it, what you
   checked, and why the effective access makes it acceptable. A cleared agent with a written reason is a
   finding; a cleared agent with no reason is an assumption waiting to bite you.
4. **Re-check the confident ones.** The mirror-image discipline: an agent that looks boring but has a
   service-account connection, a disabled connection owner, or a broad group share is **not** clean, no
   matter how ordinary its name. Let the joins, not the names, decide.

</details>

{: .caution }
> "Sandbox equals bad" and "duplicate equals sprawl" are pattern-matching, not analysis. They generate
> candidates; they do not close cases. The whole point of this hunt is to replace the vibe with a join you
> can show someone.

{: .note }
> A clean agent is a finding too. If you cannot justify *why* an agent is fine, it is not cleared yet — it
> is just un-reviewed.

## Summary

You ran five hunts — orphaned owner, shadow environment, test-became-prod, shared connection, and ambiguous
owner — and treated each result as a candidate to be confirmed, not a verdict. You separated the agent owner
from the connection owner wherever they diverged, and you did the harder half of the job: clearing the
agents that only look risky, with a written reason for each. Next you consolidate all of this into the
finished deliverable and set the flags.
