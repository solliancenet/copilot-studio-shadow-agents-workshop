# Task 02-03 — Hunt the problem estate

## Introduction

The findings are not written in any single file. They only show up when you **cross-reference** two files:
an agent whose owner has left, a connection owned by someone who left, an environment that is a sandbox
on paper but production in practice. This task teaches you the hunts — the specific cross-references that
turn a flat inventory into a risk picture. It also teaches the harder discipline: an agent that *looks*
risky is not a finding until you can show the two records that prove it, and an agent that looks scary can
be **clean** once you inspect its effective access.

## Description

You will run five targeted hunts against your CSVs and the live tenant, each looking for one problem
condition. Each hunt produces a **candidate list**, not a verdict. You then confirm every candidate with a
second data point, and — just as important — you deliberately try to **clear** the agents that only look
risky. You are building evidence, not vibes.

## Success Criteria

- [ ] You ran each of the five hunts and recorded the candidate agents each one surfaced.
- [ ] For every candidate you confirmed the condition with a second data point (not just the one column that flagged it).
- [ ] You distinguished the **agent owner** from the **connection owner** wherever they differ. (Whose credential actually acts on each call is Exercise 03's question.)
- [ ] You attempted to clear at least the agents that look risky on name or location alone, and wrote a one-line justification for each you cleared.
- [ ] You can explain why a sandbox location or a duplicated name is a **candidate**, not a **verdict**.
- [ ] You compared your hunt results and clearances with the suggested ones.

## Key Tasks

### 01: Run the five hunts

Each hunt is a lookup: take a value from one file, find the matching row in another, and check one column.
Run them against your inventory; write down which agents turn up. Do **not** assume the column that flagged
an agent is the whole story — confirm with the second data point noted in each hunt.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Orphaned — the owner is gone.** For each agent, take its `owner_upn`, find that person's row in
   your `users-export.csv`, and check `employee_leave_date` and `account_enabled`. Every agent whose owner
   has a leave date in the past, or shows `account_enabled` `FALSE`, is a candidate. An active, published
   agent whose owner has left has nobody accountable — and if the leaver's account is still **enabled**,
   nothing has cut off what they built either. In the tenant, the leave date isn't shown in the Microsoft
   Entra admin center: read it with the users query from
   [Task 01-01]({% link docs/01_the_agent_estate/01_01.md %}).
   *Confirm with the second data point:* check whether that agent still has a **live
   connection** — an orphan with a working connection is the dangerous kind. Rerun the connections call from [Task 01-01]({% link docs/01_the_agent_estate/01_01.md %})
   for the agent's environment and read each connection's `properties.statuses`:

   ```bash
   az rest --method get --url "https://api.powerapps.com/providers/Microsoft.PowerApps/scopes/admin/environments/<environment-id>/connections?api-version=2016-11-01" --resource https://service.powerapps.com/
   ```

   Without the tenant: check that `connections-export.csv` still lists a connection for the agent. The
   pack doesn't record whether a connection works, so a listed connection is your best evidence that it's
   live.
2. **Shadow — built in a personal/developer environment.** For each agent, find its `environment` in your
   `environments-export.csv` and read the `type`. Every agent in a **Developer** environment (individual
   maker) is a candidate. A Developer environment is a personal one, never a sanctioned place to run
   production agents. *Confirm with the second data point:* was IT ever meant to govern this environment?
   Check its `managed` and `maker_access` values; in the tenant, the Power Platform admin center's
   **Manage** → **Environments** shows whether it is managed (the environment's **…** menu offers **Edit
   Managed Environments** when it is). A developer/personal environment that everyone, or one person
   alone, can build in is a blind spot by design.
3. **Test-became-prod — the label lies.** Look up each agent's environment the same way, this time picking
   out **Sandbox** environments. Then look at the agent's own row: is `published` `Yes` and `status`
   `Active`, was it recently modified, and is it described as doing **real business work** (not
   experimentation)? A sandbox that is quietly carrying production load is a finding. *Confirm with the
   second data point:* check whether the same environment has **no DLP** (`dlp_policy` empty) — production
   work running with sandbox governance. In the tenant, confirm it in the Power Platform admin center under
   **Security** → **Data and privacy** → **Data policy**: the **Applied to** column shows the environments
   each policy covers.
4. **Shared connection — the agent may run as someone else.** For each connection an agent uses, gather
   three facts before you flag anything: its owner (`connection_owner_upn`), who it is shared with
   (`shared_with`), and how the tool that uses it authenticates. In the tenant, read the last one on the
   agent's **Tools** page in Copilot Studio: select the tool and read its credentials setting under
   **Details** → **Additional details**. **Maker-provided** means everyone who chats with the agent runs on
   the connection the maker set up; **End user** means each person uses their own. Without the tenant,
   `auth_type` records it: on a tool's row, every label in the pack (`User (delegated)`, `Service account`,
   `Runs as owner`, `API key in action config`, `Static bearer token`) means the call carries one fixed
   credential (a connection owner's, a flow owner's, or a key or token), never the chatting user's: the
   Maker-provided case. `User (delegated)` is the connection owner's delegated sign-in. A SharePoint
   knowledge source isn't a tool: it searches the site with no connection, so a pack row for it doesn't
   tell you whose access it reads with. Put them together to name the
   runtime actor: with **Maker-provided**
   credentials — or a service account, a flow owner, a key, or a token — the connection's identity, not
   the agent owner and not the person chatting, is who the agent acts as; with **End user**, it is the
   person chatting. Flag a candidate when the agent acts as the connection's identity and **any** of these
   is true: the connection owner is **not** the agent owner; it is a **service account**
   (`is_service_account` is `TRUE` in your `users-export.csv`); or its owner has **left** or is **disabled**.
   Separately, flag any connection `shared_with` a group: sharing lets that group's members use the
   connection themselves, which matters on its own — but it doesn't, by itself, mean the agent's users
   run as its owner. *Confirm with the second data point:* look up the connection owner in your
   `users-export.csv` to see exactly whose authority is in play.
5. **Unknown / ambiguous owner — nobody is personally accountable.** Look up each agent's `owner_upn` in
   your `users-export.csv` and check `is_shared_mailbox`. An agent whose owner shows `TRUE` (or whose
   "owner" is otherwise not a person) is a candidate. A shared mailbox as owner means an agent that
   everyone and no one owns. In the tenant, confirm it in the **Exchange admin center** at
   `https://admin.exchange.microsoft.com`: **Recipients** → **Mailboxes**, filtered to shared mailboxes.
   *Confirm with the second data point:* check what that agent is wired to — an ambiguously-owned agent
   with an external integration or a hard-coded credential is worse than one with none.

   Then run a second lookup. Find any agent whose owner is a live person but whose connection belongs to
   someone else, and that someone has left or is disabled. The owner can't account for authority that isn't
   theirs, and the person whose authority it is has left. So no one can account for what the agent does.
   This overlaps with hunt 4. That's fine: the same agent can take both flags.

</details>

### 02: Clear the ones that only look risky

Some agents will trip a hunt on **name or location alone** and turn out to be fine. Clearing them is real
security work: you owe a reason, not a shrug. Do not clear an agent because it "seems okay" — clear it
because its **effective access** is limited and you can point to the evidence.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **A name or a location is not a verdict.** An agent can trip a hunt on its name alone (a copy, a "v2")
   or its location alone (a personal or sandbox environment). Before you decide, check its effective
   access:
   - **Knowledge:** exactly what it grounds on — its **Knowledge** page in Copilot Studio.
   - **Tools and actions:** every tool, topic call and flow, and whether any of them writes or sends.
   - **Acting credential:** for each tool, whose credential the call carries.
   - **Audience:** who can chat with it.

   Without the tenant, the pack shows only the connection and its `auth_type`: record the rest as
   `Unknown`, naming the check (the agent's **Knowledge**, **Tools** and **Topics** pages in Copilot
   Studio, and its sharing), and leave it uncleared until that check is done.
2. **Clear it only if its reach fits its purpose.** If what it can read and do is proportionate to its
   stated purpose, and limited to data its users could already see, clear it. Still record where you
   found it (for example, "discovered in a personal environment"), and say explicitly that its risk is
   low.
3. **Write the justification.** For every agent you clear, record one line: which hunt flagged it, what you
   checked, and why the effective access makes it acceptable. A cleared agent with a written reason is a
   finding; a cleared agent with no reason is an assumption waiting to bite you.
4. **Re-check the confident ones.** The mirror-image discipline: an agent that looks boring but has a
   service-account connection, a departed or disabled connection owner, or a broad group share is **not** clean, no
   matter how ordinary its name. Let the records, not the names, decide.

</details>

they stay `Unknown` until you check those pages in Copilot Studio.

take none of the five flags, but nothing here clears them. Exercise 03 maps what they can reach.

</details>

{: .caution }
> "Sandbox equals bad" and "duplicate equals sprawl" are pattern-matching, not analysis. They generate
> candidates; they do not close cases. The whole point of this hunt is to replace the vibe with evidence
> you can show someone: the two rows that prove it.

{: .note }
> A clean agent is a finding too. If you cannot justify *why* an agent is fine, it is not cleared yet — it
> is just un-reviewed.

## Summary

You ran five hunts — orphaned owner, shadow environment, test-became-prod, shared connection, and ambiguous
owner — and treated each result as a candidate to be confirmed, not a verdict. You separated the agent owner
from the connection owner wherever they diverged, and you did the harder half of the job: clearing the
agents that only look risky, with a written reason for each. Next you consolidate all of this into the
finished deliverable and set the flags.
