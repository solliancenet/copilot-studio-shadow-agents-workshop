# Task 02-02 — Build the inventory

## Introduction

No single CSV tells the whole story. `agents-export.csv` gives you names and owners but not what they run
as; `connections-export.csv` gives you the connections but not whether a DLP policy governs them;
`users-export.csv` tells you whether an owner's account is even still enabled. The inventory you need lives
in the **joins** — and the discipline is to account for **every column for every agent, across all four
environments**, without skipping the sandbox and default environments where the interesting agents hide.

## Description

You will line up your five CSVs by their shared keys and use them to fill the
[Agent Estate Inventory]({% link worksheets/templates/01-agent-estate-inventory.md %}) — one row per agent —
then open each agent in Copilot Studio for what the CSVs can't tell you: its tools and its grounding.
Without the tenant, you record them as unknown — the pack doesn't hold them. Every agent in your
`agents-export.csv` gets a row, including the ones in `Claims-Test` and `Maker-Sandbox`. You are not
flagging problems yet (that is Task 02-03); you are producing a complete, corroborated record of what
exists and what each agent is wired to.

## Success Criteria

- [ ] Your inventory has exactly one row per agent in your estate, and every agent is present.
- [ ] All four environments are represented — you did not drop the sandbox or default-environment agents.
- [ ] Each row's **Identity** column names the agent's Entra identity.
- [ ] Each row's **Connections / Connectors / auth** columns cover every connection the agent uses, including agents that have **more than one**.
- [ ] Each row records the **owner** and whether that owner's account is enabled, service, or shared.
- [ ] Each row records the **environment type and whether DLP applies**.

## Key Tasks

### 01: Line up the exports

Your five CSVs share columns. Learn which columns match and lining them up becomes mechanical. The diagram
below shows how they connect; the agent name is the spine, and everything hangs off it.

```mermaid
graph LR
  A[agents-export.csv<br/>display_name · environment · owner_upn]
  I[agent-identities-export.csv<br/>agent · entra_identity · app_id]
  C[connections-export.csv<br/>used_by_agent · connector<br/>connection_owner_upn · auth_type]
  U[users-export.csv<br/>upn · account_enabled<br/>is_service_account · is_shared_mailbox]
  E[environments-export.csv<br/>environment · type · dlp_policy]

  A -- "display_name = agent" --> I
  A -- "display_name = used_by_agent" --> C
  A -- "owner_upn = upn" --> U
  A -- "environment = environment" --> E
  C -- "connection_owner_upn = upn" --> U
```

<!-- ![The five artifact-pack exports matched on agent name, owner UPN, and environment](../../media/ex02_t02_kt01_s01.png) -->

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Match by agent.** `agents-export.csv` `display_name` matches `agent-identities-export.csv` `agent` and
   `connections-export.csv` `used_by_agent`. This attaches each agent's Entra workload identity and its
   connection(s).
2. **Match by owner.** `agents-export.csv` `owner_upn` matches `users-export.csv` `upn`. This tells you
   whether the agent's owner account is `account_enabled`, and whether it is flagged
   `is_service_account` or `is_shared_mailbox`.
3. **Match the connection owner too — separately.** `connections-export.csv` `connection_owner_upn` also
   matches `users-export.csv` `upn`. **Do this lookup on its own**: the connection owner is often a
   different person from the agent owner, and their account status matters just as much.
4. **Match by environment.** `agents-export.csv` `environment` matches `environments-export.csv`
   `environment`. This tells you the environment `type`, whether it is `managed`, and whether a `dlp_policy`
   is applied.
5. **Watch for one-to-many.** An agent can use **more than one** connection, and each has its own owner —
   the `used_by_agent` column can list the same agent on multiple connection rows. Capture every
   connection; do not stop at the first match.

</details>

### 02: Fill every inventory column for every agent

Work down the agent list and complete the template row by row. Map each inventory column to its source so
nothing is left blank and nothing is invented. Every cell gets the observed value, `Not applicable`, or
`Unknown — follow up`, plus a note of where the value came from.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Agent, Environment, Owner, Status** — straight from your `agents-export.csv`
   (`display_name`, `environment`, `owner_upn`, `status`).
2. **Identity** — from your `agent-identities-export.csv` (`entra_identity`, and `app_id` if you want the
   exact principal). This is the workload identity Module 3 will teach you to enumerate.
3. **Connections / Connectors** — from your `connections-export.csv` (`connection_name`, `connector`).
   List all connections for the agent.
4. **Tools / actions** and **External systems** — open the agent in **Copilot Studio** at
   `https://copilotstudio.microsoft.com`: pick its environment in the environment switcher, then go to
   **Agents** → the agent.

   - On the **Tools** page, list the agent's tools. Select one to read, under
     **Details** → **Additional details**, whether it uses **End user** or **Maker-provided** credentials.
   - On the **Topics** page, look for HTTP request nodes and MCP calls. The **Tools** page doesn't show
     them.
   - For a cloud flow, open the **Power Platform admin center** and go to **Manage** → **Environments** →
     the environment → **Resources** → **Flows** → the flow → **Details**, which shows its connections and
     owners.

   Record the tools and external systems you find, with the connector and auth type (`auth_type`) as your
   evidence: an HTTP action reaches an external API; an MCP server exposes a set of tools; a Power Automate
   flow runs with its owner's authority.

   Without the tenant: the pack doesn't hold an agent's tools or topics. Record the connector and
   `auth_type` as what you know, and the tools and external systems as "Unknown — needs the agent's
   configuration".
5. **Grounding / data** — open the agent's **Knowledge** page in Copilot Studio and record each knowledge
   source it lists. Without the tenant, record "Unknown — needs the agent's Knowledge page": a SharePoint
   connection doesn't tell you which site or library the agent grounds on, or whether it grounds on it at
   all. Either way, you will sharpen "how much of it" in Module 3.
6. **Permissions (summary)** — a first-pass reading of reach: the connector, the `auth_type`, the
   `connection_owner_upn`, and whether the connection is `shared_with` a group. Keep it short; this is the
   seed for the access map, not the full analysis.
7. **Cover every environment.** Confirm you have rows for agents in `Halcourt (default)`, `Halcourt-Prod`,
   `Claims-Test`, **and** `Maker-Sandbox`. If your count of environments is fewer than four, you dropped
   one — the sandbox and default agents are the ones most often missed and most worth finding.

</details>

{: .tip }
> This is five files lined up on shared columns. A spreadsheet `XLOOKUP` (or `VLOOKUP`) on the columns
> above turns it into minutes of work and makes the one-to-many connection rows obvious.
> Keep the agent name as the column you match everything to.

{: .note }
> Record what you observe, not what you conclude. Resist the urge to write "orphaned" or "risky" in a cell
> yet — Task 02-03 is where the joins become findings. A clean record now makes the hunt honest.

## Summary

You joined your five CSVs on their shared keys — agent name, owner UPN, connection owner UPN, and
environment — and filled a complete inventory row for every agent across all four environments. Crucially,
you captured the **connection owner** as a separate fact from the agent owner, and you kept every connection
for agents wired to more than one. That complete record is the substrate for the next task, where the
joins start revealing which agents are actually a problem.
