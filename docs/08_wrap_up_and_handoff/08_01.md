## Key Tasks

### 01: Discovery & governance — know what you have and where it can be built

Feeds the **Agent Estate Inventory** (DISCOVER). The findings on the first day were mostly about places
nobody was looking — personal environments, a "test" environment doing production work, connections owned
by someone who left. These references are about seeing all of it and setting where agents are allowed to
be built at all.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. [Environments overview](https://learn.microsoft.com/power-platform/admin/environments-overview){:target="_blank"} — read this first: every agent lives in an environment, and the environments you are not watching are where shadow and orphan agents accumulate.
2. [Environment strategy](https://learn.microsoft.com/power-platform/guidance/adoption/environment-strategy){:target="_blank"} — how to structure environments so "test" does not quietly become production and personal envs are not a blind spot.
3. [Use connectors in Copilot Studio agents](https://learn.microsoft.com/microsoft-copilot-studio/advanced-connectors){:target="_blank"} — how connections carry the real authority; read it to understand why the *connection* owner matters as much as the agent owner.
4. [CoE Starter Kit](https://learn.microsoft.com/power-platform/guidance/coe/starter-kit){:target="_blank"} — the tooling that automates the tenant-wide inventory you did by hand, including orphaned-resource detection.

</details>

### 02: Identity & access — whose authority, and can it be constrained

Feeds the **Agent Access Map** (MAP). This is the heart of the day: an agent exercises *some* identity's
authority, and the risk is what that identity can reach — not what the user in the chat can. These
references cover scoping the acting identity and constraining where its token can be used.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. [Dataverse security roles & privileges](https://learn.microsoft.com/power-platform/admin/security-roles-privileges){:target="_blank"} — the mechanism for replacing a god-mode service account with a scoped role plus row-level security, which is the real fix for the excess-permission failure.
2. [Conditional Access overview](https://learn.microsoft.com/entra/identity/conditional-access/overview){:target="_blank"} — what CA does and does not govern; it is about authenticating principals, not authorizing what an agent does after sign-in.
3. [Conditional Access for workload identities](https://learn.microsoft.com/entra/identity/conditional-access/workload-identity){:target="_blank"} — the emerging path for constraining an agent's own Entra identity. Treat 2026 coverage of agent identities as something to **verify in your tenant**; it can only help where the target trusts Entra rather than a static key.

</details>

### 03: Data controls — classify and gate the data agents can reach

Feeds the **Control Efficacy Matrix** (CONTROL / RETEST). These controls act on the data itself: which
connectors an environment may use, and whether sensitive content is labeled so Copilot will withhold it.
They *close* the over-broad-grounding exfiltration case when the target file is labeled; they only *dent*
the semantic-injection case.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. [Power Platform data loss prevention](https://learn.microsoft.com/power-platform/admin/wp-data-loss-prevention){:target="_blank"} — the concept: DLP governs which connectors can be combined, not the content that flows through an allowed one.
2. [Create a DLP policy](https://learn.microsoft.com/power-platform/admin/create-dlp-policy){:target="_blank"} — the step-by-step for the policy you tested against the connector-heavy agents.
3. [Purview sensitivity labels](https://learn.microsoft.com/purview/sensitivity-labels){:target="_blank"} — labeling a sensitive file so Copilot honors the label and withholds it; the strong control in the exfiltration scenario. Confirm how far Purview labeling extends to Copilot Studio grounding **in your own tenant**, as this surface is still moving in 2026.
4. [Purview data loss prevention](https://learn.microsoft.com/purview/dlp-learn-about-dlp){:target="_blank"} — DLP on the data side, for blocking labeled or sensitive content on the paths where it applies.

</details>

### 04: Detection & audit — see it when it happens, reconstruct it after

Also feeds the **Control Efficacy Matrix** (CONTROL / RETEST). Detection never *closes* a failure — it
lets you find it and reconstruct it. Read these knowing the honest limit you found: when a shared or
service identity acts, the log names that identity as the actor, not who really asked.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. [Microsoft Defender for Cloud Apps](https://learn.microsoft.com/defender-cloud-apps/what-is-defender-for-cloud-apps){:target="_blank"} — behavioral detection that may flag anomalous exfiltration after the fact.
2. [Power Platform activity logging](https://learn.microsoft.com/power-platform/admin/logging-powerapps){:target="_blank"} — where agent and connector activity surfaces for the platform, and its granularity.
3. [Microsoft Purview audit](https://learn.microsoft.com/purview/audit-solutions-overview){:target="_blank"} — the tenant audit trail for reconstruction; read it with the attribution gap in mind, because it will show you *that* something happened more reliably than *who* caused it.

</details>

### 05: The injection & exfiltration concepts — OWASP LLM Top 10

Feeds the **Agent Threat Model** (BREAK). This is the vendor-neutral framing for the two hard cases the
day kept returning to: content that becomes instructions, and an agent that acts with more authority than
its user has.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. [OWASP Top 10 for LLM applications](https://genai.owasp.org/llm-top-10/){:target="_blank"} — read the whole list once for shared language with your security team.
2. Map what you saw to the list: **prompt injection** (untrusted grounding content becoming instructions, Scenario A), **sensitive information disclosure** (over-broad grounding leaking data, Scenario B), and **excessive agency** (an over-scoped tool or connector, Scenarios C and E). These are the OWASP names for the trust-boundary crossings you recorded in your threat model.

</details>

way you worked the estate. The discipline that carries the most weight after today is small: bookmark the

of it. The reading is only useful pointed at a specific failure in a specific estate — which is exactly
what your binder gives you.
