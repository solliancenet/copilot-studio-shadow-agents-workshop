# Task 04-06 — Lifecycle

## Introduction

Permissions and connections outlive the assumptions that created them. Someone builds an agent "just for
testing" and it quietly starts doing production work. An owner leaves the company and their account is
disabled — but the agent they built keeps running, and the connections they created keep working. The
survivor can still act, long after anyone is accountable for it. Lifecycle failures are the least dramatic
and among the most durable.

## Description

You will examine two survivors. **Onboarding Guide** (`cs-agent-onboarding-default`) was owned by **Tom
Dean**, whose account is now **disabled** — yet the agent is still published and still holds live SharePoint
and Office 365 Outlook (**send mail**) connections that Tom created. **Claims Copilot**
(`cs-agent-claims-copilot-test`) was built in the `Claims-Test` sandbox and quietly became a production tool,
carrying its shared service-account connection and broad role across a promotion no one reviewed.

You will **observe and record** that the survivor can still act. Do **not** actually send mail externally or
alter production data; confirming the capability exists is the finding.

## Success Criteria

- [ ] You confirmed Onboarding Guide's owner account status (**disabled**) while the agent remains published
      with live connections.
- [ ] You identified that its connections (SharePoint; Outlook **send mail**) still function despite the
      owner being gone.
- [ ] You identified **Claims Copilot** as a `Claims-Test` agent doing production work with a surviving
      shared connection.
- [ ] You explained *why* disabling the owner did not stop the agent.
- [ ] You wrote the **Scenario F** row in your [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}).

## Key Tasks

### 01: Trace ownership and status

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}), find **Onboarding Guide**:
   owner `tom.dean@halcourtmutual.onmicrosoft.com`, `status` = Active, `published` = Yes.
2. In [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}), find `tom.dean`:
   `account_enabled` = **FALSE**, `last_sign_in_utc` far in the past. The owner is gone; the agent is not.
3. Write the contradiction plainly: *an active, published agent owned by a disabled account.* That is an
   orphan.

</details>

### 02: Observe the survivor live (Onboarding Guide)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In Copilot Studio / the Power Platform admin center, confirm Onboarding Guide is still **published** and
   its connections are still **Connected** (not errored), despite the owner being disabled.
2. Confirm the agent still has an **Office 365 Outlook — send mail** capability through Tom's connection.
   You may verify the capability is present and enabled; **do not actually send external mail** from the
   training estate.
3. Record the finding: an unowned agent with a live mail-send connection persists and can still act. Nobody
   is accountable for it, and — as Module 2 established — it is the kind of agent nobody realizes exists.

> Disabling a user account does not retire what that user built. The agent and its connections are separate
> objects with their own lifecycle; unless someone deletes or reassigns them, they survive the person.
{: .important }

</details>

### 03: Walk it through offline (the joins)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. This is a **join across three CSVs** — no single file tells the story:
   - [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}): Onboarding Guide → owner
     `tom.dean`, published.
   - [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}): `tom.dean` →
     `account_enabled = FALSE`.
   - [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}): `SP-Onboarding`
     and `O365-Outlook-Onboarding` → owner `tom.dean`, still `used_by_agent` = Onboarding Guide.
2. Now do the **test-became-production** join for Claims Copilot:
   - [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}): `Claims-Test`
     is a **Sandbox**, `dlp_policy` empty, `managed` = No.
   - [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}): Claims Copilot lives in
     `Claims-Test`, is published, and has a recent `last_modified_utc` — a "test" agent under active,
     production-shaped use.
   - [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}): its
     `DV-Claims-Shared` service-account connection survived intact.
3. Conclude why the owner's departure changed nothing: **connections and agent identities are independent of
   the owner's account status.** No lifecycle process disabled them when Tom left, and no promotion gate
   re-reviewed Claims Copilot when its "test" env became real.

</details>

### 04: Record the threat-model row

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Fill the **Scenario F** row in [03 — Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}):
   - **Attack:** exploitation of a lifecycle gap — an orphaned agent, or a test agent doing production work.
   - **Asset:** the onboarding SharePoint content and mail-send capability (Onboarding Guide); all claims /
     customer PII (Claims Copilot).
   - **Trust boundary crossed:** the assumption "an owner exists and reviews this" no longer holds; the
     "test" label no longer matches real exposure.
   - **Impact:** an unowned agent with live mail-send persists indefinitely; a "test" agent carries broad
     production access with no owner review.
   - **Existing control:** record what exists today (any CoE / lifecycle policy? environment separation? or
     nothing?) and whether it caught these survivors.
2. Leave the **CLOSES IT / DENTS IT / MISSES IT** call for
   [Module 5]({% link docs/05_test_the_controls/05_test_the_controls.md %}); note that joiner-mover-leaver
   hygiene and CoE orphan detection are the likely real fixes.

</details>

## Summary

You found two survivors: an agent whose owner is gone but whose connections still send mail, and a "test"
agent quietly running production claims access. Neither required an attack — just time and the absence of a
lifecycle process. The offline joins made the failure undeniable without touching the tenant: an active
agent owned by a disabled account, and a sandbox environment doing production work. This is the other
*closable* class of problem — when identity lifecycle and CoE governance actually retire what people build,
these survivors disappear, which Module 5 will let you confirm.
