# Task 04-06 — Lifecycle

## Introduction

Permissions and connections outlive the assumptions that created them. Someone builds an agent "just for
testing" and it quietly starts doing production work. An owner leaves the company and their account is
disabled — but the agent they built may keep running, and the connections they created may keep working.
If they do, the survivor can still act, long after anyone is accountable for it. Lifecycle failures are the
least dramatic and among the most durable.

## Description

You will examine two lifecycle candidates. **Onboarding Guide** is owned by **Tom Dean**: you will check his
account's status, whether the agent is still published, and whether the Office 365 Outlook (**send mail**)
connection Tom created still works. **Claims Copilot** lives in the `Claims-Test` sandbox: you will check
whether there is evidence it is doing production work, and what it carries with it if so.

You will **observe and record** whether each survivor can still act. Do **not** actually send mail or alter
production data; confirming the capability exists is the finding.

## Success Criteria

- [ ] You checked Onboarding Guide's owner account status and whether the agent is still published.
- [ ] You checked whether its Outlook (**send mail**) connection is still healthy and the capability still
      present — without sending mail.
- [ ] You decided whether **Claims Copilot** is a production-use candidate or confirmed production use, and
      cited the evidence.
- [ ] You explained what disabling the owner did, and did not, stop.
- [ ] You wrote the **Scenario F** row in your [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %})
      and compared it with the suggested row.

## Key Tasks

### 01: Trace ownership and status

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Find **Onboarding Guide** in the Power Platform admin center under **Manage → Inventory** and note its
   **Owner**. In the Microsoft 365 admin center (`https://admin.microsoft.com`), under
   **Agents → All agents → Registry**, its **Details** tab shows its publish status. In your
   [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}), the same row shows its
   `status` and `published` values.
2. Look up Tom Dean in the Microsoft Entra admin center (`https://entra.microsoft.com`) under
   **Entra ID → Users**: the user's **Overview** shows whether the account is enabled and when it last
   signed in. In your [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}), read
   `tom.dean`'s `account_enabled` and `last_sign_in_utc`.
3. If you found an active, published agent owned by a disabled account, write the contradiction plainly.
   That is an orphan.
4. Now the second candidate, **Claims Copilot**, which lives in `Claims-Test`:
   - In the Power Platform admin center, under **Manage → Environments**, note `Claims-Test`'s type and
     whether it is managed: its **…** menu shows **Edit Managed Environments** when it is.
   - Under **Security → Data and privacy → Data policy**, read the **Applied to** column: does any policy
     cover `Claims-Test`?
   - In the registry, Claims Copilot's **Details** tab shows its publish status and when it was last
     updated.
   - In Copilot Studio, its **Settings → Connection Settings** shows the connection its tools use and that
     connection's status.

   Your [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}),
   [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and
   [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) hold the same
   facts. Published, recently modified, and in a sandbox with no data policy: those make Claims Copilot a
   **production-use candidate**, not proof. Note what evidence would confirm it — its actual audience,
   activity records, or real claims records being processed.

</details>

> Key Tasks 02 and 03 are two routes to the same result. If you can reach the tenant, do **02** and skip
> 03. If you can't, skip 02 and do **03**. Both continue at Key Task 04.
{: .note }

### 02: Observe the survivors live (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In Copilot Studio and the Power Platform admin center, check whether Onboarding Guide is still
   **published** and whether its connection shows **Connected** or an error.
2. Check whether the agent still has an **Office 365 Outlook — send mail** capability through Tom's
   connection. You may verify the capability is present and enabled; **do not actually send mail** from the
   training estate.
3. For Claims Copilot, look for evidence of production use: who it is shared with, whether its activity
   shows real use, and whether the records it reads are real claims. Record what you find, or record it as
   a candidate.
4. Record what you found: whether an agent with a disabled owner still has a working mail-send connection,
   and whether anyone is accountable for it. If no accountable owner can be found, it is also a candidate
   for the "Nobody realizes it exists" flag.

> Disabling a user account doesn't by itself retire what that user built. The agent and its connections are
> separate objects with their own lifecycle — check whether a connection still works after its owner is
> disabled, and if it does, nothing stops it until someone deletes or reassigns it.
{: .important }

</details>

### 03: Walk it through from the artifact pack (offline route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. This takes three CSVs — no single file tells the story:
   - [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}): Onboarding Guide → its
     owner, `status` and `published`.
   - [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}): the owner's
     `account_enabled`.
   - [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}):
     `O365-Outlook-Onboarding` → its owner and `used_by_agent`. The pack doesn't record whether a
     connection still works, so a listed connection is your best evidence that it's live.
2. Now the test-became-production candidate, Claims Copilot:
   - [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}):
     `Claims-Test`'s `type`, `dlp_policy` and `managed`.
   - [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}): Claims Copilot's
     environment, `published` and `last_modified_utc`.
   - [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}): its
     connection and `auth_type`.

   The pack can't show production use itself — the agent's audience, its activity, or what records it
   processes — so record Claims Copilot as a production-use candidate.

</details>

### 04: Record the threat-model row

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Fill the **Scenario F** row in [03 — Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %})
   from what you observed: Attack, Asset, Trust boundary crossed, Impact, Existing control. Then compare it
   with the suggested row below.
2. Carry this evidence into [Exercise 05]({% link docs/05_test_the_controls/05_test_the_controls.md %}) and
   test which controls prevent, reduce, detect, or leave it unchanged.

</details>

<details markdown="block">
<summary>Reveal the suggested Scenario F row</summary>

- **Attack:** exploitation of a lifecycle gap — an orphaned agent, or a test agent doing production work.
- **Asset:** the mail-send capability (Onboarding Guide); all claims / customer PII (Claims Copilot).
- **Trust boundary crossed:** the assumption "an owner exists and reviews this" no longer holds; the
  "test" label no longer matches real exposure.
- **Impact:** an unowned agent with live mail-send persists indefinitely; a "test" agent carries broad
  production access with no owner review.
- **Existing control:** record what exists today (any CoE / lifecycle policy? environment separation? or
  nothing?) and whether it caught these survivors.
- **Why the owner's departure changed nothing:** connections and agent identities don't follow the owner's
  account status. No lifecycle process disabled them when Tom left, and no promotion gate re-reviewed
  Claims Copilot when its "test" environment became real. The agent's Entra identity follows the agent, not
  the owner, so disabling the owner leaves it in place.
- **Likely fixes to test in Exercise 05:** joiner-mover-leaver hygiene, and orphan detection through the
  Agent 365 registry (plus the CoE Starter Kit).

</details>

## Summary

You examined two lifecycle candidates — an agent whose owner's account is disabled, and a "test" agent that
may be doing production work — and checked, rather than assumed, whether each can still act. Neither
failure needs an attack, just time and the absence of a lifecycle process. Whether you read it in the
tenant or from the artifact pack, the evidence sits in more than one place: the agent, its owner's account,
its connection, and its environment. Carry this evidence into Exercise 05 and test which controls prevent,
reduce, detect, or leave it unchanged.
