# Task 04-02 — Data exfiltration

## Introduction

An agent's data reach is the **union of everything its connection can read** — which is very often far
more than the person chatting with it can see. Exfiltration here is not breaking authentication and it is
not a clever hack. It is coaxing the agent to relay data it is entitled to read but *you* are not. The
agent becomes a **confused deputy** for reads: it has the keys to the whole archive and will fetch from
shelves you were never allowed to walk to.

## Description

Building directly on Scenario A, you will probe whether **Benefits Buddy** will surface information from the
`HR-Benefits` site that an ordinary employee has no rights to open — specifically the
leadership/compensation content that lives in a subfolder the agent's grounding includes. You will then do
the same reasoning for **Claims Copilot** and the Dataverse `Customer` table (PII: SSN, DOB), where the
agent's reach again exceeds the user's.

You will **observe reachability and record it.** You will **not** copy real sensitive values (compensation
figures, SSNs) into your notes — recording *that the data was reachable* is the finding; hoarding the data
would be the harm.

## Success Criteria

- [ ] You established the full read-scope of the agent's grounding/connection, and contrasted it with what
      the chatting user can open directly.
- [ ] You determined whether Benefits Buddy will surface content from a location the chatting user cannot

- [ ] You did the same reasoning for Claims Copilot / Dataverse `Customer` PII (agent reach vs. user reach).
- [ ] You recorded the **gap between agent data-reach and user data-reach** — without transcribing any real

- [ ] You wrote the **Scenario B** row in your [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}).

## Key Tasks

### 01: Establish agent reach vs. user reach

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For Benefits Buddy, restate the fact from Scenario A: grounding is the **whole** `HR-Benefits` site, and
   the connection reads as Marcus Webb (an HR maker) via delegated permissions.
2. Identify at least one location inside that site that an ordinary employee — say the Jordan Blake persona
   — cannot open directly. In the tenant, Benefits Buddy's **Knowledge** page in Copilot Studio shows the
   source and its scope. The grounding screenshot shows a leadership/compensation subfolder alongside the
   everyday enrollment documents.
3. Write down the asymmetry plainly: *the agent can read the leadership content; the employee asking cannot.*
   Exfiltration is the act of getting the agent to bridge that gap.
4. For **Claims Copilot**, find whose identity its Dataverse reads run as. In Copilot Studio, switch to the
   `Claims-Test` environment and open Claims Copilot. On its **Tools** page, each tool's **Details** →
   **Additional details** show whether it uses **End user** or **Maker-provided** credentials. Its
   **Settings → Connection Settings** lists the connection those tools use and its status.
   Its owner and who it's shared with are in the `DV-Claims-Shared` row of your
   [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) from
   [Task 01-01]({% link docs/01_the_agent_estate/01_01.md %}) (`connection_owner_upn`, `shared_with`). To
   re-check them in the tenant, rerun the connections and role-assignment calls from that task.
5. Reason about the PII parallel for Claims Copilot. The `DV-Claims-Shared` row shows Microsoft Dataverse,
   `auth_type` **Service account** (`svc-claims`), shared with the `Claims-Adjusters` group. The `Customer`
   table holds SSN and DOB, and the agent reads it through that service-account connection — so the
   agent's PII reach is the service account's reach, regardless of who is chatting. (You confirm the
   *scope* of that reach in Scenario C; here you only need that agent reach > user reach.)

## Summary

Exfiltration through an agent is an **access** problem wearing a language-model costume. The agent reads as
a broad identity — Marcus's delegated SharePoint reach, or the `svc-claims` service account — and any chat
user borrows that reach simply by asking. You demonstrated the gap between what the agent can read and what
the user can read, for both leadership compensation and customer PII, and you recorded reachability without
ever taking the data. The honest fix is to shrink the agent's reach to what the task needs; Module 5 will
put least-privilege grounding and Purview labeling to the test against this exact row.
