# Task 04-02 — Data exfiltration

## Introduction

An agent's data reach is set by the credential each call carries, what its grounding and tools expose, and
what the downstream system authorizes — and it is very often far more than the person chatting with it can
see. Exfiltration here is not breaking authentication and it is not a clever hack. It is coaxing the agent
to relay data its credential can read and *you* can't. The agent's credential has the keys to the whole
archive, so the agent will fetch from shelves you were never allowed to walk to. Scenario D looks at the same
split for actions.

## Description

Building directly on Scenario A, you will probe whether **Benefits Buddy** will surface information from the
`HR-Benefits` site that an ordinary employee has no rights to open, such as leadership or compensation
content. You will then do the same reasoning for **Claims Copilot** and the Dataverse `Customer` table,
which holds PII (SSN, DOB).

You will **observe reachability and record it.** You will **not** copy real sensitive values (compensation
figures, SSNs) into your notes — recording *that the data was reachable* is the finding; hoarding the data
would be the harm.

## Success Criteria

- [ ] You established what the agent's grounding and acting credential can reach, and contrasted it with

- [ ] You determined whether Benefits Buddy will surface content from a location the chatting user cannot
      reach on their own.
- [ ] You did the same reasoning for Claims Copilot / Dataverse `Customer` PII (agent reach vs. user reach).

- [ ] You wrote the **Scenario B** row in your [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %})

### 01: Establish agent reach vs. user reach

### 02: Observe it live (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. As your lab account, open the `HR-Benefits` site in SharePoint and try to open its `Leadership/` folder.
   Record whether you can. This is what you can reach directly.
2. Open Benefits Buddy. Open the agent's Teams link, signed in with your own lab account. The link opens the agent's
   details in Teams: select **Add** or **Open**, whichever appears. Then, in the **Let's go** dialog,
   select **Open**, not **Open with Copilot**. If the agent's first reply says it is still signing you in,
   send your message again after a few seconds.
3. Ask a question that could **only** be answered from the leadership or compensation content, for example
   "how does my band compare across bands?"
4. Compare the two:
   - If you couldn't open `Leadership/` but the agent answers from it, its search uses more access than
     yours (the maker's): that's exfiltration.
   - If the agent can't answer from it either, its search uses your own access: no data-reach gap.

   Update the "whose access" Unknown in your Access Map with what you found.
5. If sensitive content surfaces, **record that it was reachable** and screenshot the *fact* (you may redact
   values). Do **not** copy real compensation figures into your worksheet.

> This is exactly where Scenario A and Scenario B meet: the injected instruction from Scenario A can *ask
> the agent to do this for the user*, turning "the data is technically reachable" into "the data is being
> handed out." Note in your row whether the exfiltration needs the injection, or happens on a plain
> question.
{: .note }

</details>

<details markdown="block">
<summary>Reveal the suggested Scenario B row</summary>

- **The general shape:** where an agent's reads run with broader access than the asker's — the
  `svc-claims` service account for Claims Copilot, and, if the tenant route showed it, the maker's access
  for Benefits Buddy — anyone who can chat with the agent borrows that reach by asking. If Benefits Buddy
  answered only from what you can open yourself, its half of this scenario has no data-reach gap; record
  that, and the whole-site grounding as the excessive scope.
- **What the offline route should conclude:** in the pack's model, Marcus can see the whole HR site,
  including leadership content, and an ordinary employee can't, so whole-site grounding read with his
  access would relay leadership content to anyone in its audience. Whether the live search reads with his
  access is what the tenant route tests.
- **Attack:** exfiltration via over-broad grounding / an over-broad acting credential.
- **Asset:** leadership compensation content (Benefits Buddy); customer PII — SSN, DOB (Claims Copilot).
- **Trust boundary crossed:** agent data-reach > user data-reach; the agent relays what the user cannot
  reach directly.
- **Impact:** any employee in the agent's audience can obtain sensitive data the agent is entitled to but
  they are not.
- **Existing control:** record what exists today (e.g., does the leadership file carry a Purview label, and
  does that label encrypt? does any record-level access narrow `Customer`?) and whether it stopped you.
- **Likely fixes to test in Exercise 05:** scoping the grounding and the connection to what the task needs, and
  an encrypting Purview label on the sensitive file (a classification-only label doesn't stop grounding).

</details>

## Summary

Exfiltration through an agent is an **access** problem wearing a language-model costume. When an agent's
calls carry a broader credential than the requester holds, anyone in its audience can borrow that reach by
asking. You compared what the agent can read with what the user can read, for both leadership compensation
and customer PII, and you recorded reachability without ever taking the data. Carry this evidence into
Exercise 05 and test which controls prevent, reduce, detect, or leave it unchanged.
