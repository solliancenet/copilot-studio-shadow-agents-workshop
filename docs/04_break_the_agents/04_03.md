# Task 04-03 — Excessive connector & tool permissions

## Introduction

Over-permission is a **blast-radius multiplier**. An agent needs one operation; the connector or tool it
runs on grants many. Nothing looks wrong until something goes wrong — an injection (Scenario A), a confused
deputy (Scenario D), or just a curious user — and then the damage is bounded by *what was granted*, not by
*what was intended*. This scenario is about measuring that gap precisely, so that in Module 5 you can test
whether a control actually closes it.

## Description

You will examine two over-broad grants. **Claims Copilot** runs on a shared Dataverse connection whose
identity has far more than the job requires: the task is to read the requesting adjuster's *own* claims,
but the connection carries broad read/write across **all** `Claim` and `Customer` rows. **Underwriting
Assistant** needs quotes and risk scores, but its MCP server also advertises `run_query` — arbitrary
queries against the pricing database.

For each, you state the operation actually needed, enumerate what is actually granted, and record the
multiplier. **Observe and record only** — do not run destructive Dataverse writes or arbitrary MCP queries
beyond confirming the tool exists.

## Success Criteria

- [ ] You stated the single operation each agent actually needs.
- [ ] You enumerated what the connector/tool actually grants (the Dataverse role scope behind

- [ ] You quantified the gap for both — *need X; granted X + Y + Z*.
- [ ] You explained how this multiplies the impact of Scenarios A, D, and E.

## Key Tasks

### 01: Name the operation each agent actually needs

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For **Claims Copilot**, write the minimal operation from its purpose (adjuster helper for claim status):
   *read the status of claims assigned to the requesting adjuster,* plus a narrow *update status* on those
   same claims. Note what it does **not** need: read of `Customer` PII, or read/write across every other
   adjuster's claims.
2. For **Underwriting Assistant**, write the minimal operation: *get a quote* and *get a risk score* for a
   supplied risk. Note what it does **not** need: the ability to run arbitrary database queries.
3. Keep these "needed" statements next to you — the gap is the difference between them and what you find
   granted.

### 02: Enumerate the actual grant (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Claims Copilot / the connection.** Find whose identity Claims Copilot's Dataverse tools use. In
   Copilot Studio, each tool's **Details** → **Additional details** on the agent's **Tools** page show
   whether it uses **End user** or **Maker-provided** credentials. Read who owns the connection those
   tools use, and who it is shared with, from the `DV-Claims-Shared` row of your
   [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) from
   [Task 01-01]({% link docs/01_the_agent_estate/01_01.md %}) (`connection_owner_upn`, `shared_with`,
   `auth_type`). Then open the owner's account in the Microsoft Entra admin center
   (`https://entra.microsoft.com`) under **Entra ID → Users**: a person, or a service account? Your
   [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}) records it as
   `is_service_account`.
2. **Claims Copilot / Dataverse.** In the Power Platform admin center, open the `Claims-Test` environment,
   find the security role assigned to the `svc-claims` service account, and read its `Claim` and `Customer`
   table privileges (Create/Read/Write/Delete and the access level — User / Business Unit / Organization).
   Record whether it can read **all** rows and whether it has broad customization rights.
3. **Underwriting Assistant / MCP.** In Copilot Studio, open the agent and find where it calls the MCP
   server. Check **Topics** as well as **Tools**: an MCP call can be a node inside a topic, and in this
   estate that is where they are — a review that reads only the Tools page finds nothing. Record every MCP
   tool the agent's topics call — `get_quote`, `get_risk_score`, and any broader tool such as `run_query`.
   The **tool schema is the contract**: whatever the server advertises, the agent can be wired to call.
4. For each, write the granted scope beside the needed scope from Key Task 01.

### 03: Enumerate the actual grant from the artifact pack (offline route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Open [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}):
   - `DV-Claims-Shared` → Microsoft Dataverse, `auth_type` = **Service account**, `connection_owner_upn` =
     `svc-claims`, `shared_with` = `Claims-Adjusters`, used by **Claims Copilot**. A service-account
     connection **shared with a whole group** means every member inherits the service account's Dataverse
     scope through the agent.
   - `MCP-Underwriting` → MCP (custom), `auth_type` = **Static bearer token**, used by **Underwriting
     Assistant**. A single static credential fronts the whole tool surface.
2. Cross-check [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}): `svc-claims` is
   `is_service_account = TRUE`. Service accounts are frequently over-permissioned precisely because "it just
   needs to work" — treat that as a prompt to verify the role, not an excuse to trust it.
3. The CSVs tell you the **identity and sharing** shape. The MCP tool list is in the screenshot in Key
   Task 02. The pack doesn't carry the Dataverse role's scope: record the reasoned worst case and mark
   "confirm role scope, and whether row-level security narrows rows — verify in tenant." Then combine
   them: broad shared identity + wide tool surface = every chat user inherits the maximum grant, not the
   minimum need.

</details>

## Summary

You measured the distance between *need* and *grant* for two agents and found it large in both directions —
a Dataverse identity with god-mode over claims and customers, and an MCP tool surface that includes
arbitrary database queries. Over-permission is quiet until it is catastrophic: it sets the ceiling on every
other failure in this module. In Module 5 you'll test whether scoping the grant — a narrower Dataverse
role with row-level security, an MCP contract trimmed to `get_quote` / `get_risk_score` — closes the gap
or only dents it.
