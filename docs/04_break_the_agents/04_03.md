# Task 04-03 — Excessive connector & tool permissions

## Introduction

Over-permission is a **blast-radius multiplier**. An agent needs one operation; the connector or tool it
runs on grants many. Nothing looks wrong until something goes wrong — an injection (Scenario A), a confused
deputy (Scenario D), or just a curious user — and then the damage is bounded by *what was granted*, not by
*what was intended*. This scenario is about measuring that gap precisely, so you can say later that closing
it is one of the genuinely fixable problems.

## Description

You will examine two over-broad grants. **Claims Copilot** (`cs-agent-claims-copilot-test`) runs on a shared
Dataverse connection whose identity has far more than the job requires: the task is to read the requesting
adjuster's *own* claims, but the connection carries broad read/write across **all** `Claim` and `Customer`
rows. **Underwriting Assistant** (`cs-agent-underwriting-prod`) needs quotes and risk scores, but its MCP
server also advertises `run_query` — arbitrary queries against the pricing database.

For each, you state the operation actually needed, enumerate what is actually granted, and record the
multiplier. **Observe and record only** — do not run destructive Dataverse writes or arbitrary MCP queries
beyond confirming the tool exists.

### 01: Name the operation each agent actually needs

1. For **Claims Copilot**, write the minimal operation from its purpose (adjuster helper for claim status):

### 02: Enumerate the actual grant (live)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Claims Copilot / Dataverse.** In the Power Platform admin center, open the `Claims-Test` environment,
   find the security role assigned to the `svc-claims` service account, and read its `Claim` and `Customer`
   table privileges (Create/Read/Write/Delete and the access level — User / Business Unit / Organization).
   Record whether it can read **all** rows and whether it has broad customization rights.
2. **Underwriting Assistant / MCP.** In Copilot Studio, open the agent and find where it calls the MCP
   server. Check **Topics** as well as **Tools**: an MCP call can be a node inside a topic, and in this
   estate that is where they are — a review that reads only the Tools page finds nothing. Record every MCP
   tool the agent's topics call — `get_quote`, `get_risk_score`, and any broader tool such as `run_query`.
   The **tool schema is the contract**: whatever the server advertises, the agent can be wired to call.
3. For each, write the granted scope beside the needed scope from Key Task 01.

### 03: Walk it through offline (artifact pack)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Open [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}):
   - `DV-Claims-Shared` → Microsoft Dataverse, `auth_type` = **Service account**, `connection_owner` =
     `svc-claims`, `shared_with` = `Claims-Adjusters`, used by **Claims Copilot**. A service-account
     connection **shared with a whole group** means every member inherits the service account's Dataverse
     scope through the agent.
   - `MCP-Underwriting` → MCP (custom), `auth_type` = **Static bearer token**, used by **Underwriting
     Assistant**. A single static credential fronts the whole tool surface.
2. Cross-check [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}): `svc-claims` is
   `is_service_account = TRUE`. Service accounts are frequently over-permissioned precisely because "it just
   needs to work" — treat that as a prompt to verify the role, not an excuse to trust it.
3. The CSVs tell you the **identity and sharing** shape; the exact Dataverse role scope and the MCP tool
   list come from the tenant or the provided screenshot. Combine them: broad shared identity + wide tool
   surface = every chat user inherits the maximum grant, not the minimum need.

</details>

## Summary

You measured the distance between *need* and *grant* for two agents and found it large in both directions —
a Dataverse identity with god-mode over claims and customers, and an MCP tool surface that includes
arbitrary database queries. Over-permission is quiet until it is catastrophic: it sets the ceiling on every
other failure in this module. The good news, which Module 5 will confirm, is that this is one of the
*closable* problems — a scoped Dataverse role with row-level security, and an MCP contract trimmed to
`get_quote` / `get_risk_score`, actually remove the gap rather than just denting it.
