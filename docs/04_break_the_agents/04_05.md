# Task 04-05 — The HTTP / MCP / tool boundary

## Introduction

The moment an agent calls *out* — an HTTP action, an MCP server, any external tool — a new trust boundary
opens, and four questions decide whether it is safe: **what authentication, what authorization, what inputs
can cross, and what comes back?** A static API key or a shared bearer token quietly answers the first two in
the worst way: the agent authenticates as *the key*, not as the user, and there is no per-user
authorization at all.

## Description

You will interrogate two outbound boundaries. **Policy Lookup Bot** uses a Copilot Studio **HTTP action** — an
HTTP request made from one of its topics — to call the Policy API at an internal Azure Container Apps endpoint
(a safe, facilitator-controlled training host), with a **static API key held in the request's header
configuration**. **Underwriting Assistant** reaches its MCP server — a **Model Context Protocol** tool on its
**Tools** page — at another internal Azure Container Apps endpoint behind a **static shared bearer token**
held in its maker's connection. You will answer the four questions for each, trace how user input flows into
the request, and record where each credential lives: the API key in the agent's own configuration, visible to
anyone who can export the agent; the token in a connection that every chat uses.

You will **observe and record only.** Send at most one benign request, for the sample policy `POL-1001`. Do
**not** enumerate other customers' records, do not call broader endpoints, and **never copy the key or token
value** into your worksheet.

## Success Criteria

- [ ] For each integration, you answered the four boundary questions: authentication, authorization, inputs
      that cross, outputs that return.
- [ ] You identified the credential type and where it lives (an API key in the HTTP request's header, in
      the agent's topic; a static bearer token in the MCP tool's connection, used with the maker's
      credentials).
- [ ] You noted that a **solution export** exposes the API key to anyone who can export the agent —
      **without** recording its value — and that the bearer token, though not exported, is the same for
      every user.
- [ ] You wrote the **Scenario E** row plus the boundary Q&A in your
      [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}).

### 02: Inspect both boundaries (tenant route)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In Copilot Studio, open Policy Lookup Bot and find the **HTTP request** to the Policy API. It is not on
   the Tools page: it is a node inside one of the agent's **topics**. Read the request configuration.
   - **Authentication:** a static API key in the header configuration. Note that it is a **full-scope**
     key — the same key regardless of who is chatting.
   - **Authorization:** observe that there is **no per-user check** — the key is the only gate.
   - **Inputs:** where does the policy id in the request come from?
   - **Outputs:** a policy record.
2. Send **one** benign lookup to see the boundary behave: ask for policy `POL-1001`, a sample policy the
   training API holds for this purpose. Request no other id, and call no other endpoint.
3. Note that the key is present in the topic's request configuration and would travel with a **solution
   export**. Record *that it is exposed*; do not copy or transcribe the key.
4. In Copilot Studio, open Underwriting Assistant's MCP tool on its **Tools** page (you found it in Task
   04-03). Answer the four questions:
   - **Authentication:** a static, shared bearer token — the same token for every call. It sits in the
     connection behind the tool, and the tool's **Details** → **Additional details** say **Maker-provided
     credentials**, so every chat uses the maker's connection. You can't see the token, and the agent's
     export doesn't carry it; record *that it is one shared credential*.
   - **Authorization:** none per-user; the token is the gate.
   - **Inputs:** tool arguments defined by the MCP schema — and the schema is wide (recall `run_query` from
     Scenario C).
   - **Outputs:** more than a quote when a broad tool is called.

<details markdown="block">
<summary>Reveal the suggested Scenario E row</summary>

- **Attack:** abuse of a weak outbound boundary — static credential, no user authorization, unvalidated
  input; plus disclosure of the API key via solution export.
- **Asset:** policy and customer records via the Policy API; the pricing database via the MCP server; the
  API key and the bearer token themselves.
- **Trust boundary crossed:** agent → external API / MCP server; the credential is the only gate and user
  input flows straight through.
- **Impact:** broad policy/customer exposure, arbitrary pricing-DB access for every chat user through one
  shared token, and the API key exfiltrated by anyone who can export the agent.
- **Existing control:** record what exists (does DLP restrict custom connectors/HTTP actions in this
  environment? is the secret in a vault or in config?).
- **Likely fixes to test in Exercise 05:** per-user OAuth, scoped tokens, input validation, a vaulted secret.

</details>

## Summary

Two outbound boundaries, the same four questions, the same weak answers: the agent authenticates as a static
credential, no one checks the *user*, user input crosses the boundary, and the endpoints return more than
the task needs. The API key sits in exportable configuration; the bearer token sits in the maker's connection,
shared by every chat. You answered the four questions for both boundaries — in the agent's topic and on the
other's Tools page with at most one benign request, or from the artifact pack — without ever enumerating
records or lifting the key. Carry this evidence into Exercise 05 and
test which controls prevent, reduce, detect, or leave it unchanged.
