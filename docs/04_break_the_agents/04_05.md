# Task 04-05 — The HTTP / MCP / tool boundary

## Introduction

The moment an agent calls *out* — an HTTP action, an MCP server, any external tool — a new trust boundary
opens, and four questions decide whether it is safe: **what authentication, what authorization, what inputs
can cross, and what comes back?** A static API key or a shared bearer token quietly answers the first two in
the worst way: the agent authenticates as *the key*, not as the user, and there is no per-user
authorization at all.

## Description

You will check two agents that call outside services. **Policy Lookup Bot** calls a Policy API from one of
its topics, with a static API key in the request. **Underwriting Assistant** calls its MCP server with a
static bearer token held in its maker's connection. For each, answer the four questions and record where the
credential lives.

You will **observe and record only.** Send one request, for the sample policy `POL-1001`. Never copy the key
or token into your worksheet.

## Success Criteria

- [ ] For each integration, you answered the four boundary questions: authentication, authorization, inputs
      that cross, outputs that return.
- [ ] You identified the credential type and where it lives (an API key in the HTTP request's header, in
      the agent's topic; a static bearer token in the MCP tool's connection, used with the maker's
      credentials).
- [ ] You noted that the API key is readable by anyone who can open the agent — **without** recording its
      value — and that the bearer token is the same for every user.
- [ ] You wrote the **Scenario E** row plus the boundary Q&A in your
      [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}).

<details markdown="block">
<summary>Reveal the suggested Scenario E row</summary>

- **Attack:** abuse of a weak outbound boundary — static credential, no user authorization, unvalidated
  input; plus disclosure of the API key to anyone who can open the agent.
- **Asset:** policy and customer records via the Policy API; the pricing database via the MCP server; the
  API key and the bearer token themselves.
- **Trust boundary crossed:** agent → external API / MCP server; the credential is the only gate and user
  input flows straight through.
- **Impact:** **Observed:** a `POL-1001` lookup returns the full record — holder, type, premium, status — to
  anyone who asks. **Reasoned:** every chat user's lookups ride one key whose reach on the API you couldn't see (`Unknown`);
  every chat user can reach `run_query` on the pricing database through one shared token; anyone who can
  open the agent can read the key.
- **Existing control:** record what exists (does DLP restrict custom connectors/HTTP actions in this
  environment? is the secret in a vault or in config?).
- **Likely fixes to test in Exercise 05:** per-user OAuth, scoped tokens, input validation, a vaulted secret.

</details>

## Summary

Two outbound boundaries, the same four questions, the same weak answers: the agent authenticates as a static
credential, no one checks the *user*, user input crosses the boundary, and the endpoints return more than
the task needs. The API key sits in the agent's configuration; the bearer token sits in the maker's connection,
shared by every chat. You answered the four questions for both boundaries — in Policy Lookup Bot's topic and on
Underwriting Assistant's Tools page with at most one benign request, or from the artifact pack — without ever enumerating
records or lifting the key. Carry this evidence into Exercise 05 and
test which controls prevent, reduce, detect, or leave it unchanged.
