# Task 04-05 — The HTTP / MCP / tool boundary

## Introduction

The moment an agent calls *out* — an HTTP action, an MCP server, any external tool — a new trust boundary
opens, and four questions decide whether it is safe: **what authentication, what authorization, what inputs
can cross, and what comes back?** A static API key or a shared bearer token quietly answers the first two in
the worst way: the agent authenticates as *the key*, not as the user, and there is no per-user
authorization at all.

## Description

You will interrogate two outbound boundaries. **Policy Lookup Bot** (`cs-agent-policy-lookup-prod`) uses a
Copilot Studio **HTTP action** to call the Policy API at an internal Azure Container Apps endpoint (a safe,
facilitator-controlled training host), with
a **static API key held in the action's header configuration**. **Underwriting Assistant**
(`cs-agent-underwriting-prod`) reaches its MCP server at another internal Azure Container Apps endpoint
behind a **static shared bearer token**. You will answer the four questions for each, trace how user input
flows into the request, and record the **credential-in-configuration** exposure — the key is visible to
anyone who can export the agent.

You will **observe and record only.** Send at most one benign request with your own sample identifier. Do
**not** enumerate other customers' records, do not call broader endpoints, and **never copy the key value**
into your notes.

## Success Criteria

- [ ] For each integration, you answered the four boundary questions: authentication, authorization, inputs
      that cross, outputs that return.
- [ ] You identified the credential type and where it lives (API key in the HTTP action config; static
      bearer for the MCP server).
- [ ] You noted that a **solution export** exposes the key to anyone who can export the agent — **without**
      recording the key value itself.
- [ ] You identified that the `{id}` input is unvalidated and that other endpoints (`/policy/all`,
      `/customer/{id}`) exist beyond the intended `GET /policy/{id}`.
- [ ] You wrote the **Scenario E** row plus the boundary Q&A in your
      [Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}).

## Key Tasks

### 01: Frame the four questions

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Write the four questions at the top of your notes, one column each:
   - **Authentication** — how does the agent prove it may call this endpoint?
   - **Authorization** — is the *user* checked, or only the agent/key?
   - **Inputs** — what data crosses the boundary, and where does it come from?
   - **Outputs** — what comes back, and is it more than the task needs?
2. You will fill this grid twice — once for the HTTP action, once for the MCP server.

</details>

### 02: Inspect the HTTP action (Policy Lookup Bot)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In Copilot Studio, open Policy Lookup Bot and its **HTTP action** to the Policy API. Read the request
   configuration.
   - **Authentication:** a static API key in the header configuration. Note that it is a **full-scope**
     key — the same key regardless of who is chatting.
   - **Authorization:** observe that there is **no per-user check** — the key is the only gate.
   - **Inputs:** the path takes `{id}` **straight from user input**, with no validation.
   - **Outputs:** a policy record. Note that the API also exposes `GET /policy/all` and `GET /customer/{id}`
     beyond the intended `GET /policy/{id}`.
2. Send **one** benign lookup with your own sample policy id to see the boundary behave. Do **not** request
   another customer's id and do **not** call `/policy/all` or `/customer/{id}`.
3. Note that the key is present in the action configuration and would travel with a **solution export**.
   Record *that it is exposed*; do not copy or transcribe the key.

![Policy Lookup Bot HTTP action configuration with the API key value redacted](../../media/ex04_t05_kt02_s01.png)

> The key is a live full-scope credential in the training estate. Treat it like a production secret:
> looking is fine, copying it into your notes or a chat is not. The finding is "a secret sits in exportable
> configuration," not the secret itself.
{: .caution }

</details>

### 03: Inspect the MCP boundary, then walk it through offline

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In Copilot Studio, open Underwriting Assistant's MCP tools. Answer the four questions:
   - **Authentication:** a static, shared bearer token — the same token for every call.
   - **Authorization:** none per-user; the token is the gate.
   - **Inputs:** tool arguments defined by the MCP schema — and the schema is wide (recall `run_query` from
     Scenario C).
   - **Outputs:** more than a quote when a broad tool is called.
2. Offline, open [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}):
   - `HTTP-PolicyAPI` → HTTP action, `auth_type` = **API key in action config**, used by Policy Lookup Bot.
   - `MCP-Underwriting` → MCP (custom), `auth_type` = **Static bearer token**, used by Underwriting
     Assistant.
   Both rows say the same thing in one column: a **single static credential** is the only thing standing
   between the agent and the endpoint.
3. Combine the CSV with the config screenshot to state the failure without touching the tenant: static
   credential + no per-user authorization + unvalidated input + a secret that rides along on export.

</details>

### 04: Record the row and the four answers

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Fill the **Scenario E** row in [03 — Agent Threat Model]({% link worksheets/templates/03-agent-threat-model.md %}):
   - **Attack:** abuse of a weak outbound boundary — static credential, no user authorization, unvalidated
     input; plus credential disclosure via solution export.
   - **Asset:** policy and customer records via the Policy API; the pricing database via the MCP server; the
     API key itself.
   - **Trust boundary crossed:** agent → external API / MCP server; the credential is the only gate and user
     input flows straight through.
   - **Impact:** broad policy/customer exposure, arbitrary pricing-DB access, and key exfiltration to anyone
     who can export the agent.
   - **Existing control:** record what exists (does DLP restrict custom connectors/HTTP actions in this
     environment? is the secret in a vault or in config?).
2. Complete the worksheet's **E** prompt: *"What auth exists? What authorization? What inputs cross? What
   comes back?"* — one line for the HTTP action, one for the MCP server.
3. Leave the **CLOSES IT / DENTS IT / MISSES IT** verdict for
   [Module 5]({% link docs/05_test_the_controls/05_test_the_controls.md %}); note that the real fix lives on
   the integration (per-user OAuth, scoped tokens, input validation, a vaulted secret), not on a platform
   toggle.

</details>

## Summary

Two outbound boundaries, the same four questions, the same weak answers: the agent authenticates as a static
credential, no one checks the *user*, user input crosses unvalidated, and the endpoints return more than the
task needs — and in the HTTP case the credential itself is sitting in exportable configuration. You saw the
boundary behave with a single benign request and reconstructed the rest from the artifact pack, without ever
enumerating records or lifting the key. When Module 5 tests DLP, workload-identity Conditional Access, and
proper per-user auth against this row, keep the four-question grid in front of you — it is how you will tell
a real fix from a distraction.
