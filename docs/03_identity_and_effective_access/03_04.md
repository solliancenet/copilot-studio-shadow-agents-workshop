# Task 03-04 — Map three agents

## Introduction

Now you apply the whole chain. You will complete an Access Map for three agents, filling every layer from
the tenant (or from the filled-in artifact pack if you can't reach it), and answer the one question the map
exists for: **can this agent obtain data, or cause an action, that its intended users could not?** The three
agents are chosen because between them they cover three different kinds of path: a Dataverse connection, an
HTTP action, and SharePoint grounding.

## Description

Take **Claims Copilot**, **Policy Lookup Bot**, and **Benefits Buddy**. For each, copy a fresh block from
the Access Map template, fill the layer cells from the tenant, join the rows of your CSVs that support each
cell, then decide whether the agent exceeds its intended users and classify the gap. Draw your own
conclusions first, then compare each map with the suggested one after its Key Task. Where you can't
determine something, write `Unknown` in the cell and record, in the map's **Unknowns** section, the open
question, your risk hypothesis if it resolves broadly, and the evidence that would settle it. A map that
keeps facts and hypotheses apart is a legitimate, honest map.

## Success Criteria

- [ ] A completed **Agent Access Map** block for each of the three agents, with every layer row holding a
  value or `Unknown` (acting credential, user context, permission scopes, connector permissions,
  tool/action authorization, accessible data, untrusted input paths).
- [ ] For each agent you named the **intended users** and answered **"Can it exceed them?"** with a concrete
  *how* when the answer is yes.
- [ ] For each agent you recorded its **actual audience**, a representative requester, and that requester's
  direct entitlement (or `Unknown`) before deciding whether it exceeds its intended users.
- [ ] For each agent you marked the **type of gap** — excessive permission, confused deputy, both, or none —
  and justified it in one line.
- [ ] Every unknown has an open question, a risk hypothesis, and the evidence that would verify it — none is
  recorded as fact.
- [ ] You can state, for each agent, whether "who is asking" and "who is acting" are the same identity.
- [ ] You compared each map with the suggested one and noted where yours differed and why.

## Key Tasks

### 01: Map Claims Copilot

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Open the [Agent Access Map]({% link worksheets/templates/02-agent-access-map.md %}) template and copy a
   fresh per-agent block. Set **Agent = Claims Copilot** and read its `environment` from your
   `agents-export.csv`. Record its **Agent identity** from **Entra ID** → **Agents** → **Agent identities**,
   matched as in Task 01-02. Without the tenant: its `entra_identity` in `agent-identities-export.csv`.
2. **Acting credential + user context:** in Copilot Studio, open each tool on Claims Copilot's **Tools**
   page (`/actions`) and read, under **Details** → **Additional details**, whether it uses **End user** or
   **Maker-provided** credentials. Find that connection in your
   `connections-export.csv` and record its `connector`, `connection_owner_upn`, `auth_type`, and
   `shared_with`. State plainly whether the agent acts with the chatting user's credential or the
   connection's. Without the tenant: the row in `connections-export.csv` where
   `used_by_agent = Claims Copilot`.
3. **Permission scopes:** authorization on Dataverse is the **effective record access** of the account
   behind the acting credential — its security roles' privilege depth on `Claim` and `Customer`, plus
   anything that narrows records (ownership, business units, teams, sharing). Read it in **your own lab
   environment**, which carries a copy of the same account and role, and where you are the administrator:
   in the **Power Platform admin center**, go to **Manage** → **Environments** → your environment →
   **Settings** → **Users + permissions** → **Users**, open that account, and choose **Manage security roles** to see its
   roles. Open each role under **Security roles** and record what it grants on `Claim` and `Customer`, with
   its access level; record anything you can't see as `Unknown`. Without the tenant, the pack doesn't carry
   the role: record the role scope as `Unknown`, with the risk hypothesis "a role with organization-level
   read would reach every row" and the check "open the account's security roles by the admin center route
   above and read the access level each grants on `Claim` and `Customer`."
4. **Connector + tool authorization:** on Claims Copilot's **Tools** page in Copilot Studio, capture the
   operations wired up. Without the tenant, the pack doesn't list an agent's tools: record `Unknown`, with
   the open question "which operations do the tools call, and does any of them write?" and the check "open
   each tool on Claims Copilot's **Tools** page and read the operation it calls." Note whether any of them
   are writes — a write is *action authority*, not just read reach.
5. **Accessible data:** state what the acting credential can actually read/write through that connector,
   per step 3. If any of those tables holds personal data, note it explicitly as data at stake.
6. **Untrusted input paths:** the chat (for example, a claim id) is user-controlled input that flows into
   the Dataverse calls.
7. **Answer the question.** Intended users are claims adjusters. First establish the **actual audience** —
   who can chat with the agent — from its sharing settings in Copilot Studio; without the tenant, the pack
   doesn't record it, so mark it `Unknown`. Then take a representative **low-privilege requester** from
   that audience and establish what they can do directly. In the tenant, use your own lab account; without
   the tenant, take Jordan Blake. The Microsoft Entra admin center (**Entra ID** → **Users**) or
   `users-export.csv` tells you the account exists and is enabled, not what it can reach: for direct
   entitlement, check that account's own Dataverse security roles in the same environment, or record it as
   `Unknown`. If a requester in the audience can reach or change claims
   they could not touch directly, record *how*, and mark the gap type.

</details>

<summary>Reveal the suggested Claims Copilot map</summary>

**Agent:** Claims Copilot  **Environment:** `Claims-Test`

**Agent identity:** `cs-agent-claims-copilot-test`

| Acting credential | The shared Dataverse connection `DV-Claims-Shared`, owned by the service account `svc-claims` (`auth_type` = Service account). The agent acts as `svc-claims`, not as the chatting user. |
| User context | None. Nothing checks the requester's own Dataverse access. |
| Permission scopes | `svc-claims` holds a broad role: System Customizer, plus read and write on **all** `Claim` and `Customer` rows. Nothing in record-level access (ownership, business units, teams, sharing) narrows the records. The task needs only the requesting adjuster's own claims. |
| Connector permissions | Microsoft Dataverse, through a connection shared with `Claims-Adjusters`. |
| Tool / action authorization | `List rows` on `Claim` and `Customer`, and nothing that writes. The agent's reach is read-only even though `svc-claims`'s role could write: a tool added later would inherit that write authority. |
| Accessible data | Every claim and every customer record, read and write. `Customer` holds personal data (SSN, date of birth). |
| Untrusted input paths | The chat (a claim id or customer detail flows into the Dataverse calls), and the `Claims-Knowledge` grounding, which `Claims-Adjusters` can edit. |

| Who | Suggested value |
|---|---|
| Intended users | Claims adjusters. |
| Actual audience | Wider than the adjusters: every employee (`All-Employees`), including Jordan Blake. |
| Representative requester | Your own lab account in the tenant; Jordan Blake without it. |
| Requester's direct entitlement | Almost nothing. No access to claims or customer records of their own. |

- **Can it exceed its intended users?** Yes. Any employee can ask the agent for any claim or customer record,
  and change a claim's status. The calls run as `svc-claims`, whose role reaches every row, and nothing
  checks who is asking.
- **Type of gap:** Both. Excessive permission, because `svc-claims` reaches every row when the task needs one
  adjuster's claims. Confused deputy, because the agent uses that authority for requesters who lack it.
- **Unknowns the offline route should end with:** the role scope of `svc-claims` on `Claim` and `Customer`;
  which operations the tools call, and whether any writes; the actual audience; Jordan's direct
  entitlement. Each carries the hypothesis and check from the steps above.

</details>

### 02: Map Policy Lookup Bot

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Copy a fresh block. Set **Agent = Policy Lookup Bot**, environment from your `agents-export.csv`. Record
   its **Agent identity** from **Entra ID** → **Agents** → **Agent identities**, or from
   `agent-identities-export.csv` without the tenant. Look up its owner in the **Exchange admin center** at
   `https://admin.exchange.microsoft.com`, under **Recipients** → **Mailboxes** filtered to shared mailboxes.
   Without the tenant: find the owner's row in `users-export.csv` and check `is_shared_mailbox`. Record
   whether one accountable person stands behind the agent.
2. **Acting credential:** in Copilot Studio, open Policy Lookup Bot, go to **Topics**, and read the headers
   on the HTTP request node in the topic that calls the policy API, and record what the call authenticates
   with. If you find a credential, note that it's there, but don't copy its value into your map. Without
   the tenant: its row in `connections-export.csv`, `auth_type`. Record whose identity the policy API sees,
   and whether it's the same for every user.
3. **Permission scopes / tool authorization:** where is authorization decided for this path (Task 03-02)?
   The HTTP request node shows what the agent sends, not what the API lets that credential reach. Record
   whether anything checks the chatting user's own entitlement. Record the open question "what can this
   credential reach on the policy API?", with the check "read what the API's own authorization grants that
   credential — the API's configuration for the key, not the request node."
4. **Connector + accessible data:** the tool is a Copilot Studio HTTP action calling the policy endpoint.
   Accessible data = whatever that credential can reach: record it as `Unknown`, with your risk hypothesis
   and the evidence that would settle it.
5. **Untrusted input paths:** in the topic, find where the policy identifier in the call comes from. If it
   comes from the chat, note whether anything checks it against the asker's entitlement before the call
   goes out. Without the tenant, the pack doesn't show the topic: record `Unknown`, with the open question
   "where does the identifier come from, and is it checked?" and the check "open the topic in Policy Lookup
   Bot's **Topics** page and trace the variable that fills the identifier in the HTTP request node."
6. **Answer the question.** Intended users can look up policies they are entitled to. First record the
   actual audience (or `Unknown`). Use the same representative requester as in Key Task 01: your own lab
   account in the tenant, or Jordan Blake without it. Ask: given what you found about the credential and
   the input, can a user reach policies (or other records) beyond their own entitlement? Record *how* if
   yes, and mark the gap type. Add any second-order risk in a note — for example, who else could read a
   credential stored in the agent?

</details>

<details markdown="block">
<summary>Reveal the suggested Policy Lookup Bot map</summary>

**Agent:** Policy Lookup Bot  **Environment:** `Halcourt-Prod`

**Agent identity:** `cs-agent-policy-lookup-prod`

**Owner:** the IT Helpdesk shared mailbox (`is_shared_mailbox` = TRUE). No one person is accountable for the
agent.

| Layer | Suggested value |
|---|---|
| Acting credential | A static API key in the HTTP request node's header config (`HTTP-PolicyAPI`, `auth_type` = API key in action config). The policy API sees the key, and the same key for every user. |
| User context | None. Nothing checks the chatting user's own entitlement before the call goes out. |
| Permission scopes | Decided by the policy API, not the agent. The API is a facilitator-controlled training endpoint, so you can't inspect its authorization: keep this `Unknown` in your map. By the estate's design, the key is a single full-scope key: it reaches `/policy/{id}`, `/policy/all` and `/customer/{id}`. In a real estate, the check is the API owner's configuration for that key. |
| Connector permissions | No connector: a Copilot Studio HTTP action calling the policy endpoint. No connection identity stands behind it, only the key. |
| Tool / action authorization | The action calls `GET /policy/{id}`. The key itself authorizes more than that one call. |
| Accessible data | Any customer's policy. With the full-scope key, also every policy and customer records, which hold personal data. |
| Untrusted input paths | The chat. The `{id}` in the call comes straight from the user's message, and nothing validates it against the asker's entitlement. |

| Who | Suggested value |
|---|---|
| Intended users | People looking up policies they are entitled to. |
| Actual audience | Every employee (`All-Employees`), including Jordan Blake. |
| Representative requester | Your own lab account in the tenant; Jordan Blake without it. |
| Requester's direct entitlement | Almost nothing. They hold no credential for the policy API. |

- **Can it exceed its intended users?** Yes. A user can put another customer's policy id in the chat, and the
  agent fetches it with the key. The same key reaches every policy and customer records, so the input is a
  path toward those too.
- **Type of gap:** Both. Excessive permission, because a full-scope key backs a lookup that needs one
  policy. Confused deputy, because the key acts for every user and nothing checks the asker.
- **Second-order risk:** the key sits in the agent's configuration. Anyone who can view or export the agent
  can read it and call the API directly, outside the agent.
- **Unknowns the offline route should end with:** what the key can reach on the policy API (this stays
  `Unknown` with the tenant too); where the `{id}` comes from, and whether anything checks it; the actual
  audience; the requester's direct entitlement.

</details>

### 03: Map Benefits Buddy

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Copy a fresh block. Set **Agent = Benefits Buddy**, environment from your `agents-export.csv`. Record
   its **Agent identity** from **Entra ID** → **Agents** → **Agent identities**, or from
   `agent-identities-export.csv` without the tenant.
2. **Acting credential + user context:** find its connection in the connections call from Task 01-01 or
   your `connections-export.csv`, and record its `connector`,
   `connection_owner_upn` and `auth_type`. Then record the consequence (Task 03-01): whose permissions
   does the agent read with?
3. **Permission scopes / accessible data:** the agent's SharePoint reach equals the permissions of the
   account the knowledge source reads with on the grounded site, and depends on **how much of the site is
   grounded** (a scoped library vs. the whole site). In Copilot Studio, open Benefits Buddy's **Knowledge**
   page and record exactly what it grounds on. Site membership is still unknown: record it as `Unknown`,
   with the risk hypothesis "whole-site grounding would expose anything that account can read" and the
   check "read that account's access in the HR site's **Settings** → **Site permissions**." Without the
   tenant, the pack carries neither site membership nor the grounding scope. Record both as `Unknown`, with
   the open question "what can that account see on the HR site, and which folders are grounded?" and two
   checks: the HR site's **Site permissions** for that account, and Benefits Buddy's **Knowledge** page.
4. **Untrusted input paths:** list every place content enters the agent's reasoning. Remember that
   grounding content counts: documents the agent ingests as authoritative are an input path, not just data.
5. **Answer the question.** Intended users are employees asking benefits questions. First record the
   actual audience (or `Unknown`), and take the same representative requester as in Key Task 01. Ask the
   data-reach version of the key question: can the agent surface content from the grounded site that the
   **requesting employee** could not open directly? If the account the knowledge source reads with can read
   more of the site than the asker can, record *how* and mark the gap type. If the grounded scope is narrow
   and matches the asker's entitlement, there is no effective-access gap. Justify whichever way it falls.

</details>

| Connector permissions | SharePoint (Marcus's delegated connection) and Office 365 Users. No custom actions. |
| Tool / action authorization | Read only. No write tools and no custom actions. |
| Accessible data | The whole `HR-Benefits` site is grounded, not a scoped library. That includes `Leadership/`, which holds executive compensation bands. |
| Untrusted input paths | The chat, and every grounded document. `HR-Team` members can edit what the agent ingests as authoritative. Exercise 04 tests whether a document can steer it. |

| Who | Suggested value |
|---|---|
| Intended users | Employees asking benefits questions. |
| Actual audience | Every employee (`All-Employees`), including Jordan Blake. |
| Representative requester | Your own lab account in the tenant; Jordan Blake without it. |
| Requester's direct entitlement | A visitor (read) on `HR-Benefits` through `All-Employees`, but no access to `Leadership/`. |

- **Can it exceed its intended users?** Yes. An employee can ask about compensation, and the agent can
  surface content from `Leadership/`, which Marcus can read and the asker can't open.
- **Type of gap:** Excessive permission. Whole-site grounding on the maker's reach is wider than a benefits
  FAQ needs. If you marked Both, that's defensible: the three deputy conditions in the tip below hold for
  reads too.
- **Unknowns the offline route should end with:** what Marcus can see on the HR site; which folders are
  grounded; the actual audience; the requester's direct access to the site.

</details>

## Summary

You produced the Exercise 03 deliverable: an Access Map for three agents, every layer filled with a value or
`Unknown`, and every unknown carried as an open question with a hypothesis and a check rather than as fact.
Along the way you answered the question that drove the whole exercise — for each agent, can it obtain data
or cause an action its intended users could not — and you classified the gaps as excessive permission,
confused deputy, both, or none. Then you compared each map with the suggested one and noted where yours
differed and why. Carry these maps into Exercise 04: the agents where "who is acting" outruns "who is
asking" are exactly the ones you will break next.
