# Task 03-04 — Map three agents

## Introduction

Now you apply the whole chain. You will complete an Access Map for three agents, filling every layer from
the tenant (or from the filled-in artifact pack if you can't reach it), and answer the one question the map
exists for: **can this agent obtain data, or cause an action, that its intended users could not?** Three
agents are chosen because together they surface the two gaps that dominate agent estates — a service
account acting as a deputy, a static credential that is the whole authorization, and a grounded read wider
than the asker.

## Description

Take **Claims Copilot**, **Policy Lookup Bot**, and **Benefits Buddy**. For each, copy a fresh block from
the Access Map template, fill the seven layer cells from the tenant, join the rows of your CSVs that
support each cell, then decide whether the agent exceeds its intended users and classify the gap. You draw
the conclusions — this task hands you the joins and the questions, not the verdicts. Where you can't
determine a grant's depth, fill the cell with the reasoned worst case and a "verify in tenant" note; that
is a legitimate, honest map.

## Success Criteria

- [ ] A completed **Agent Access Map** block for each of the three agents, with all seven layer rows filled
  (acting identity, user context, permission scopes, connector permissions, tool/action authorization,
  accessible data, untrusted input paths).
- [ ] For each agent you named the **intended users** and answered **"Can it exceed them?"** with a concrete
  *how* when the answer is yes.
- [ ] For each agent you marked the **type of gap** — excessive permission, confused deputy, both, or none —
  and justified it in one line.
- [ ] Every cell you could not fully determine is marked as an explicit **open question to verify** (a
  role's breadth, a site's membership, a key's server-side scope), not left blank.
- [ ] You can state, for each agent, whether "who is asking" and "who is acting" are the same identity.

## Key Tasks

### 01: Map Claims Copilot

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Open the [Agent Access Map]({% link worksheets/templates/02-agent-access-map.md %}) template and copy a
   fresh per-agent block. Set **Agent = Claims Copilot** and read its `environment` from your
   `agents-export.csv`.
2. **Acting identity + user context:** in Copilot Studio, open Claims Copilot's **Settings** →
   **Connection Settings** to see the connection its tools run on, then open each tool on its **Tools**
   page and read, under **Details** → **Additional details**, whether it uses **End user** or
   **Maker-provided** credentials. Find that connection in your
   `connections-export.csv` and record its `connector`, `connection_owner_upn`, `auth_type`, and
   `shared_with`. State plainly whether the agent acts as the chatting user or as the connection's
   identity. Without the tenant: the row in `connections-export.csv` where
   `used_by_agent = Claims Copilot`.
3. **Permission scopes:** the acting identity's authorization on Dataverse is decided by its **security
   role** plus **row-level security** on `Claim` and `Customer`. In the **Power Platform admin center**, go
   to **Manage** → **Environments** → Claims Copilot's environment → **Settings** →
   **Users + permissions** → **Users**, open the acting identity, and choose **Manage security roles** to
   see its roles. Open each role under **Security roles** and record what it grants on `Claim` and
   `Customer`; mark anything you can't see, such as whether row-level security narrows rows, as an open
   question. Without the tenant, the pack does not carry the role's breadth, so record the reasoned worst
   case (a shared service account with a broad role reaches all rows) **and** mark "confirm role scope +
   whether any RLS narrows rows — verify in tenant."
4. **Connector + tool authorization:** on Claims Copilot's **Tools** page in Copilot Studio, capture the
   operations wired up. Without the tenant: row reads on `Claim`/`Customer` and a claim-status update. Note
   whether any of them are writes — a write is *action authority*, not just read reach.
5. **Accessible data:** state what the acting identity can actually read/write through that connector, per
   step 3. `Customer` holds PII — note that explicitly as data at stake.
6. **Untrusted input paths:** the chat (a claim id, a target status) is user-controlled input that flows
   into the Dataverse calls.
7. **Answer the question.** Intended users are claims adjusters. Compare the acting identity's reach to what
   a **low-privilege chat user** holds on their own — think Jordan Blake, enabled but personally entitled to
   almost nothing. Check his **Overview** in the Microsoft Entra admin center (**Entra ID** → **Users** →
   Jordan Blake); without the tenant, `users-export.csv`. If any chat user can reach or change
   claims they could not touch directly, record *how*, and mark the gap type.

</details>

### 02: Map Policy Lookup Bot

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Copy a fresh block. Set **Agent = Policy Lookup Bot**, environment from your `agents-export.csv`. Look
   for its owner in the **Exchange admin center** at `https://admin.exchange.microsoft.com`, under
   **Recipients** → **Mailboxes** filtered to shared: it is a **shared mailbox** — no single accountable
   person. Without the tenant: `users-export.csv`, `is_shared_mailbox = TRUE`.
2. **Acting identity:** in Copilot Studio, open Policy Lookup Bot, go to **Topics**, and read the headers
   on the HTTP request node in the topic that calls the policy API: the call carries a static **API key**.
   Note that the key is there; don't copy its value into your map. Without the tenant: its row in
   `connections-export.csv`, where the `auth_type` is **API key in action config**. Record that the agent
   authenticates to the policy API as the **key**, identically for every user — not as the chatting person.
3. **Permission scopes / tool authorization:** authorization is decided **on the API side** against that
   key. The HTTP request node shows what the agent sends, not what the key may reach, so record that there
   is **no per-user authorization**, and mark "enumerate what this key is scoped to reach on the API —
   verify against the API's own authorization" as an open question.
4. **Connector + accessible data:** the tool is a Copilot Studio HTTP action calling the policy endpoint.
   Accessible data = whatever that single key can reach; fill the reasoned worst case and the verify note.
5. **Untrusted input paths:** the policy identifier comes straight from the chat and the user controls it.
   Note that the input flows into the outbound call without a per-user entitlement check.
6. **Answer the question.** Intended users can look up policies they are entitled to. Ask: because the key is
   the only gate and the input is user-controlled, can a user reach policies (or other records) beyond their
   own entitlement? Record *how* if yes, and mark the gap type. Add the second-order risk in a note: anyone
   who can view or export the agent can read the key itself.

</details>

### 03: Map Benefits Buddy

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Copy a fresh block. Set **Agent = Benefits Buddy**, environment from your `agents-export.csv`.
2. **Acting identity + user context:** its connection in your `connections-export.csv` is a **SharePoint**
   connection with `auth_type = User (delegated)`, owned by the agent's maker. Record the crucial
   consequence: the agent reads SharePoint as the **connection owner**, with the owner's permissions —
   **not** as the chatting employee.
3. **Permission scopes / accessible data:** the agent's SharePoint reach equals the owner's permissions on
   the grounded site, and depends on **how much of the site is grounded** (a scoped library vs. the whole
   site, including any restricted subfolders). In Copilot Studio, open Benefits Buddy's **Knowledge** page
   and record exactly what it grounds on. Site membership is still an open question: record "determine
   what the owner can see on the HR site — verify in tenant", and reason about the worst case (whole-site
   grounding exposes anything the owner can read). Without the tenant, the pack carries neither site
   membership nor the grounding scope, so the open question is "determine what the owner can see on the HR
   site and exactly which folders are grounded — verify in tenant."
4. **Untrusted input paths:** two of them — the chat, **and the grounding content itself** (documents the
   agent ingests as authoritative). Note both; grounded content is an input path, not just data.
5. **Answer the question.** Intended users are employees asking benefits questions. Ask the data-reach
   version of the key question: can the agent surface content from the grounded site that the **requesting
   employee** could not open directly? If the acting identity (the owner) can read more of the site than the
   asker can, record *how* and mark the gap type. Contrast this with the estate's read-only, single-library
   HR FAQ decoy: same connector, but if the grounded scope is narrow and matches the asker's entitlement,
   there is no effective-access gap — justify whichever way it falls.

</details>

{: .note }
> This is an **analysis** exercise on the facilitator's intentionally-vulnerable training estate — you are
> mapping reach, not exploiting it. You will actually exercise these paths, safely and by observation, in
> Module 4. For now, the deliverable is an honest map: what each agent *could* reach, and whether that
> exceeds its users.

{: .tip }
> If the acting identity is a service account or a shared connection, you have almost certainly found a
> confused-deputy path — the agent exercises authority the requesting user does not personally hold. That
> single heuristic will pre-classify most of the estate; the map is where you prove it and size the reach.

## Summary

You produced the Module 3 deliverable: an Access Map for three agents, every layer filled, every gap you
could not fully size marked as an open question to verify rather than left blank. Along the way you
answered the question that drove the whole exercise — for each agent, can it obtain data or cause an
action its intended users could not — and you classified the gaps as excessive permission, confused
deputy, or clean. Carry these maps into Module 4: the agents where "who is acting" outruns "who is asking"
are exactly the ones you will break next.
