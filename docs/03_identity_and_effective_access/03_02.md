# Task 03-02 — What is it authorized to do?

## Introduction

Knowing *who* is acting (Task 03-01) is only half the picture. The other half is **authorization**: what
that actor is permitted to do — and, critically, **where that decision is actually made**. Authentication
proves the actor is who it claims. Authorization decides what it may then reach. For agents, the
authorization decision is scattered across five very different places, and each one has to be inspected on
its own terms. If you look in the wrong place, you will conclude an agent is safe when it is not.

## Description

You will take each downstream path an agent uses and locate the exact control surface where authorization
is decided for that path — a Dataverse security role and row-level security, a SharePoint permission, a
connector's granted scopes, an HTTP action's credential, or an MCP server's tool schema. You will separate
"authenticated" from "authorized," and you will flag every path where the authorization decision collapses
into a single shared credential (meaning there is no per-user check at all). The artifact pack tells you the
connector and auth type; the *depth* of each grant (a role's breadth, a site's membership, a key's
server-side scope) is what you either confirm in the tenant or record as an open question.

## Success Criteria

- [ ] For each path type — Dataverse, SharePoint/site grounding, connector scope, HTTP/API action, MCP tool
  — you wrote down **where** authorization is decided and **how** you would confirm it.
- [ ] You identified every path in the estate where authorization reduces to a **single shared credential**
  (service account, delegated owner, static API key, or static bearer) with no per-user authorization.
- [ ] For each Dataverse-backed agent you named the two authorization surfaces that matter — the acting
  identity's **security role** and **row-level security** on the table — and recorded whether you can
  determine them from the pack or must verify in the tenant.
- [ ] You distinguished a coarse, environment-level gate (DLP: *which connectors may be used*) from a
  fine-grained data grant (*what the connector may reach once used*), and noted that the first does not
  bound the second.

## Key Tasks

### 01: Map where authorization is decided, path by path

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, list its downstream paths (one per connection from Task 03-01). Then, for each path, fill
   in the authorization decision point using this map:

   | Path (connector) | Where authorization is actually decided | How to confirm |
   |---|---|---|
   | Dataverse | The **security role(s)** assigned to the acting identity **plus row-level security** on each table (`Claim`, `Customer`). A role with organization-wide read on a table ignores who asked. | Power Platform admin → Environment → Security roles for the acting identity; check table privileges and whether RLS/business units narrow rows. |
   | SharePoint / site grounding | The **permissions of the connection owner** on the site or library, and **how much of the site the agent grounds on** (whole site vs. a scoped library). The agent can read whatever the owner can. | SharePoint site permissions for the owner; the agent's grounding/knowledge configuration in Copilot Studio. |
   | Connector scope | The **delegated OAuth scopes** granted when the connection was created — the connector's own permission surface. | The connection's consented permissions; the connector reference in Copilot Studio. |
   | HTTP / API action | **Entirely on the API side**, against whatever credential the action sends. A single static, full-scope key means there is **no per-user authorization** — the key is the whole decision. | The action's header/credential config; the API's own authorization model and what that key is scoped to. |
   | MCP / tool | The **tool schema the server advertises** (which operations exist) plus the **server-side authorization** tied to the bearer token. A tool broader than the agent's need is an authorization gap in the contract. | Enumerate the MCP server's advertised tools; check what the shared token is permitted to invoke. |
   | Power Automate flow | The **flow owner's** permissions on the target system, exercised for anyone who triggers the flow. | The flow's connections and the owner's rights on the target. |

2. For each path, write the specific answer for the specific agent — not the generic row. For a
   Dataverse-backed agent, that means naming the acting identity and stating: *"authorization = whatever
   security role svc-claims holds on Claim/Customer, minus any row-level security — must confirm the role's
   breadth in the tenant."* The pack gives you the actor; the tenant gives you the grant's size.
3. Where the pack cannot tell you the depth of a grant, that is not a dead end — it is a documented
   **open question** ("role breadth unknown from export; verify in tenant"). An unknown grant is a finding.

</details>

### 02: Separate "authenticated" from "authorized"

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Go back through your path map and mark each path with one of two labels: **per-user authorization** (the
   requesting user's own entitlement is checked before the action runs) or **shared-credential
   authorization** (one identity's grant applies to everyone who can use the agent).
2. In this estate, look specifically at the service-account Dataverse connection, the "runs as owner" flow,
   the API-key HTTP action, and the static-bearer MCP connection. For each, ask: *does anything check what
   the person chatting is personally allowed to do?* If the only gate is the shared credential, write
   "no per-user authorization" against that path.
3. Note the difference in blast radius between the two labels. A shared-credential path grants **every**
   user of the agent whatever the credential holds. That is the mechanism you will exploit conceptually in
   Module 4 and try to close in Module 5.

</details>

{: .warning }
> When a path authenticates with a **static credential** — an API key in an action header, a shared bearer
> token, a service account — the credential *is* the authorization. There is no separate per-user check
> behind it. Anyone who can make the agent use that path inherits the credential's full reach, and anyone
> who can export or view the agent may be able to read the credential itself.

{: .note }
> DLP and environment policy are real controls, but they answer a **coarser** question than the one here:
> *which connectors may be used in this environment.* They do not bound what an allowed connector may reach
> once it is used. A Dataverse connector permitted by DLP can still carry an over-broad security role — the
> two decisions live in different places.

## Summary

You located the authorization decision point for every path an agent uses, and you learned that it is never
in one place: a Dataverse role and row-level security here, a SharePoint permission there, an API key on the
far side of an HTTP action, a tool schema on an MCP server. You separated authentication from authorization,
and you flagged the paths where authorization has collapsed into a single shared credential with no per-user
check. Identity (Task 03-01) plus authorization (this task) are the two inputs you now combine into
effective access.
