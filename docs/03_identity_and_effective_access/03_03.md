# Task 03-03 — Effective access

## Introduction

Identity and authorization are inputs. **Effective access** is the output — what an agent can actually
obtain or cause once every layer is combined. This is the number that matters to a security reviewer,
because an agent can look harmless at every individual layer and still be dangerous when the layers stack.
A benign-sounding purpose, a normal connector, a routine credential, an ordinary chat box — each fine on its
own — can compose into "any employee can read data they are not entitled to." This task gives you the
formula and teaches you to read the layers together, not the row.

## Description

You will learn the effective-access formula, walk it end to end for one agent to see how the layers
compound, and state the single question your Access Map has to answer. You are not filling maps yet — that
is Task 03-04. Here you build the reasoning move: refuse to judge an agent from any one layer, and instead
combine audience, acting credential, downstream authorization, exposed operations, reachable data, and user
input into one reachability statement.

## Success Criteria

- [ ] You can name the six layers of effective access and say what each contributes.
- [ ] You walked all six layers for at least one agent and produced a single plain-language reachability
  statement ("this agent can read/cause X for anyone who can chat with it").
- [ ] You can explain, with an example, why inspecting a single layer (owner, or connector, or purpose)
  misses the risk that only appears when the layers combine.
- [ ] You can state the key question the Access Map must answer, and why "who is asking" and "who is acting"
  are different questions.

## Key Tasks

### 01: Learn the formula and read the layers together

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Read the formula. Effective access is where six layers overlap:

   > **Effective access = who can invoke the agent, the credential it acts with, what that credential is
   > authorized to do, the operations its tools expose, and the data they reach — steered by user input and
   > grounding.**

   - **Audience** — who can invoke the agent at all (its sharing and channels).
   - **Acting credential** — whose authority each call carries (Task 03-01): the end user's, the maker's or
     connection owner's, a service account's, a flow owner's, or a static key or token.
   - **Downstream authorization** — what the downstream system lets that credential do, and where that is
     decided (Task 03-02).
   - **Exposed operations** — what the connector and tools actually let the agent do (read rows, update
     status, send mail, call an endpoint, invoke an MCP tool).
   - **Reachable data** — what can genuinely be read or written through those operations.
   - **User input and grounding** — what the chatting user can supply that flows into a call (a record id, a
     query string, free text that becomes a parameter), and the grounded content the agent treats as
     authoritative.

2. Read them together, not in sequence. The risk is rarely visible in any single layer; it emerges from the
   combination:

   ```mermaid
   flowchart LR
     AU["Audience<br/>(who can invoke it)"] --> E
     CR["Acting credential<br/>(whose authority)"] --> E
     AZ["Downstream authorization<br/>(what that credential may do)"] --> E
     OP["Exposed operations<br/>(connector + tools)"] --> E
     RD["Reachable data<br/>(what it truly reaches)"] --> E
     UI["User input &amp; grounding<br/>(what steers it)"] --> E
     E[["Effective access<br/>(what is actually reachable)"]]
   ```

3. Practice the reasoning move on a made-up agent first. It isn't in the Halcourt estate, so you won't
   get ahead of the maps you build in Task 03-04. Take a hypothetical **Order Status Bot**:
   - *Purpose:* look up an order by number. Sounds benign.
   - *Audience:* anyone who can open the chat.
   - *Acting credential:* its HTTP action sends a static API key, the same principal for every caller.
   - *Downstream authorization:* the API decides what that key may do; nothing checks the end user.
   - *Exposed operations:* a Copilot Studio HTTP action calling the orders endpoint.
   - *Reachable data:* whatever the key can reach on the API, which you would have to enumerate, not assume.
   - *User input:* the order number comes straight from the chat.
   - **Combine:** effective access = whatever that single key can reach on the API, steered by what the
     user types, on behalf of anyone who can open the chat. The "harmless lookup" is now a question
     about the API's entire authorization surface, and no single layer told you that.

</details>

### 02: State the question the map must answer

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Write the key question at the top of your Access Map, because every layer you fill is in service of it:

   > **Can this agent obtain data, or cause an action, that its intended users could not obtain or cause
   > themselves?**

2. Break it into the two comparisons that make it precise:
   - **Data reach:** is the *reachable data* behind the acting credential larger than the data the intended
     user is personally entitled to? (If yes, you have an exfiltration / over-broad-access path.)
   - **Action authority:** can the agent *cause* something — a write, an approval, an outbound mail, a state
     change — that the requesting user has no authority to perform themselves? (If yes, you have a
     confused-deputy path, where the user borrows the acting credential's authority.)
3. Keep "who is asking" and "who is acting" as separate columns in your head. When they differ, the gap
   between them is exactly the risk. An agent whose acting credential reaches no further than its
   least-privileged user has no effective-access gap, however scary it sounds; an agent whose acting
   credential reaches further is a finding, however dull it sounds.

</details>

{: .tip }
> An agent can *look* risky — a duplicate name, sensitive-sounding data, a personal sandbox — and be fine,
> and another can *look* dull and be the real exposure. Judge effective access, not vibes: fill the six
> layers and compare the acting credential's reach to the user's entitlement.

## Summary

Effective access is where audience, acting credential, downstream authorization, exposed operations,
reachable data, and user input overlap — and the danger lives in the combination, not in any single layer.
You learned to read the layers together instead of the row, walked it end to end for one agent, and fixed
the question the Access Map exists to answer: can the agent obtain or cause something its intended users
could not? Next, you answer that question for real, three times.
