# Task 03-03 — Effective access

## Introduction

Identity and authorization are inputs. **Effective access** is the output — what an agent can actually
obtain or cause once every layer is combined. This is the number that matters to a security reviewer,
because an agent can look harmless at every individual layer and still be dangerous when the layers stack.
A benign-sounding purpose, a normal connector, a routine credential, an ordinary chat box — each fine on its
own — can compose into "any employee can read data they are not entitled to." This task gives you the
formula and teaches you to read the stack, not the row.

## Description

You will learn the effective-access formula, walk it end to end for one agent to see how the layers
compound, and state the single question your Access Map has to answer. You are not filling maps yet — that
is Task 03-04. Here you build the reasoning move: refuse to judge an agent from any one layer, and instead
combine identity, permissions, connector, tool, accessible data, and user input into one reachability
statement.

## Success Criteria

- [ ] You can write the effective-access formula from memory and say what each of the six terms contributes.
- [ ] You walked all six layers for at least one agent and produced a single plain-language reachability
  statement ("this agent can read/cause X for anyone who can chat with it").
- [ ] You can explain, with an example, why inspecting a single layer (owner, or connector, or purpose)
  misses the risk that only appears when the layers combine.
- [ ] You can state the key question the Access Map must answer, and why "who is asking" and "who is acting"
  are different questions.

## Key Tasks

### 01: Learn the formula and read the stack

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Commit the formula. Effective access is the composition of six layers:

   > **Effective access = identity + permissions + connector + tool + accessible data + user input**

   - **Identity** — who actually acts (Task 03-01): agent identity, delegated owner, service account, or a
     static credential.
   - **Permissions** — what that identity is authorized to do, and where that is decided (Task 03-02).
   - **Connector** — the pipe to the downstream system, and the operations it exposes.
   - **Tool / action** — the specific capability wired up (read rows, update status, send mail, call an
     endpoint, invoke an MCP tool).
   - **Accessible data** — what the identity can genuinely read or write through that connector and tool.
   - **User input** — what the chatting user can supply that flows into the call (a record id, a query
     string, free text that becomes a parameter).

2. Read them as a stack, bottom to top. The risk is rarely visible in any single layer; it emerges from the
   product:

   ```mermaid
   flowchart TB
     I["Identity<br/>(who acts)"] --> P["Permissions<br/>(what it may do)"]
     P --> C["Connector<br/>(the pipe)"]
     C --> T["Tool / action<br/>(the capability)"]
     T --> D["Accessible data<br/>(what it truly reaches)"]
     D --> UI["User input<br/>(what the asker controls)"]
     UI --> E[["Effective access<br/>(what is actually reachable)"]]
   ```

3. Practice the reasoning move on one agent — take **Policy Lookup Bot** as a worked example of "harmless
   until combined." Layer it up:
   - *Purpose:* look up a policy by id. Sounds benign.
   - *Identity:* the HTTP action authenticates with a **static API key** — the same identity for every user
     (from `connections-export.csv`, `auth_type = API key in action config`).
   - *Permissions:* there is no per-user check; authorization is whatever that key is scoped to on the API
     side.
   - *Connector + tool:* a Copilot Studio HTTP action calling the policy endpoint.
   - *Accessible data:* **whatever the key can reach on the API** — which you must enumerate, not assume.
   - *User input:* the policy id comes straight from the chat, and the user controls it.
   - **Combine:** effective access = whatever that single key can reach on the API, steered by raw,
     unvalidated user input, on behalf of anyone who can open the chat. Now the "harmless lookup" is a
     question about the API's entire authorization surface — and no single layer told you that.

</details>

### 02: State the question the map must answer

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Write the key question at the top of your Access Map, because every layer you fill is in service of it:

   > **Can this agent obtain data, or cause an action, that its intended users could not obtain or cause
   > themselves?**

2. Break it into the two comparisons that make it precise:
   - **Data reach:** is the *accessible data* of the acting identity larger than the data the intended user
     is personally entitled to? (If yes, you have an exfiltration / over-broad-access path.)
   - **Action authority:** can the agent *cause* something — a write, an approval, an outbound mail, a state
     change — that the requesting user has no authority to perform themselves? (If yes, you have a
     confused-deputy path, where the user borrows the acting identity's authority.)
3. Keep "who is asking" and "who is acting" as separate columns in your head. When they differ — and in this
   estate they almost always differ — the gap between them is exactly the risk. An agent whose acting
   identity reaches no further than its least-privileged user has no effective-access gap, however scary it
   sounds; an agent whose acting identity reaches further is a finding, however dull it sounds.

</details>

{: .tip }
> This is why the two decoys in the estate matter. An agent can *look* risky (a duplicate "v2", HR data, a
> personal sandbox) and be fine, and another can *look* dull and be the real exposure. Judge effective
> access, not vibes: fill the six layers and compare the acting identity's reach to the user's entitlement.

## Summary

Effective access is the composition of identity, permissions, connector, tool, accessible data, and user
input — and the danger lives in the combination, not in any single layer. You learned to read the stack
instead of the row, walked it end to end for one agent, and fixed the question the Access Map exists to
answer: can the agent obtain or cause something its intended users could not? Next, you answer that question
for real, three times.
