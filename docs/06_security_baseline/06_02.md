# Task 06-02 — CONTROL IT: environment, DLP, identity, authorization, data

## Introduction

SCOPE IT shrank what each agent *is*. CONTROL IT surrounds it with the platform's guardrails: the right
environment with a DLP policy, authorization that checks the **requesting user** instead of a shared
identity, sensitivity labels on the data it can reach, and Conditional Access where it applies. Your
Exercise 05 matrix says which of these closed a failure and which only dented one; CONTROL IT turns that
into requirements and documented residual risk.

## Description

Take your Exercise 05 **Control Efficacy Matrix** and turn its verdicts into the four CONTROL IT criteria:
governed environment with DLP, authorization against the requesting user, data protection (labels and
Purview), and Conditional Access applicability. Decide, per criterion, what the control actually addresses
— and where you must layer a second control because the first only dents the failure. Each key task gives
the tenant route and, where it differs, the offline route through the artifact pack.

## Success Criteria

- [ ] Each agent doing real work lives in an environment with an **appropriate DLP policy** — not the
      default environment, and not a "sandbox" that quietly became production.
- [ ] Authorization is enforced against the **requesting user**, not a shared/owner/service identity,
      wherever the agent takes a consequential action or reads sensitive data.
- [ ] **Sensitivity labels / Purview:** you verified **protection**, not just classification — the label
      applied, whether it encrypts and who holds VIEW and EXTRACT, any DLP policy keyed on it, and what
      the retest showed.
- [ ] **Conditional Access:** for each path, a recorded **applicability determination** — which principal
      requests the token, whether the call uses an Entra token, which channel the agent runs in, and
      which policy can apply.

## Key Tasks

### 01: Place the agent in a governed environment with DLP

<!-- ![The DLP policy view in the Power Platform admin center — confirm the environment an agent lives in is actually covered, not just named "prod".](../../media/ex06_t02_kt01_s01.png) -->

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the Power Platform admin center, open **Security → Data and privacy → Data policy**.
2. Read the **Applied to** column:
   a. list the environments each DLP policy covers;
   b. list the environments with no policy.
3. For each agent doing real work, note whether its environment has a DLP policy that matches the
   **Data sensitivity** column of your [Exercise 02 inventory]({% link worksheets/templates/01-agent-estate-inventory.md %}).
4. Mark any agent in an uncovered environment, or in the default environment, as a CONTROL IT fail.
5. Write the CONTROL IT rule: an agent lives in an environment whose DLP matches its inventoried data
   sensitivity, and the default environment is disallowed for sensitive agents.

Without the tenant: read the `dlp_policy` column of
[`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}); an empty cell
means no policy.

</details>

{: .note }
> "Test" is a label, not a category of exposure. A sandbox used for production work needs production-grade
> DLP, or the agent moves to a managed production environment.

### 02: Enforce authorization against the requesting user

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. List every agent that takes a consequential action (writes, approvals, sends) or reads sensitive data.
2. For each, note how authorization is decided:
   a. the agent acts in the user's delegated context; or
   b. the agent checks the user's permission before a shared credential acts; or
   c. neither.
3. For each acting credential that is a service account or a connection someone else owns (flagged in OWN
   IT and SCOPE IT), record what your Exercise 05 matrix says about this failure: does least privilege
   alone change whose credential acts?
4. Write the CONTROL IT rule: authorization is enforced against the requesting user, not a shared identity,
   for any agent that can change state or read PII.

Without the tenant: use the acting credentials you recorded from
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) in SCOPE IT.

</details>

{: .note }
> When an agent acts as a shared connection or service account, it exercises authority the requesting user
> doesn't hold. Neither DLP nor Conditional Access changes whose credential acts.

### 03: Verify data protection

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent handling PII or compensation data (the **Data sensitivity** column of your
   [Exercise 02 inventory]({% link worksheets/templates/01-agent-estate-inventory.md %})), identify the
   sensitivity label on the content it reaches.
2. In the Microsoft Purview portal, open **Information Protection → Sensitivity labels**, select the label
   and note:
   a. whether it encrypts;
   b. who holds VIEW and EXTRACT rights.
3. Check whether any Purview DLP policy is keyed on the label.
4. Record what the Exercise 05 retest showed.

</details>

{: .note }
> Copilot Studio can't ground on a file protected by an encrypting label, even for users who can open it; a
> classification-only label doesn't stop grounding.

### 04: Determine Conditional Access applicability

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each path an agent uses, note:
   a. which principal requests the token — the user, a service account, or the agent's Agent ID;
   b. whether the call uses an Entra token at all;
   c. which channel the agent runs in;
   d. which Conditional Access policy can apply.
2. Record the applicability determination for each path.

Without the tenant: use the acting credentials and auth types from
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}).

</details>

{: .note }
> Conditional Access on an agent's Entra Agent ID is enforced at runtime only when the agent runs in
> Microsoft Teams; other channels use the existing connector authentication flow. Custom connectors, MCP
> servers and REST API tools add no API permissions to the Agent ID.

{: .note }
> Static API keys and bearer tokens never involve Entra Conditional Access for the downstream call.
> `svc-claims` is an Entra user, so user-targeted Conditional Access can govern its sign-in and token
> refresh. Conditional Access for agents requires a Microsoft Agent 365 license (or E7).

### 05: Layer the dented failures

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. List each failure your matrix marked as only dented.
2. For each, name the combination of controls that together raises the bar (for example, scoped grounding
   **plus** an encrypting label).
3. Write the CONTROL IT rule so the layering and any documented residual risk are explicit.

</details>

## Summary

CONTROL IT wraps each scoped agent in platform guardrails: a governed environment with DLP sized to the
data, authorization that checks the requesting user rather than a shared identity, verified data protection
on reachable content, and a recorded Conditional Access applicability determination for each path. Your
Exercise 05 verdicts decided which controls are requirements and which need a documented residual-risk
decision, and you layered deliberately where one control is not enough. What no control here fully
guarantees is that you would *notice* a failure in flight, or that the agent will not outlive its owner.
That is [WATCH IT]({% link docs/06_security_baseline/06_03.md %}).
