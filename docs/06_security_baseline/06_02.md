# Task 06-02 — OWN IT: owners and accountability

## Introduction

"Owner" is doing too much work as a single field. An agent needs someone accountable for *what it is for*
(the business owner), someone accountable for *how it is built and connected* (the technical owner), and
someone accountable for *the risk it carries* (security). And there is a second, quieter owner the agent
UI does not show you: the **connection owner** — the identity the agent actually acts as. When you ask
"whose authority is this agent exercising?", the honest answer is usually the connection owner's, not the
name printed on the agent.

## Description

Split the single "owner" into three accountable roles, then verify two things the platform will not
verify for you: that owner accounts are **live and appropriate**, and that the **connection** behind each
agent is owned by someone enabled and known. Use the Halcourt estate to find where those checks fail,
then write the OWN IT rules so they catch the same failures anywhere.

**Tenant path.** Agent owners are in the Power Platform admin center (**Manage → Inventory**, filtered to
Copilot Studio agents). Account status and last sign-in are in the Microsoft Entra admin center
(**Entra ID → Users**), and shared mailboxes in the Exchange admin center (**Recipients → Mailboxes**,
filtered to shared). Connection owners and sharing come from `az rest` (step 03 below), and how each tool
authenticates from the agent itself in Copilot Studio. No single surface shows the findings; they live in
the joins between them. Your own three CSVs hold what you gathered from these surfaces earlier.

**Offline path.** Join three files from the [artifact pack]({% link worksheets/index.md %}#the-artifact-pack):
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) (agent owner),
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) (connection owner,
sharing, auth type), and [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %})
(enabled/disabled, last sign-in, service/shared). The findings live in the joins, not in any single file.

## Success Criteria

- [ ] Every agent has a named **business owner**, **technical owner**, and **security accountability**
      (they may be the same person for small agents, but each role is named).
- [ ] Every agent owner is an **enabled** account — not a disabled/departed user, not (unreviewed) a
      shared mailbox or service account with no human behind it.
- [ ] Every **connection** an agent uses is traced to its owner, and that owner is enabled and known.
- [ ] The OWN IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      requires connection ownership to be verified, not just agent ownership.

## Key Tasks

### 01: Separate the three ownership roles

One name in an "owner" field is not accountability — it is a place to point after an incident. Name the
three roles so responsibility is unambiguous before anything goes wrong.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, record a **business owner** (accountable for the agent's purpose and continued need),
   a **technical owner** (maintains the configuration, connectors, and connections), and a **security
   accountability** (signs off that the residual risk is acceptable).
2. For a small maker-built agent these may be one person — that is allowed, but the person must knowingly
   hold all three roles. The failure to avoid is *no one* holding the security role.
3. Write the OWN IT rule so all three roles are named at registration time, and so "the maker who built
   it" is never assumed to be the security-accountable party by default.

</details>

### 02: Verify owner accounts are live and appropriate

The platform will happily keep an agent published under an owner who has left the company. Your job is to
catch the accounts the org offboarded but the agent estate did not.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Take each agent's owner — the **Owner** column in the Power Platform admin center's
   **Manage → Inventory** — and check the account in the **Microsoft Entra admin center**: under
   **Entra ID → Users**, the user's **Overview** shows whether it is enabled. To check every account at
   once, run this in [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer){:target="_blank"}:

   ```http
   GET https://graph.microsoft.com/v1.0/users?$select=userPrincipalName,displayName,accountEnabled,signInActivity
   ```

   Offline, join each agent's `owner_upn` from
   [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) to
   [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}). Flag any owner whose account
   is disabled (`account_enabled` is `FALSE`) — a disabled account owning a live, published agent is an
   orphan waiting to be found.
2. Flag owners that are **shared mailboxes** — the **Exchange admin center** lists them under
   **Recipients → Mailboxes**, filtered to shared — or **service accounts**, which no tenant field marks,
   so judge from the account's name and what it is used for. Offline, `users-export.csv` flags both
   (`is_shared_mailbox = TRUE`, `is_service_account = TRUE`). These are not "wrong" automatically, but a
   shared mailbox as owner means *nobody personally* is accountable, and it must be reviewed and
   reassigned to a human.
3. Cross-check the last sign-in of owners of production agents: the user's **Overview** in Entra, the
   **Last interactive sign-in time** column you can add to the Users list, or `signInActivity` in the
   Graph call above (offline, `last_sign_in_utc`). An owner who has not signed in for months is a
   lifecycle signal worth carrying into **WATCH IT**.
4. Write the OWN IT rule so a disabled owner, or an unreviewed shared/service-account owner, is an
   automatic fail — the agent does not clear OWN IT until a live, named human is accountable.

</details>

### 03: Trace connection ownership — the real actor

This is the check most inventories skip, and it is the one that hides the true blast radius. The agent
owner can be present and blameless while the **connection** the agent runs on is owned by someone who
left — and that connection's identity is what actually reaches the data.

<!-- ![Where to read connection owners in the Power Platform admin center — the owner column that inventories built from the agent list alone never surface.](../../media/ex06_t02_kt03_s01.png) -->

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, find every connection it uses and read who owns it and how it authenticates. In
   **Copilot Studio**, the agent's **Settings → Connection Settings** lists its connections, and on its
   **Tools** page each tool's **Details** → **Additional details** show whether it uses **End user** or
   **Maker-provided** credentials. (Opening an agent requires being its owner or a co-author.) Then read
   each connection's owner from the environment's connections list, signed in with
   `az login --allow-no-subscriptions`:

   ```bash
   az rest --method get --url "https://api.powerapps.com/providers/Microsoft.PowerApps/scopes/admin/environments/<environment-id>/connections?api-version=2016-11-01" --resource https://service.powerapps.com/
   ```

   Each connection shows its name (`properties.displayName`), its connector (the last segment of
   `properties.apiId`), and its owner (`properties.createdBy.userPrincipalName`). Offline, use
   [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}): read
   `used_by_agent`, `connection_owner_upn`, and `auth_type`.
2. Compare the connection owner to the agent owner. Where they differ, the connection owner is the
   identity actually exercising authority — record it as the *effective* owner, and check that account in
   Entra exactly as you did in step 02 (offline, in
   [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %})). A connection owned by a
   disabled account is a live credential with no accountable human behind it.
3. Note every connection whose acting identity is not the requesting user: one that runs as a **service
   account**; a **static key or bearer token in configuration** (in an HTTP request node or MCP call on
   the agent's **Topics** page); or a **shared** connection — handed to a group, or lent to everyone who
   can chat with an agent whose tool runs on **Maker-provided credentials**. To see who a connection is
   shared with, ask for its role assignments, where `<connection-name>` is the connection's `name` from
   the call above, not its display name:

   ```bash
   az rest --method get --url "https://api.powerapps.com/providers/Microsoft.PowerApps/scopes/admin/environments/<environment-id>/apis/<connector>/connections/<connection-name>/roleAssignments?api-version=2016-11-01" --resource https://service.powerapps.com/
   ```

   Offline, read the `auth_type` and `shared_with` columns. Carry each of these straight into
   [SCOPE IT]({% link docs/06_security_baseline/06_03.md %}) and the confused-deputy checks in
   [CONTROL IT]({% link docs/06_security_baseline/06_04.md %}).
4. Write the OWN IT rule so **connection ownership is verified alongside agent ownership**. An agent whose
   connection owner is disabled, unknown, or a departed admin does not clear OWN IT — regardless of who
   owns the agent itself.

</details>

## Summary

OWN IT replaces a single ambiguous "owner" with three named roles and — critically — forces you to trace
the **connection** owner, the identity the agent truly acts as. By joining agent owners, account status,
and connection owners — in the tenant or from your CSVs — you can find owners who have been offboarded,
shared mailboxes with nobody behind them, and connections whose real authority belongs to someone who
left. The trust boundary named here is the one inventories miss: *agent owner ≠ connection owner*, and the
connection is the real actor. Next, in
[SCOPE IT]({% link docs/06_security_baseline/06_03.md %}), you take that acting identity and ask what it
is allowed to reach.
