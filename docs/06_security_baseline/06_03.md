# Task 06-03 — SCOPE IT: least privilege in practice

## Introduction

SCOPE IT is where least privilege stops being a slogan. Every agent acts with one or more credentials, and
those credentials carry permissions, connectors, tools, and API reach. The security question is blunt:
**whose authority is this agent exercising, and what can it reach when it does?** If the answer is "more
than the job needs," you have found the gap before an attacker does. Use your Exercise 05 matrix: where
least privilege closed a failure, this stage makes it a requirement.

## Description

Take your Exercise 03 **Agent Access Map** and turn it into the five SCOPE IT criteria: understood acting
credential, least-privilege permissions, connectors limited to the job, minimally scoped grounding, and
integrations that authenticate per-user with **no secrets in configuration**. Run each Halcourt agent
through those checks and write the rule that reduces effective access to the minimum the purpose requires.
Each key task gives the tenant route and, where it differs, the offline route through the artifact pack.

## Success Criteria

- [ ] For every knowledge source, connector, tool, flow, HTTP integration and MCP integration, you named
      the **acting credential** — the end user's, the maker's or connection owner's, a service account's,
      a flow owner's, or a static key or token.
- [ ] Permissions are least-privilege — for Dataverse, a scoped security role and narrowed record-level
      access, not a broad customizer/admin role.
- [ ] **Connectors and tools** are limited to what the purpose needs; MCP operations the agent can invoke
      are trimmed to the specific operations required.
- [ ] **Grounding** is scoped to the minimum content; whole-site or whole-drive grounding is justified or
      narrowed so the agent's data reach does not exceed its users'.
- [ ] HTTP/MCP integrations authenticate **per-user where possible**, validate input, and hold **no
      static secrets in the action configuration**.

## Key Tasks

### 01: Name the acting credential per operation

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, open it in Copilot Studio (you must be its owner or a co-author).
2. List every operation the agent uses:
   a. knowledge sources, on the **Knowledge** page;
   b. connectors, tools and flows, on the **Tools** page;
   c. HTTP request nodes and MCP calls, on the **Topics** page.
3. For each tool, open **Details → Additional details** and note **End user** or **Maker-provided**.
4. For each Maker-provided connection, read the connection's owner with `az rest`
   (`properties.createdBy.userPrincipalName`), as in [OWN IT]({% link docs/06_security_baseline/06_02.md %}).
5. For each HTTP and MCP call on **Topics**, note what the node authenticates with.
6. Record the acting credential for each operation.
7. Write down the agent's effective access — what those credentials can reach together.
8. Compare effective access with the intended users' own access from KNOW IT.

Without the tenant: read `auth_type` and `connection_owner_upn` from
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}), alongside your
inventory's grounding and tool columns.

</details>

{: .note }
> The agent's Entra Agent ID, the requesting user, the connection owner and the acting credential are
> related but distinct. One agent can use several acting credentials at once.

{: .note }
> Where the agent reaches data or actions its users can't, you have a scope problem to fix here, an
> authorization problem for CONTROL IT, or both.

### 02: Reduce the connector, tool, and API surface to the job

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each connector, tool and endpoint from Key Task 01:
   a. check whether the stated purpose requires it;
   b. mark any with no purpose-justification for removal.
2. For each **HTTP action**:
   a. note how it authenticates (per-user, scoped token, or static key);
   b. note whether user-supplied parameters are validated;
   c. note which API endpoints it can reach;
   d. note where the secret is stored.
3. For each **MCP server**:
   a. list what the server advertises;
   b. list what the agent's topics call;
   c. list what the token is authorized to invoke;
   d. mark every operation beyond what the purpose needs for removal.
4. Write the SCOPE IT rule:
   a. connectors and tools limited to the job;
   b. HTTP with per-user or scoped-token auth, input validation, a least-privilege API, and the secret in
      Key Vault, not in the action configuration;
   c. MCP trimmed to the operations the purpose needs.

Without the tenant: use your inventory's tool columns and
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}).

</details>

{: .note }
> A static key in an action header authenticates the key, not the user, and travels with any export of the
> agent.

{: .note }
> What an MCP server advertises, what the agent calls, and what the token can invoke are three different
> lists. Scope is set by the widest one.

### 03: Scope permissions and grounding to the minimum

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each Dataverse-backed agent:
   a. in the Power Platform admin center, open **Manage → Environments** → the environment → **Settings →
      Users + permissions → Security roles**;
   b. select the acting account's role and choose **… → Members** to confirm who holds it;
   c. replace broad roles (System Customizer, org-wide read/write on tables holding PII) with a scoped
      role;
   d. narrow record-level access with ownership, business units, teams and sharing.
2. For each grounded agent:
   a. open the agent's **Knowledge** page and note how far each source reaches;
   b. narrow whole-site or whole-drive grounding to the specific library or documents the purpose
      requires.
3. Re-ask the SCOPE IT question: with the scoped role, narrowed record-level access and narrowed
   grounding, can the agent still reach anything its intended users couldn't obtain themselves? If yes,
   keep scoping.
4. Write the SCOPE IT rule so least-privilege permissions (scoped role + narrowed record-level access) and
   minimally scoped grounding are required, with the agent's data reach bounded by its intended users'
   reach.

Without the tenant: the pack carries no security roles and doesn't show how far a grounding source
reaches; record both as open questions and use your inventory's grounding column.

</details>

{: .note }
> A shared service identity has one fixed security context. Scoping it shrinks the blast radius, but
> requester-specific access needs on-behalf-of authorization, a requester-aware check, or a deliberately
> fixed data subset.

{: .note }
> Whole-site or whole-drive grounding pulls in whatever the acting credential can see, including folders
> the intended users can't.

## Summary

SCOPE IT is least privilege made concrete: you named the acting credential for each operation, measured
effective access against intended users, and drove that reach down through scoped Dataverse roles and
narrowed record-level access, trimmed connectors and MCP operations, per-user integration auth with no
secrets in configuration, and narrowed grounding. This is where you turn your Exercise 05 least-privilege
verdicts into requirements. SCOPE IT doesn't change whose credential acts for a shared or service
connection — that's an authorization question for
[CONTROL IT]({% link docs/06_security_baseline/06_04.md %}).
