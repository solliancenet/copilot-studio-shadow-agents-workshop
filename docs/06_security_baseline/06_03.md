# Task 06-03 — WATCH IT: logging, detection, lifecycle review

## Introduction

Controls fail quietly. An agent that was scoped correctly in March acquires a new connector in June; an
owner leaves and their connection keeps sending mail; a "test" agent slides into production use. WATCH IT
is the stage that assumes something *will* drift and asks: would you know? It has three jobs — make
actions **logged and attributable**, stand up **detection** for anomalous behavior, and schedule the
**lifecycle and permission reviews** that catch orphans and creep before they become incidents.

## Description

Turn monitoring from an afterthought into three standing commitments on the checklist: attributable
logging, anomaly/exfiltration detection, and a scheduled lifecycle + permission review with orphan
detection. Use the Halcourt estate to test attribution and build the recurring review query. Each key task
gives the tenant route first and the artifact-pack route where one applies.

## Success Criteria

- [ ] Agent actions are **logged**, and for each agent whose acting credential is shared or a service
      identity you **tested attribution** — correlating the `CopilotInteraction` event with the downstream
      event — and recorded it as complete, cross-log only, partial, or unavailable.
- [ ] **Detection** exists for anomalous behavior and potential exfiltration (unusual data volume, access
      to sensitive stores, out-of-pattern actions).
- [ ] A **scheduled lifecycle and permission review** is defined, with orphan detection on owner departure
      and separate rules for owners, connections, and the agent's identity.
- [ ] The WATCH IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      names *who* runs each review and *how often*, not just that it exists.

## Key Tasks

### 01: Make actions logged and test attribution

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. List where agent activity is logged for your estate:
   a. **Purview → Audit**, `CopilotInteraction` events for each chat;
   b. Dataverse auditing, per environment and table;
   c. the logs of the HTTP API, the MCP server, and flow run history.
2. For each agent whose acting credential is shared or a service identity (flagged in Exercises 02–03), find a
   `CopilotInteraction` event and the matching downstream event.
3. Correlate the two:
   a. by time window;
   b. by the resource touched;
   c. by the transcript thread ID, opened in **DSPM for AI**.
4. Record attribution for each agent as complete, cross-log only, partial, or unavailable.
5. Write the WATCH IT rule: attributable logging is required, and any agent whose attribution is partial or
   unavailable is flagged for the requesting-user authorization fix in CONTROL IT.

Without the tenant: use your Task 05-07 attribution result for Claims Copilot.

</details>

{: .note }
> The downstream log may name `svc-claims` while Copilot Studio's own audit event still identifies the
> requester — correlation is the test.

### 02: Stand up detection for anomalous behavior

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Define "anomalous" for your highest-sensitivity agents:
   a. unusual volumes of records read;
   b. access to a sensitive store the agent rarely touches;
   c. a new connector appearing;
   d. an action far outside normal hours or patterns.
2. Map each signal to a surface and record which signals each covers and which it doesn't:
   a. Defender for Cloud Apps for connected-app and data-movement anomalies;
   b. Purview audit for sensitive-data access;
   c. Power Platform activity logs for configuration changes.
3. Record whether Defender real-time protection is enabled to block risky tool calls for each agent.
4. Write the WATCH IT rule so detection and prevention are specified per sensitivity class.

</details>

{: .note }
> Detection tells you after the fact; real-time protection can stop a risky tool call before it runs. A
> PII-handling agent warrants both; a public-FAQ agent does not.

### 03: Schedule lifecycle and permission review

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Build the recurring review query:
   a. list every agent owner from the Power Platform admin center (**Manage → Inventory**);
   b. list every connection owner from the `az rest` connections list;
   c. check each account in the **Microsoft Entra admin center** under **Entra ID → Users** — the
      **Overview** shows whether it's enabled, and the list can add a **Last interactive sign-in time**
      column — or get both for every account at once in
      [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer){:target="_blank"} with
      `GET https://graph.microsoft.com/v1.0/users?$select=userPrincipalName,displayName,accountEnabled,signInActivity`;
   d. flag every agent or connection whose owner is disabled or long-dormant.
2. Write the owner-departure rules:
   a. owner departure triggers reassignment of the business, technical and security roles;
   b. connections backed by the departed owner's credentials are reviewed, then replaced, reassigned or
      retired;
   c. the Agent ID follows the agent, not the owner — when the agent is retired or deleted, confirm its
      Agent ID is gone;
   d. investigate any residual identity through the supported lifecycle process rather than deleting it by
      name.
3. Schedule a **permission review** on the same cadence: re-run the SCOPE IT checks for roles, connectors,
   tools and grounding.
4. Write the WATCH IT rule so each review names an owner and a frequency, and owner departure triggers
   orphan detection immediately.

Without the tenant: look up each owner UPN from
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) in
[`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}) and flag rows where
`account_enabled` is `FALSE` or `last_sign_in_utc` is old.

</details>

{: .note }
> Most of the estate's worst findings are lifecycle failures a calendar would have caught. Orphan detection
> is the same lookup, run on a schedule.

## Summary

WATCH IT accepts that controls drift and builds the standing commitments that catch the drift:
attributable logging, with attribution tested by correlating Copilot Studio's audit event with the
downstream log; anomaly and exfiltration detection sized to each agent's sensitivity; and a scheduled
lifecycle plus permission review with orphan detection wired to owner departure. You built the recurring
review query — from the tenant's admin surfaces or by looking up owners in your CSVs — the same lookup
that finds a departed owner's surviving connection. With all five stages defined, the last task turns them
into the gate an agent must clear: [the production promotion gate]({% link docs/06_security_baseline/06_04.md %}).
