# Task 06-03 — SCOPE IT: least privilege in practice

## Introduction

SCOPE IT is where least privilege stops being a slogan. Every agent has an acting identity, and that
identity carries permissions, connectors, tools, and API reach. The security question is blunt: **whose
authority is this agent exercising, and what can it reach when it does?** If the answer is "more than the
job needs," you have found the gap before an attacker does. This is also where the honest lesson from
Module 5 lands — over-permission is one of the failures a real fix genuinely **CLOSES IT**, so scoping
here is not defense-in-depth theater, it is the actual remedy.

## Description

Take your Module 3 **Agent Access Map** and turn it into the five SCOPE IT criteria: understood acting
identity, least-privilege permissions, connectors limited to the job, minimally scoped grounding, and
integrations that authenticate per-user with **no secrets in configuration**. Run each Halcourt agent
through those checks and write the rule that reduces effective access to the minimum the purpose requires.

**Offline path.** Use [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %})
for the acting identity and auth type of each agent, cross-referenced with your inventory's grounding and
tool columns. The [Agent Access Map]({% link worksheets/templates/02-agent-access-map.md %}) template is
the structure for the per-agent analysis; the artifact pack supplies every value you need offline.

## Success Criteria

- [ ] The **acting identity** of each agent is named: the agent's own identity, the user's delegated
      context, or a shared/service connection.
- [ ] Permissions are **least-privilege** — for Dataverse, a scoped security role plus row-level security
      where relevant, not a broad customizer/admin role.
- [ ] **Connectors and tools** are limited to what the purpose needs; over-wide tool schemas (for example
      an MCP server exposing arbitrary-query tools) are trimmed to the specific operations required.
- [ ] **Grounding** is scoped to the minimum content; whole-site or whole-drive grounding is justified or
      narrowed so the agent's data reach does not exceed its users'.
- [ ] HTTP/MCP integrations authenticate **per-user where possible**, validate input, and hold **no
      static secrets in the action configuration**.

## Key Tasks

### 01: Name the acting identity and its reach

Before you can scope anything, you have to know *who acts*. The three cases have very different blast
radii, and the platform does not label them for you.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, classify the acting identity as one of: **agent identity** (its own auto-created Entra
   identity), **user-context / delegated** (acts as the signed-in user), or **shared / service
   connection** (acts as a service account or a connection owned by someone else). Read `auth_type` and
   `connection_owner_upn` from [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %})
   to decide.
2. For each, write down what that identity can reach — the union of every connector, tool, and grounding
   source it touches. This is *effective access*, and it is the number least privilege must shrink.
3. Compare effective access to the **intended users'** own access from KNOW IT. Where the agent can reach
   data or actions its users personally cannot, you have a scope problem to fix here (over-permission) or
   an authorization problem to fix in CONTROL IT (confused deputy) — often both.

</details>

### 02: Reduce the connector, tool, and API surface to the job

An agent inherits the full reach of everything it is wired to. A connector present "just in case", a tool
schema wider than the task, or an API that returns more than asked all expand the surface an attacker or
an injected instruction can use.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. List each agent's connectors, tools/actions, and external endpoints (HTTP and MCP) — including calls
   wired inside topics, which the agent's Tools page doesn't show. For every one, ask whether the *stated
   purpose* requires it. A connector or tool with no purpose-justification is removed.
2. For **HTTP actions**, treat the auth design as part of scope: a single static, full-scope API key in
   the action header authenticates *the key, not the user*, and travels with any export of the agent.
   The rule is per-user or scoped-token auth, input validation on any user-supplied parameter, a
   least-privilege API that exposes only the needed endpoints, and the secret in Key Vault — never in the
   action configuration.
3. For **MCP servers**, the tool schema is the contract. A server that advertises broad operations (for
   example an arbitrary database-query tool) alongside the two the agent needs hands the agent far more
   than its job. Scope the schema down to the specific operations; a wide tool is a wide door.
4. Write the SCOPE IT rule so "connectors and tools limited to the job" and "no secrets in configuration"
   are both explicit, verifiable checkboxes.

</details>

### 03: Scope permissions and grounding to the minimum

The two biggest silent over-grants are a Dataverse role that reads far more rows than the task needs, and
grounding pointed at a whole site or drive when the agent needs a handful of documents.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For Dataverse-backed agents, inspect the security role of the acting identity. Replace broad roles
   (System Customizer, org-wide read/write on tables holding PII) with a scoped role, and add **row-level
   security** so the agent can reach only the rows the requesting user's job justifies — for example, an
   adjuster's own assigned claims rather than every claim and customer record.
2. For grounded agents, check the grounding scope. Whole-site or whole-drive grounding pulls in whatever
   the acting identity can see — including folders the intended users cannot. Narrow grounding to the
   specific library or documents the purpose requires, so the agent's data reach does not exceed its
   users' reach.
3. Confirm the fix by re-asking the SCOPE IT question: with the scoped role, RLS, and narrowed grounding,
   can the agent still reach anything its intended users could not obtain themselves? If yes, keep
   scoping. This is the failure class where least privilege actually **CLOSES IT** — do the work here
   rather than hoping a downstream control compensates.
4. Write the SCOPE IT rule so least-privilege permissions (role + RLS) and minimally scoped grounding are
   required, with the agent's data reach explicitly bounded by its intended users' reach.

</details>

## Summary

SCOPE IT is least privilege made concrete: you named each agent's acting identity, measured its effective
access against its intended users, and drove that reach down through scoped Dataverse roles and row-level
security, trimmed connectors and tool schemas, per-user integration auth with no secrets in
configuration, and narrowed grounding. This is the stage where the over-permission and excess-connector
failures from Module 4 are genuinely closed rather than merely dented. What SCOPE IT does *not* fix is
*whose identity acts* when a shared or service connection is in play — that confused-deputy problem is an
authorization question you take into [CONTROL IT]({% link docs/06_security_baseline/06_04.md %}) next.
