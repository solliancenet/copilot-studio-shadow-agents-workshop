# Task 06-05 — WATCH IT: logging, detection, lifecycle review

## Introduction

Controls fail quietly. An agent that was scoped correctly in March acquires a new connector in June; an
owner leaves and their connection keeps sending mail; a "test" agent slides into production use. WATCH IT
is the stage that assumes something *will* drift and asks: would you know? It has three jobs — make
actions **logged and attributable**, stand up **detection** for anomalous behavior, and schedule the
**lifecycle and permission reviews** that catch orphans and creep before they become incidents.

## Description

Turn monitoring from an afterthought into three standing commitments on the checklist: attributable
logging, anomaly/exfiltration detection, and a scheduled lifecycle + permission review with orphan
detection. Use the Halcourt estate to build the recurring review query and to see the one place logging
cannot help you.

**Offline path.** [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}) carries
`account_enabled` and `last_sign_in_utc`; joined to
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) it *is* your
first lifecycle-review query — the exact join a scheduled review would run every month.

## Success Criteria

- [ ] Agent actions are **logged**, and the logging that exists is attributable to the **real requester**
      wherever the acting identity is a shared or service identity — with the attribution gaps documented.
- [ ] **Detection** exists for anomalous behavior and potential exfiltration (unusual data volume, access
      to sensitive stores, out-of-pattern actions).
- [ ] A **scheduled lifecycle and permission review** is defined, including **orphan detection** triggered
      on owner departure or account disablement.
- [ ] The WATCH IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      names *who* runs each review and *how often*, not just that it exists.

## Key Tasks

### 01: Make actions logged — and find where attribution breaks

Logging tells you *what happened*. The harder question is *who really asked* — and when a shared identity
acts on behalf of many users, the log records the shared identity, not the person. Naming that gap is part
of the control, not a footnote.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Identify where agent activity is logged for your estate — Power Platform activity logging and Purview
   audit for the platform actions, plus the logs of any downstream system (Dataverse, the HTTP API, the
   MCP server).
2. For each agent whose acting identity is a **service account or shared connection** (from OWN IT), test
   the attribution: if this agent takes an action, does any log record the *requesting user*, or only the
   shared identity? Where only the shared identity appears, you cannot reconstruct who really asked —
   record it as a known attribution gap that logging alone **MISSES IT** on.
3. Write the WATCH IT rule so attributable logging is required, and so agents with an unavoidable
   attribution gap are flagged for the requesting-user authorization fix from CONTROL IT rather than
   treated as adequately monitored.

</details>

### 02: Stand up detection for anomalous behavior

Attributable logs are the raw material; detection is what turns them into a signal before the quarterly
review. The point is to catch the exfiltration or the out-of-pattern action while it still matters.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Define what "anomalous" means for your highest-sensitivity agents: unusual volumes of records read,
   access to a sensitive store the agent rarely touches, a new connector appearing, or an action taken
   far outside normal hours or patterns.
2. Map those signals to a detection surface — Defender for Cloud Apps for connected-app and data-movement
   anomalies, Purview audit for sensitive-data access, and Power Platform activity logs for configuration
   changes. Record which signal each covers and, honestly, which it does not.
3. Write the WATCH IT rule so detection is *specified per sensitivity class* — a PII-handling agent needs
   exfiltration detection; a public-FAQ agent does not warrant the same investment.

</details>

### 03: Schedule lifecycle and permission review

Most of the estate's worst findings are lifecycle failures that a calendar would have caught: a departed
owner, a surviving connection, a role that grew, a "test" agent doing prod work. Make the review a
standing job with a named owner and a cadence.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Build the recurring review query from the artifact pack: join
   [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}) to
   [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and
   [`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) and surface
   every agent or connection whose owner is disabled (`account_enabled = FALSE`) or long-dormant
   (`last_sign_in_utc` old). This is exactly the join **orphan detection** must run on a schedule.
2. Tie orphan detection to the **joiner-mover-leaver** process: when an owner is disabled, their agents
   and connections must be flagged, reassigned, or retired — connections and agent identities should die
   with the owner, not outlive them. This is the fix that lifecycle failures actually **CLOSES IT**.
   Retire them by name: deleting an agent's environment removes what lives inside it, but in this lab's
   tenant the agents' Entra identities and the connections they held in the default environment both
   survived an environment-level teardown.
3. Schedule a **permission review** on the same cadence: re-run the SCOPE IT checks so roles, connectors,
   tools, and grounding that grew since last review are caught and re-scoped.
4. Write the WATCH IT rule so each review names an owner and a frequency, and so owner-departure triggers
   orphan detection automatically rather than waiting for the next scheduled pass.

</details>

{: .note }
> How much of this Copilot Studio activity Purview audit and Defender surface — and what Agent 365
> contributes to orphaned-agent detection and lifecycle policy — is evolving through 2026. Confirm the
> coverage in your own tenant and record what you actually get, rather than assuming the fullest documented
> capability is available to you today.

## Summary

WATCH IT accepts that controls drift and builds the standing commitments that catch the drift:
attributable logging (with the honest note that a shared acting identity breaks attribution and logging
alone misses "who really asked"), anomaly and exfiltration detection sized to each agent's sensitivity,
and a scheduled lifecycle plus permission review with orphan detection wired to owner departure. You built
the recurring review query straight from the artifact pack — the same join that finds a departed owner's
surviving connection. With all five stages defined, the last task turns them into the gate an agent must
clear: [the production promotion gate]({% link docs/06_security_baseline/06_06.md %}).
