# Task 06-01 — OWN IT: owners and accountability

## Introduction

"Owner" is doing too much work as a single field. An agent needs someone accountable for *what it is for*
(the business owner), someone accountable for *how it is built and connected* (the technical owner), and
someone accountable for *the risk it carries* (security). And there is a second owner the agent UI
doesn't show you: the **connection owner**, who created the connection the agent's tools use. Whether that
connection's credential is what acts depends on how each tool authenticates — SCOPE IT works that out.

## Description

Split the single "owner" into three accountable roles, then verify two things the platform will not
verify for you: that owner accounts are **live and appropriate**, and that the **connection** behind each
agent is owned by someone enabled and known. Use the Halcourt estate to find where those checks fail,
then write the OWN IT rules so they catch the same failures anywhere.

Each key task gives the tenant route first and ends with the artifact-pack line to use without the tenant.

## Success Criteria

- [ ] Every agent has a named **business owner**, **technical owner**, and **security accountability**
      (they may be the same person for small agents, but each role is named).
- [ ] Every agent owner is an **enabled** account — not a disabled/departed user, not (unreviewed) a
      shared mailbox or service account with no human behind it.
- [ ] Every **connection** an agent uses is traced to its owner, that owner is enabled and known, and you
      recorded — separately — the agent owner, connection owner, and how each tool authenticates.
- [ ] The OWN IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      requires connection ownership to be verified, not just agent ownership.

## Key Tasks

### 01: Separate the three ownership roles

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, record:
   a. a **business owner** — accountable for the agent's purpose and continued need;
   b. a **technical owner** — maintains the configuration, connectors, and connections;
   c. a **security accountability** — signs off that the residual risk is acceptable.
2. Where one person holds all three roles, record that they hold each one.
3. Write the OWN IT rule so all three roles are named at registration time, and so "the maker who built
   it" is never the security-accountable party by default.

</details>

{: .note }
> One name in an "owner" field is a place to point after an incident, not accountability. A small agent
> may have one person in all three roles; the failure is *no one* holding the security role.

### 02: Verify owner accounts are live and appropriate

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Read each agent's owner from the **Owner** column in the Power Platform admin center's
   **Manage → Inventory**.
2. Check each owner's account status:
   a. in the **Microsoft Entra admin center**, open **Entra ID → Users** and read the user's
      **Overview**;
   b. or check every account at once in
      [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer){:target="_blank"}:

      ```http
      GET https://graph.microsoft.com/v1.0/users?$select=userPrincipalName,displayName,accountEnabled,signInActivity
      ```

   c. flag any owner whose account is disabled.
3. Flag owners that are not a named person:
   a. **shared mailboxes** — in the **Exchange admin center**, **Recipients → Mailboxes**, filtered to
      shared;
   b. **service accounts** — judge from the account's name and what it is used for.
4. Read the last sign-in of each production agent's owner — the user's **Overview**, the **Last
   interactive sign-in time** column in the Users list, or `signInActivity` from the Graph call — and
   note any owner who hasn't signed in for months.
5. Write the OWN IT rule: a disabled owner, or an unreviewed shared-mailbox or service-account owner, is
   an automatic fail until a live, named human is accountable.

Without the tenant: look up each `owner_upn` from
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) in
[`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}) and flag rows where
`account_enabled` is `FALSE`, `is_shared_mailbox` is `TRUE`, or `is_service_account` is `TRUE`; read
`last_sign_in_utc` for step 4.

</details>

{: .note }
> The platform keeps an agent published under an owner who has left. A disabled account owning a live
> agent is an orphan; a shared mailbox as owner means nobody personally is accountable. A long-idle owner
> is a lifecycle signal for **WATCH IT**.

### 03: Trace connection ownership

<!-- ![Where to read connection owners in the Power Platform admin center — the owner column that inventories built from the agent list alone never surface.](../../media/ex06_t01_kt03_s01.png) -->

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In **Copilot Studio**, open the agent's **Settings → Connection Settings** and list its connections.
   (Opening an agent requires being its owner or a co-author.)
2. On the agent's **Tools** page, open each tool's **Details → Additional details** and record whether it
   uses **End user** or **Maker-provided** credentials.
3. Sign in with `az login --allow-no-subscriptions`, then read each connection's owner from the
   environment's connections list:

   ```bash
   az rest --method get --url "https://api.powerapps.com/providers/Microsoft.PowerApps/scopes/admin/environments/<environment-id>/connections?api-version=2016-11-01" --resource https://service.powerapps.com/
   ```

   a. name: `properties.displayName`;
   b. connector: the last segment of `properties.apiId`;
   c. owner: `properties.createdBy.userPrincipalName`.
4. Record, separately for each tool:
   a. the agent owner;
   b. the connection owner;
   c. how the tool authenticates.
5. Check each connection owner's account status as in Key Task 02.
6. Read who each connection is shared with, where `<connection-name>` is the connection's `name` from the
   call above, not its display name:

   ```bash
   az rest --method get --url "https://api.powerapps.com/providers/Microsoft.PowerApps/scopes/admin/environments/<environment-id>/apis/<connector>/connections/<connection-name>/roleAssignments?api-version=2016-11-01" --resource https://service.powerapps.com/
   ```

7. Write the OWN IT rule so connection ownership is verified alongside agent ownership. An agent whose
   connection owner is disabled, unknown, or departed does not clear OWN IT.

Without the tenant: read `used_by_agent`, `connection_owner_upn`, `auth_type`, and `shared_with` in
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}), and look up each
`connection_owner_upn` in [`users-export.csv`]({% link worksheets/artifact-pack/users-export.csv %}).

</details>

{: .note }
> The connection owner is who created the connection — an accountability fact. Whether that connection's
> credential is what acts at runtime depends on how each tool authenticates: with **Maker-provided**
> credentials it is; with **End user** credentials the requester acts. SCOPE IT works that out per tool.

{: .note }
> Carry service-account connections, static keys or tokens in HTTP or MCP nodes, and shared connections
> into [SCOPE IT]({% link docs/06_security_baseline/06_02.md %}) and the confused-deputy checks in
> [CONTROL IT]({% link docs/06_security_baseline/06_03.md %}).

## Summary

OWN IT replaces a single ambiguous "owner" with three named roles and forces you to trace the
**connection** owner as well as the agent owner. By cross-referencing agent owners, account status, and
connection owners — in the tenant or from your CSVs — you can find owners who have been offboarded, shared
mailboxes with nobody behind them, and connections created by someone who left. The trust boundary named
here is the one inventories miss: agent owner ≠ connection owner, and neither is automatically the
identity that acts — SCOPE IT works that out per tool. Next, in
[SCOPE IT]({% link docs/06_security_baseline/06_02.md %}), you ask what each acting credential is allowed
to reach.
