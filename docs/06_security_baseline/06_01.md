# Task 06-01 — KNOW IT: inventory, classify, understand purpose

## Introduction

You cannot secure what you cannot see. Every downstream stage — ownership, scope, controls, monitoring —
assumes the agent is already *in the inventory*. The agents that hurt you are the ones that never made it
onto the list: the personal-environment bot nobody sanctioned, the "test" agent doing production work.
KNOW IT is the first gate, and it is the one most estates fail silently.

## Description

Take your Module 2 **Agent Estate Inventory** and distil it into the three KNOW IT criteria on the
checklist: *complete cross-environment inventory*, *documented purpose and intended users*, and
*data-sensitivity classification*. Run the Halcourt estate through those criteria as the worked example,
then write each criterion as a rule you could apply to an estate you have never seen.

**Offline path.** Everything you need is in the [artifact pack]({% link worksheets/index.md %}#the-artifact-pack).
Treat [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and
[`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}) as a real tenant
export and join them exactly as you would at home — no live tenant required.

## Success Criteria

- [ ] Every agent across **all four** environments appears in one inventory; no environment is omitted.
- [ ] Each agent has a one-line documented **purpose** and a named **intended user population**.
- [ ] Each agent carries a **data-sensitivity classification** for what it can reach (for example: PII,
      compensation, internal, public/none).
- [ ] The KNOW IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      is written as a reusable rule, not a one-off note about Halcourt.

## Key Tasks

### 01: Confirm a complete, cross-environment inventory

An inventory is only as good as its blind spots. The environments most likely to be missing from a
"sanctioned" list are the **default** environment (everyone can build there) and any **developer /
personal** environment (invisible unless you enumerate every environment in the tenant).

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. Open [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}) and list
   every environment and its type. Confirm you are accounting for all four — not just the production one.
2. Open [`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) and confirm at least
   one agent maps to each environment. An environment with zero agents in your list is a signal you did
   not enumerate it, not proof it is empty. In a live tenant it can also mean the account you enumerated
   with holds no role there (Task 02-01).
3. Count the agents. Write the KNOW IT rule so it forces coverage of **every** environment, explicitly
   including the default and any personal/developer environment — the ones a partial inventory skips.
4. In the live tenant, the equivalent enumeration is the Power Platform admin center environment list (or
   the CoE Starter Kit inventory). Note that the artifact pack is a point-in-time export; the rule must
   say *how often* the inventory is refreshed.

</details>

### 02: Document purpose and intended users

The `description` column is a starting point, not a classification — and in this pack it was written by
hand: the Dataverse agent table an admin export reads has no description column, so purpose is something a
person has to record. "Helps employees submit expenses" tells you nothing about *who* is supposed to use
the agent or *what* it is allowed to do on their behalf.
Purpose and intended-user population are the yardstick every later stage measures against.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, write one sentence of purpose in your own words and name the intended user population —
   distinguish "any employee" from a scoped team (for example, claims adjusters, underwriters, or the HR
   team). The population matters: an agent open to *any employee* has a much larger set of untrusted
   inputs than one scoped to a small team.
2. Where the stated purpose is narrow but the agent's reach is wide, flag it now. Purpose is the number
   you will compare against effective access in **SCOPE IT**: a benefits agent whose purpose is "answer
   open-enrollment questions" should not need to read an executive compensation file.
3. Write the KNOW IT rule so purpose and intended users are recorded *before* an agent is considered for
   promotion — not reconstructed afterward from what it happens to touch.

</details>

### 03: Classify the data sensitivity it can reach

Classify by what the agent can *reach*, not by what it was *meant* to touch — those differ, and the gap
is the finding. Cross-reference each agent's grounding sources and connectors from your inventory.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, note the grounding sources and connectors from your Module 2 inventory (SharePoint
   sites, Dataverse tables, HTTP and MCP endpoints, mailboxes).
2. Assign a sensitivity class to the *most sensitive* data reachable through any of them. An agent that
   can reach a Dataverse `Customer` table (SSN, DOB) or an HR/benefits site is handling PII or
   compensation data; one grounded on a single all-staff-published FAQ library is handling public
   content. When in doubt, classify up.
3. Record the classification per agent. It becomes the direct input to **CONTROL IT** (which agents need
   sensitivity labels and DLP) and to the **promotion gate** (a PII-handling agent faces a higher bar
   than a public-FAQ agent).

</details>

## Summary

KNOW IT turns "we have some agents somewhere" into a complete, classified, purpose-documented list that
spans every environment. You confirmed the inventory covers the default and personal environments where
agents hide, wrote a one-line purpose and intended-user population for each, and classified the
sensitivity of the data each can reach. That classification is the yardstick for every stage that
follows — you cannot scope, control, or watch an agent whose data reach you have not named. Next, in
[OWN IT]({% link docs/06_security_baseline/06_02.md %}), you make each of these agents accountable to a
real, live person.
