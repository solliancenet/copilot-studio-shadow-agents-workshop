# Task 06-01 — KNOW IT: inventory, classify, understand purpose

## Introduction

You cannot secure what you cannot see. Every downstream stage — ownership, scope, controls, monitoring —
assumes the agent is already *in the inventory*. The agents that hurt you are the ones that never made it
onto the list: the personal-environment bot nobody sanctioned, the "test" agent doing production work.
KNOW IT is the first gate, and it is the one most estates fail silently.

## Description

Take your Exercise 02 **Agent Estate Inventory** and distil it into the three KNOW IT criteria on the
checklist: *complete cross-environment inventory*, *documented purpose and intended users*, and
*data-sensitivity classification*. Run the Halcourt estate through those criteria as the worked example,
then write each criterion as a rule you could apply to an estate you have never seen.

Each key task gives the tenant route first and ends with the artifact-pack line to use without the tenant.

## Success Criteria

- [ ] Every agent across **all four** environments appears in one inventory; no environment is omitted.
- [ ] Each agent has a one-line documented **purpose** and a named **intended user population**.
- [ ] Each agent carries a **data-sensitivity classification** for what it can reach (for example: PII,
      compensation, internal, public/none).
- [ ] The KNOW IT section of your [checklist]({% link worksheets/templates/05-agent-security-review-checklist.md %})
      is written as a reusable rule, not a one-off note about Halcourt.

## Key Tasks

### 01: Confirm a complete, cross-environment inventory

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Power Platform admin center**, open **Manage → Environments**:
   a. list every environment;
   b. record each environment's type.
2. Open **Manage → Inventory**:
   a. filter to Copilot Studio agents;
   b. map each agent to its environment;
   c. mark any environment with no agents mapped to it.
3. Count the agents, per environment and in total.
4. Write the KNOW IT rule:
   a. the inventory covers **every** environment, including the default and any developer or personal
      environment;
   b. the rule states how often the inventory is refreshed.

Without the tenant: read
[`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}) and
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}) from the
[artifact pack]({% link worksheets/index.md %}#the-artifact-pack).

</details>

{: .note }
> An environment with zero agents means you didn't enumerate it, or the account you used holds no role
> there (Task 02-01) — not that it is empty.

{: .note }
> Any inventory — the admin center, a **Download** from Inventory, or your CSVs — is a point-in-time
> snapshot. That is why the rule needs a refresh cadence.

### 02: Document purpose and intended users

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. In the **Microsoft 365 admin center**, open **Agents → All agents → Registry**, select each agent, and
   read the description on its **Details** tab.
2. For each agent:
   a. write one sentence of purpose in your own words;
   b. name the intended user population — "any employee" or a scoped team (for example, claims
      adjusters, underwriters, or the HR team).
3. Flag every agent whose stated purpose is narrow but whose reach is wide.
4. Write the KNOW IT rule so purpose and intended users are recorded *before* an agent is considered for
   promotion.

Without the tenant: read the `description` column in
[`agents-export.csv`]({% link worksheets/artifact-pack/agents-export.csv %}).

</details>

{: .note }
> A description is a starting point, not a purpose statement. Where the maker set none, a person has to
> write one — the pack's `description` column was written by hand for that reason.

{: .note }
> An agent open to *any employee* takes far more untrusted input than one scoped to a small team. Purpose
> is what SCOPE IT compares against effective access.

### 03: Classify the data sensitivity it can reach

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent, list the grounding sources and connectors from your Exercise 02 inventory:
   a. SharePoint sites;
   b. Dataverse tables;
   c. HTTP and MCP endpoints;
   d. mailboxes.
2. Assign a sensitivity class to the *most sensitive* data reachable through any of them. When in doubt,
   classify up.
3. Record the classification per agent.

Without the tenant: cross-reference the inventory you built from the artifact pack in Exercise 02.

</details>

{: .note }
> Classify by what the agent can *reach*, not what it was meant to touch — the gap is the finding. An
> agent that can reach the Dataverse `Customer` table (SSN, DOB) or an HR/benefits site handles PII or
> compensation data; an agent grounded only on content every employee can already read is handling
> internal content.

{: .note }
> The classification feeds **CONTROL IT** (which agents need labels and DLP) and the **promotion gate** (a
> PII-handling agent faces a higher bar).

## Summary

KNOW IT turns "we have some agents somewhere" into a complete, classified, purpose-documented list that
spans every environment. You confirmed the inventory covers the default and personal environments where
agents hide, wrote a one-line purpose and intended-user population for each, and classified the
sensitivity of the data each can reach. That classification is the yardstick for every stage that
follows — you cannot scope, control, or watch an agent whose data reach you have not named. Next, in
[OWN IT]({% link docs/06_security_baseline/06_02.md %}), you make each of these agents accountable to a
real, live person.
