# Task 06-04 — CONTROL IT: environment, DLP, identity, authorization, data

## Introduction

SCOPE IT shrank what each agent *is*. CONTROL IT surrounds it with the platform's guardrails: the right
environment with a DLP policy, authorization that checks the **requesting user** instead of a shared
identity, sensitivity labels on the data it can reach, and Conditional Access on the identity itself. You
already learned the honest part in Module 5 — some of these controls **CLOSES IT**, several only
**DENTS IT** for the hard cases (indirect injection, confused deputy). CONTROL IT is layered defense
precisely *because* no single toggle carries the whole load.

## Description

Take your Module 5 **Control Efficacy Matrix** and turn its verdicts into the four CONTROL IT criteria:
governed environment with DLP, authorization against the requesting user, data controls
(labels/Purview), and Conditional Access for the agent/workload identity. Decide, per criterion, what the
control actually addresses — and where you must layer a second control because the first only dents the
failure.

**Offline path.** Use [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %})
to see which environments carry a DLP policy and which do not, and
[`connections-export.csv`]({% link worksheets/artifact-pack/connections-export.csv %}) for the acting
identities that authorization must account for. Your completed
[Control Efficacy Matrix]({% link worksheets/templates/04-control-efficacy-matrix.md %}) supplies the
per-failure verdicts you distil into rules here.

## Success Criteria

- [ ] Each agent doing real work lives in an environment with an **appropriate DLP policy** — not the
      default environment, and not a "sandbox" that quietly became production.
- [ ] Authorization is enforced against the **requesting user**, not a shared/owner/service identity,
      wherever the agent takes a consequential action or reads sensitive data.
- [ ] **Sensitivity labels / Purview** are applied to the data the agent can reach, so classification
      travels with the content the agent might return.
- [ ] **Conditional Access** for the agent/workload identity has been considered and its applicability
      recorded (with the caveat that it constrains authentication, not post-auth authorization).

## Key Tasks

### 01: Place the agent in a governed environment with DLP

Environment is the coarse control that decides *which connectors are even usable*. An agent that handles
real data in an environment with no DLP has no connector guardrail at all — and "test" is not a category
of exposure, it is only a label.

![The DLP policy view in the Power Platform admin center — confirm the environment an agent lives in is actually covered, not just named "prod".](../../media/ex06_t04_kt01_s01.png)

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. From [`environments-export.csv`]({% link worksheets/artifact-pack/environments-export.csv %}), list
   which environments have a `dlp_policy` and which have an empty one. Any agent doing real work in an
   environment with no DLP is a CONTROL IT fail until it is moved or the environment is governed.
2. Treat the exposure, not the label. An environment named or typed "sandbox/test" that is used for
   production work needs production-grade DLP — or the agent moves to a managed production environment.
   Ephemeral, gated test environments prevent the test-becomes-prod drift in the first place.
3. Write the CONTROL IT rule so an agent must live in an environment whose DLP matches the sensitivity you
   classified in KNOW IT — with the default environment explicitly disallowed for sensitive agents.

</details>

### 02: Enforce authorization against the requesting user

This is the control for the confused-deputy failure, and it is the one platform toggles struggle with.
When an agent acts as a shared connection or service account, it exercises authority the requesting user
does not personally hold — and neither DLP nor Conditional Access changes *whose* identity acts.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For every agent that takes a consequential action (writes, approvals, sends) or reads sensitive data,
   confirm the authorization decision is made against the **requesting user's** entitlement — either by
   acting in the user's delegated context, or by explicitly checking the user's permission before the
   shared identity performs the action.
2. Where the acting identity is a service account or a connection owned by someone else (you flagged these
   in OWN IT and SCOPE IT), record that this is the failure a user-context / on-behalf-of design
   **CLOSES IT** and a mere least-privilege trim only **DENTS IT** — the escalation pattern persists
   until authorization checks the real requester.
3. Write the CONTROL IT rule so "authorization enforced against the requesting user, not a shared
   identity" is a hard criterion for any agent that can change state or read PII.

</details>

### 03: Apply data controls and consider Conditional Access

The last layer protects the *data* and the *identity*. Labels keep classification attached to sensitive
content the agent might surface; Conditional Access governs where and how the agent's identity can be
used — but only when the downstream system trusts Entra rather than a static key.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. For each agent handling PII or compensation data (from your KNOW IT classification), confirm the target
   content carries the right **sensitivity label** and that auto-labeling covers files that should be
   protected but are not yet. A labeled sensitive file is one a policy can withhold from an agent
   response.
2. Consider **Conditional Access for the agent/workload identity** and record whether it applies. It can
   constrain how the agent identity's token is used, but it does not solve post-auth authorization, and
   it has no effect on an HTTP integration that authenticates with a static key instead of Entra.
3. Layer deliberately: for a failure your matrix marked as only dented by any single control, name the
   *combination* (for example, scoped grounding **plus** a sensitivity label) that together raises the
   bar. Write the CONTROL IT rule so data controls and CA applicability are both recorded, with the
   layering made explicit.

</details>

{: .caution }
> Several controls in this stage depend on 2026 product behavior that changes quickly — how Purview
> classification and DLP cover Copilot Studio responses, how Conditional Access applies to workload/agent
> identities, and which of these Agent 365 surfaces as governance. Treat the exact enforcement as
> something to **verify in your own tenant**, and record the version you tested against rather than
> assuming the documented behavior is live.

## Summary

CONTROL IT wraps each scoped agent in platform guardrails: a governed environment with DLP sized to the
data, authorization that checks the requesting user rather than a shared identity, sensitivity labels on
reachable data, and a recorded Conditional Access decision for the identity. The through-line from Module
5 is honesty — you named which controls close a failure and which only dent it, and layered deliberately
where one control is not enough. What no control here fully guarantees is that you would *notice* a
failure in flight, or that the agent will not outlive its owner. That is
[WATCH IT]({% link docs/06_security_baseline/06_05.md %}).
