# Task 07-01 — The seven questions

## Introduction

The whole day pointed here. You learned to discover, map, break, and control an estate
that was not yours; the seven questions are the reusable frame you take home. Answer them
for your own tenant and you have the start of a real agent security program. You will not
finish an inventory in the time you have — the win is knowing exactly where each answer
lives and which ones you cannot answer yet.

## Description

Work in the question table of the [Own-Estate Assessment]({% link worksheets/templates/06-own-estate-assessment.md %})
worksheet. It has one row per question. For each row, fill the columns:

- **Answer or hypothesis** — what you know, or what you suspect.
- **Evidence checked** — the surface or export you looked at.
- **Unknowns** — what you can't answer yet.
- **Next step**, **Owner**, and **Date** — how the unknown gets answered, by whom, and when.

For each question, reuse the lab technique you already practiced. Point it at the matching Microsoft surface
in your own tenant. The table below maps what you did against Halcourt to what you do at home.

| Question | What you practiced in the lab | Where to look in your tenant |
|---|---|---|
| **Discovery** — how will we inventory our agents? | Joined the five estate exports to list every agent across *all* environments, including the personal ones | The Agent 365 registry (**Microsoft 365 admin center → Agents → All agents → Registry**), then the Power Platform admin center (Agents view), the CoE Starter Kit agent inventory, and Microsoft Graph for agent identities — no single source is complete |
| **Ownership** — who is responsible? | Recorded the *agent* owner, the *connection* owner, and — per operation — the authentication mode and acting credential (Exercise 03) | Agent owner in PPAC / Copilot Studio; connection owner under Connections; for each knowledge source, tool, flow, HTTP or MCP call, whether it uses **End user** or **Maker-provided** credentials and whose credential acts; cross-check every owner against Entra account status |
| **Identity** — which identities need review? | Enumerated the auto-created agent (workload) identities and the accounts connections actually run as | Entra Agent IDs for newer agents, and legacy app-registration service principals tagged `AgentCreatedBy:CopilotStudio` for older ones; each agent's GUID under Copilot Studio → **Settings → Advanced → Metadata → Entra Agent ID**; match active agents against agent identities and investigate any that don't match; plus the service accounts and shared mailboxes behind connections |
| **Access** — which systems/data are highest risk? | Mapped *effective* access: Dataverse rows and PII, whole-site SharePoint grounding, HTTP and MCP endpoints | For Dataverse: which principal authorizes the call, its security-role privilege depth, and which records it reaches through ownership, business units, teams, and sharing; the SharePoint scope each agent grounds on; custom connectors, HTTP actions, and MCP servers, and how each authenticates |
| **Controls** — what do we already have? | Tested DLP, environment strategy, Purview labels, Conditional Access, and logging against real failures | Power Platform DLP policies (and which environments they cover); your environment strategy; Purview labels and DLP; Conditional Access, including workload identities — Conditional Access for agents requires Agent 365, and Agent ID Conditional Access is enforced only when the agent runs in Teams |
| **Detection** — would we know if something went wrong? | Tried to link a downstream event back to *who really asked* (Task 05-07) | The `CopilotInteraction` event in Purview Audit; the downstream Dataverse, flow, API, or MCP log and the credential it records; Defender for Cloud Apps; classify attribution as complete, cross-log only, partial, or unavailable |
| **Gaps** — what do we investigate first? | Prioritized findings by effective access and blast radius, not by how risky an agent *sounded* | Your own ranked list — rank by blast radius first; anything severe you can contain right away goes to the top |

{: .important }
> The findings never live in a single file. In the lab they lived in the *joins* — an
> agent whose owner is disabled, a connection owned by someone who left, an environment
> with no DLP. Your tenant is the same: pull the pieces, then look at what only shows up
> when you put them side by side.

## Success Criteria

- [ ] All seven rows of the question table are filled. Where you don't know, **Unknowns** says so and **Next step**, **Owner**, and **Date** say how you'll find out.
- [ ] Discovery names the specific surfaces you will inventory from and the five exports you will pull.
- [ ] Ownership records the agent owner and the connection owner separately. For each operation it also records the authentication mode and the credential that acts.
- [ ] Ownership flags any shared-mailbox, service-account, or departed-owner cases you already suspect.
- [ ] Identity covers both Entra Agent IDs and legacy app-registration service principals, and lists any identity that doesn't match an active agent.
- [ ] Access ranks at least your top two highest-risk data reaches.
- [ ] Detection classifies attribution as complete, cross-log only, partial, or unavailable, based on what you checked.
- [ ] Gaps names the single question you will investigate first, and why.

## Key Tasks

### 01: Answer "what do we have?" — Discovery, Ownership, Identity, Access

The first four questions build your picture of the estate: what exists, who is
accountable, which identities act, and what those identities can reach.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Discovery.** Decide where you will pull your inventory from. Start with the Agent 365
   registry: **Microsoft 365 admin center → Agents → All agents → Registry**. Then add the
   Power Platform admin center "Agents" view, the CoE Starter Kit agent inventory, and
   Microsoft Graph for agent identities. No single source is complete. You are building the
   join, exactly as you did with the five Halcourt exports. Write the sources in **Evidence
   checked**. Confirm the account you pull with holds a role in every environment. An
   environment that shows no agents may just be one it can't read. *(Offline path: if you
   cannot export yet, use the five artifact-pack CSVs — agents, connections,
   agent-identities, users, environments — as the target schema for what to pull.)*
2. **Ownership.** Record three things separately, as you did in Exercise 03:
   - the agent owner;
   - the connection owner;
   - for each operation (each knowledge source, tool, flow, HTTP or MCP call), the
     authentication mode and the credential that actually acts.

   The connection owner tells you who is accountable and whose departure breaks the
   connection. It doesn't prove which identity authorizes a call. Only the authentication
   mode and acting credential tell you that. Note any owners you suspect are shared
   mailboxes, service accounts, or people who have left.
3. **Identity.** Every agent created since May 2026 has an Entra Agent ID. Older agents
   may still use a legacy app registration until Microsoft migrates them. Look for both:
   - Entra Agent IDs;
   - legacy service principals with the tag `AgentCreatedBy:CopilotStudio`.

   To find one agent's GUID, open the agent in Copilot Studio and go to **Settings →
   Advanced → Metadata → Entra Agent ID**. Match your active agents against the agent
   identities and investigate any that don't match. A mismatch can come from a legacy app
   registration, a migration, or a failed cleanup. Deleting an agent normally deletes its
   Agent ID, so don't assume a deleted agent left it behind.

   The agent's identity is not the credential its tools use. Also list the service
   accounts your connections run as, and any shared or departed accounts still holding
   live connections. In the lab tenant each agent identity was named `<agent name>
   (Microsoft Copilot Studio)`. Confirm yours look the same rather than assuming.
4. **Access.** For your two or three most-used agents, write what they can *actually*
   reach. For Dataverse, write:
   - which principal authorizes the call;
   - its security-role privilege depth;
   - which records it can reach through ownership, business units, teams, and sharing.

   Add the SharePoint scope they ground on, and any HTTP or MCP endpoints and how those
   authenticate. Rank them by the sensitivity of the data behind them, not by the agent's
   name.

</details>

### 02: Answer "are we covered?" — Controls, Detection, Gaps

The last three questions turn the picture into a judgment: what protects the estate today,
whether you would notice a failure, and where you start.

<details markdown="block">
<summary>Expand this section for detailed steps</summary>

1. **Controls.** Inventory what you already run — DLP policies and which environments they
   cover, your environment strategy, Purview labels and DLP, and Conditional Access. Mark
   honestly which agents and environments each control actually touches. Conditional
   Access for agents requires Agent 365. Agent ID Conditional Access is enforced only when
   the agent runs in Teams. A DLP policy
   applied to production only still leaves your default and personal environments wide
   open, and that is usually where the shadow agents live.
2. **Detection.** Test the day's hardest detection question: can your logs tell you *who
   really asked?* Pick one agent action and try to correlate two events:
   - the `CopilotInteraction` event in Purview Audit — the requesting user, the agent, the
     transcript thread ID, and the time;
   - the downstream Dataverse, flow, API, or MCP event, and the credential it records.

   Classify the result as **complete**, **cross-log only**, **partial**, or
   **unavailable**, as you did for Scenario D in Task 05-07. A shared identity is a serious
   risk, but your conclusion must rest on what the logs showed. `CopilotInteraction` events
   are recorded only for users with a Microsoft 365 license, so check your own tenant's
   coverage.
3. **Gaps.** From the six answers above, name the single question you will investigate
   first. Rank by blast radius — what the agent can reach — first. Anything severe you can
   contain right away goes to the top. This becomes one of your first-week actions in the
   next task.

</details>

{: .note }
> Where an answer depends on a fast-moving product detail — which Agent 365 views your
> licensing gives you, which of your agents are already migrated to Entra Agent ID, how
> completely Defender sees Copilot Studio activity — write it down as *"verify in tenant"*
> rather than assuming. Naming the uncertainty is part of the assessment.

## Summary

You now have a diagnosis of your own estate: seven rows, each with an answer or an honest
"we don't know yet, here's how". The frame is reusable — every time a new agent, connection, or
environment appears, you run it back through these seven questions. In the next task you
turn the diagnosis into a plan.
